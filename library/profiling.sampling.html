profiling.sampling — 통계적 프로파일러¶

Added in version 3.15.

소스 코드: Lib/profiling/sampling/

Tachyon 이라는 이름의 profiling.sampling 모듈은 주기적인 스택 샘플링을 통해 Python 프로그램의 통계적 프로파일링을 제공합니다. Tachyon은 코드 변경이나 재시작 없이 스크립트를 직접 실행하거나 실행 중인 모든 Python 프로세스에 연결할 수 있습니다. 샘플링이 대상 프로세스 외부에서 발생하므로 오버헤드가 거의 없으며, 따라서 Tachyon은 개발 및 운영 환경 모두에 적합합니다.

통계적 프로파일링이란 무엇입니까?¶

통계적 프로파일링은 주기적으로 호출 스택의 스냅샷을 캡처하여 프로그램 동작에 대한 그림을 그립니다. 결정론적 프로파일러가 모든 함수 호출과 반환을 인스트루먼트하는 대신, Tachyon은 일정한 간격으로 호출 스택을 읽어 현재 실행 중인 코드를 기록합니다.

이 접근 방식은 단순한 원리에 기초합니다. 상당한 CPU 시간을 소비하는 함수는 수집된 샘플에서 빈번하게 나타난다는 것입니다. Tachyon은 프로파일링 세션 동안 수천 개의 샘플을 수집하여 시간이 어디에 소요되는지에 대한 정확한 통계적 추정치를 생성합니다. 샘플이 많이 수집될수록 이 추정치는 더욱 정교해집니다.

다음 대화형 시각화는 샘플링 프로파일링이 작동하는 방식을 보여줍니다. Play 를 눌러 Python 프로그램 실행을 지켜보고, 프로파일러가 주기적으로 호출 스택의 스냅샷을 캡처하는 것을 관찰하십시오. 샘플 간격 을 조정하여 샘플링 빈도가 결과에 어떤 영향을 미치는지 확인하십시오.

시간 추정 방식¶

Tachyon 출력에 표시되는 시간 값은 직접적인 측정이 아닌 샘플 카운트에서 파생된 추정치 입니다. Tachyon은 수집된 샘플에서 각 함수가 몇 번 나타나는지 계산한 다음, 이를 샘플링 간격으로 곱하여 시간을 추정합니다.

예를 들어, 10kHz 샘플링 속도로 10초 동안 프로파일링을 수행하면 Tachyon은 약 100,000개의 샘플을 수집합니다. 만약 함수가 5,000개의 샘플(전체의 5%)에 나타난다면, Tachyon은 해당 함수가 10초 중 5%의 시간을 소비했다고 추정하며, 이는 약 500밀리초입니다. 이것은 정밀한 측정이 아닌 통계적 추정치입니다.

이러한 추정치의 정확도는 샘플 수에 따라 달라집니다. 100,000개의 샘플을 사용하면 5%를 보이는 함수는 대략 ±0.5%의 오차 범위를 가집니다. 단지 1,000개의 샘플만으로는 같은 5% 측정값이 실제 시간의 3%에서 7%에 해당할 수 있습니다.

이것이 더 긴 프로파일링 지속 시간과 더 짧은 샘플링 간격이 더 신뢰할 수 있는 결과를 제공하는 이유입니다—더 많은 샘플을 수집하기 때문입니다. 대부분의 성능 분석에 대해, 기본 설정값은 병목 현상을 식별하고 최적화 노력을 안내하는 데 충분한 정확도를 제공합니다.

샘플링은 통계적 특성을 가지므로 실행할 때마다 결과에 약간의 차이가 발생합니다. 한 번 실행에서 12%를 보여주는 함수가 다음에는 11%나 13%를 보여줄 수 있습니다. 이는 정상적인 현상이니 걱정하지 않아도 됩니다. 정확한 비율보다는 전체적인 패턴에 초점을 맞추고, 실행 간의 작은 변화는 신경 쓰지 않으셔도 됩니다.

다른 접근 방식을 사용해야 하는 경우¶

통계적 샘플링은 모든 상황에 적합하지 않습니다.

For very short scripts that complete in under one second, the profiler may not collect enough samples for reliable results. Use profiling.tracing instead, or run the script in a loop to extend profiling time.

When you need exact call counts, sampling cannot provide them. Sampling estimates frequency from snapshots, so if you need to know precisely how many times a function was called, use profiling.tracing.

When comparing two implementations where the difference might be only 1-2%, sampling noise can obscure real differences. Use timeit for micro-benchmarks or profiling.tracing for precise measurements.

The key difference from profiling.tracing is how measurement happens. A tracing profiler instruments your code, recording every function call and return. This provides exact call counts and precise timing but adds overhead to every function call. A sampling profiler, by contrast, observes the program from outside at fixed intervals without modifying its execution. Think of the difference like this: tracing is like having someone follow you and write down every step you take, while sampling is like taking photographs every second and inferring your path from those snapshots.

이러한 외부 관찰 모델 덕분에 샘플링 프로파일링은 운영 환경에서 실용성을 가질 수 있습니다. 프로파일되는 프로그램은 내부에서 계측 코드가 실행되지 않아 최대 속도로 작동하며, 대상 프로세스는 샘플링 중 절대 중지되거나 일시 정지되지 않습니다—Tachyon는 프로세스의 메모리에서 호출 스택을 직접 읽어옵니다. 애플리케이션이 관찰되고 있다는 사실을 전혀 알지 못하는 상태로 라이브 서버에 연결하고 데이터를 수집한 뒤 분리할 수 있습니다. 다만, 샘플링 간격 사이에 완료되는 매우 짧게 살아있는 함수는 놓칠 수 있다는 단점이 있습니다.

Statistical profiling excels at answering the question, “Where is my program spending time?” It reveals hotspots and bottlenecks in production code where deterministic profiling overhead would be unacceptable. For exact call counts and complete call graphs, use profiling.tracing instead.

간단한 예제¶

스크립트를 프로파일링하고 즉시 결과를 확인하는 방법:

python -m profiling.sampling run script.py

인자로 모듈 프로파일링하기:

python -m profiling.sampling run -m mypackage.module arg1 arg2

인터랙티브 플레임 그래프 생성:

python -m profiling.sampling run --flamegraph -o profile.html script.py

PID로 실행 중인 프로세스에 연결하기:

python -m profiling.sampling attach 12345

실행 중인 프로세스 스택의 단일 스냅샷 인쇄:

python -m profiling.sampling dump 12345

실시간 모드를 사용하여 모니터링(종료하려면 q 를 누르세요):

python -m profiling.sampling run --live script.py

더 빠른 샘플링 속도로 60초 동안 프로파일링하기:

python -m profiling.sampling run -d 60 -r 20khz script.py

줄별 히트맵 생성:

python -m profiling.sampling run --heatmap script.py

바이트코드 명령을 실행하는지 확인하려면 opcode 레벨 프로파일링을 활성화하세요:

python -m profiling.sampling run --opcodes --flamegraph script.py

명령어들¶

Tachyon은 여러 하위 명령어를 통해 작동합니다. run 과 attach 는 시간 경과에 따라 샘플을 수집하고, dump 는 단일 스냅샷을 캡처하며, replay 는 이진 프로파일을 다른 형식으로 변환합니다.

run 명령어¶

run 명령어는 Python 스크립트나 모듈을 실행하고 시작 시점부터 프로파일링합니다:

python -m profiling.sampling run script.py
python -m profiling.sampling run -m mypackage.module

When profiling a script, the profiler starts the target in a subprocess, waits for it to initialize, then begins collecting samples. The -m flag indicates that the target should be run as a module (equivalent to python -m). Arguments after the target are passed through to the profiled program:

python -m profiling.sampling run script.py --config settings.yaml

attach 명령어¶

The attach command connects to an already-running Python process by its process ID:

python -m profiling.sampling attach 12345

이 명령어는 프로덕션 시스템의 성능 문제를 조사하는 데 특히 유용합니다. 대상 프로세스는 수정할 필요가 없으며 재시작할 필요도 없습니다. 프로파일러가 첨부되어 지정된 시간 동안 샘플을 수집한 다음, 분리되고 출력을 생성합니다.

python -m profiling.sampling attach --live 12345
python -m profiling.sampling attach --flamegraph -d 30 -o profile.html 12345

On most systems, attaching to another process requires appropriate permissions. See 플랫폼 요구 사항 for platform-specific requirements.

dump 명령어¶

dump 명령어는 실행 중인 프로세스의 Python 스택의 단일 스냅샷을 출력한 후 종료하며, 이는 트레이스백과 유사합니다::`

python -m profiling.sampling dump 12345

attach 와 달리, dump 는 샘플링 루프를 실행하지 않습니다. 스택을 한 번 읽습니다. 이것은 일시 정지되었거나 응답하지 않는 프로세스를 조사하거나 “현재 이 프로세스는 무엇을 하고 있는가?”에 답하는 데 유용합니다.

출력은 트레이스백을 반영하며(가장 최근 호출이 마지막), 각 스레드의 현재 상태(메인 스레드, GIL 보유 여부, CPU에서 실행 중인지, GIL을 기다리는지, 예외가 있는지, 또는 유휴 상태)를 주석으로 달아 표시합니다:

Stack dump for PID 12345, thread 140735 (main thread, has GIL, on CPU; most recent call last):
  File "server.py", line 28, in serve
    await handle_request(req)
  File "handler.py", line 91, in handle_request
    result = expensive_call(req)

대상 소스 파일이 읽을 수 있는 경우, dump 는 각 프레임의 소스 라인을 출력하고 실행 중인 표현식을 강조 표시합니다.

attach 와 마찬가지로, dump 는 대상 프로세스의 메모리를 읽을 권한이 필요합니다. 프로파일링-권한 를 참조하십시오.

dump 명령어는 다음 옵션을 지원합니다:

-a, --all-threads

대상 프로세스의 모든 스레드를 덤프합니다. 이 플래그가 없으면 메인 스레드만 표시됩니다.

--native

C 확장이나 기타 비-Python 코드 진입을 표시하는 합성 <native> 프레임을 포함합니다.

--no-gc

활성 가비지 컬렉션을 표시하는 합성 <GC> 프레임을 숨깁니다.

--opcodes

각 프레임에 스레드가 현재 실행 중인 바이트코드 Opcode를 주석으로 추가합니다(예: opcode=CALL_KW). 적응형 인터프리터가 선택한 최적화까지 식별하는 등 명령 수준 조사를 위해 유용합니다.

--async-aware

await 경계를 넘어 스택을 재구성합니다. dump``는 작업 그래프를 탐색하고 각 작업에 대해 한 섹션을 전송하며, 코루틴이 서로 기다리고 있음을 표시하는 ``<task> 마커로 구분합니다.

--async-mode {running,all}

--async-aware 가 활성화될 때 포함되는 작업을 제어합니다. running 은 각 스레드에서 현재 실행 중인 작업만 보여줍니다. all (dump 의 기본값)은 대기 중인 작업도 포함합니다. 이 플래그에 대한 attach 의 기본값은 running 이고, dump 는 단일 스냅샷이 전체 작업 그래프를 보여줄 때 가장 유용하기 때문에 all 의 기본값을 사용합니다.

--blocking

대상 프로세스의 스택을 읽는 동안 모든 스레드를 일시 중지하고 나중에 재개합니다. 이는 대상이 순간적으로 멈추는 비용으로 완전히 일관된 스냅샷을 보장합니다. 이것 없이도 dump 는 대상이 계속 실행되는 동안 메모리를 읽기 때문에 빠르지만, 간혹 찢어진(torn) 스택을 생성할 수 있습니다.

replay 명령어¶

replay 명령어는 바이너리 프로파일 파일을 다른 출력 형식으로 변환합니다::`

python -m profiling.sampling replay profile.bin
python -m profiling.sampling replay --flamegraph -o profile.html profile.bin

이 명령어는 바이너리 형식으로 프로파일링 데이터를 캡처했고 나중에 분석하거나 시각화 형식으로 변환하려는 경우에 유용합니다. 바이너리 프로파일은 재프로파일링 없이 여러 다른 형식으로 다시 재생될 수 있습니다.

# 바이너리를 pstats로 변환 (기본값, stdout에 출력)
python -m profiling.sampling replay profile.bin

# 바이너리 파일을 플레임그래프로 변환
python -m profiling.sampling replay --flamegraph -o output.html profile.bin

# Firefox Profiler용 바이너리를 gecko 형식으로 변환
python -m profiling.sampling replay --gecko -o profile.json profile.bin

# 바이너리를 히트맵으로 변환
python -m profiling.sampling replay --heatmap -o my_heatmap profile.bin

프로덕션 환경에서의 프로파일링¶

샘플링 프로파일러는 프로덕션 사용을 위해 설계되었습니다. 코드를 계측하는 대신 메모리를 외부에서 읽기 때문에 대상 프로세스에 측정 가능한 오버헤드를 주지 않습니다. 대상 애플리케이션은 계속 최대 속도로 실행되며 프로파일링되고 있다는 사실을 알지 못합니다.

프로덕션 시스템을 프로파일링할 때는 다음 지침을 염두에 두십시오:

빠른 결과를 얻으려면 짧은 지속 시간(10-30초)으로 시작한 다음, 더 많은 통계적 정확도가 필요하면 확장하십시오. 기본적으로 프로파일링은 대상 프로세스가 완료될 때까지 실행되는데, 이는 일반적으로 주요 핫스팟을 식별하기에 충분합니다.

가능하다면 피크 트래픽보다는 대표적인 부하가 걸리는 동안 프로파일링을 수행하십시오. 정상 작동 중에 수집된 프로파일이 특이한 급증 시기에 수집된 것보다 해석하기 쉽습니다.

프로파일러 자체가 실행되는 장치(대상 프로세스가 아닌)의 일부 CPU를 소모합니다. 같은 장치 내에서는 보통 무시할 수 있는 수준입니다. 원격 프로세스를 프로파일링하는 경우, 네트워크 지연 시간은 대상에 영향을 주지 않습니다.

프로덕션 환경의 결과는 데이터 크기, 동시 부하 또는 캐싱 효과 등으로 인해 개발 환경과 다를 수 있습니다. 이는 예상되는 것이며 종종 정확히 포착하고 싶은 내용입니다.

플랫폼 요구 사항¶

프로파일러는 스택 추적을 캡처하기 위해 대상 프로세스의 메모리를 읽습니다. 이 기능은 대부분의 운영 체제에서 높은 권한이 필요합니다.

Linux

리눅스에서는 프로파일러가 대상 프로세스의 메모리를 읽기 위해 ptrace 또는 process_vm_readv 를 사용합니다. 일반적으로 다음 중 하나가 필요합니다:

  • root로 실행하기

  • CAP_SYS_PTRACE 권한 보유

  • Yama ptrace 범위 조정: /proc/sys/kernel/yama/ptrace_scope

기본 ptrace_scope가 1인 경우, ptrace는 부모 프로세스에만 제한됩니다. 동일한 사용자 소유의 모든 프로세스에 연결하는 것이 허용되도록 하려면 이를 0으로 설정하십시오:

echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope

macOS

macOS에서는 프로파일러가 대상 프로세스에 접근하기 위해 task_for_pid() 를 사용합니다. 다음 중 하나가 필요합니다:

  • root로 실행하기

  • 프로파일러 바이너리가 com.apple.security.cs.debugger 권한을 보유하는 것

  • System Integrity Protection (SIP) 비활성화 (권장되지 않음)

Windows

윈도우에서는 프로파일러가 다른 프로세스의 메모리를 읽기 위해 관리자 권한 또는 SeDebugPrivilege 권한이 필요합니다.

버전 호환성¶

프로파일러와 대상 프로세스는 동일한 Python 마이너 버전을 실행해야 합니다 (예: 둘 다 Python 3.15). Python 3.14에서 Python 3.15 프로세스로 연결하는 것은 지원되지 않습니다.

베타 또는 릴리스 후보와 같은 프리릴리즈 Python 버전에 대해서는 추가 제한 사항이 있습니다: 프로파일러나 대상 중 하나라도 프리릴리즈 버전인 경우, 둘 다 정확히 동일한 버전을 실행해야 합니다.

자유 스레딩 Python 빌드에서는 프로파일러가 자유 스레딩 빌드에서 표준 빌드로, 또는 그 반대로 연결할 수 없습니다.

샘플링 구성¶

다양한 출력 형식과 시각화 옵션을 탐색하기 전에, 샘플링 프로세스 자체를 구성하는 방법을 이해하는 것이 중요합니다. 프로파일러는 여러 옵션을 제공하며, 이들은 샘플을 얼마나 자주 수집할지, 프로파일링이 얼마나 오래 실행될지, 어떤 스레드가 관찰되는지, 그리고 각 샘플에 어떤 추가 컨텍스트가 캡처되는지를 제어합니다.

기본 구성은 대부분의 사용 사례에 적합합니다:

샘플링 전율 및 지속 시간¶

가장 기본적인 두 가지 매개변수는 샘플링 전율과 지속 시간이 있습니다. 이 둘은 프로파일링 세션 동안 수집되는 샘플 수를 결정합니다.

--sampling-rate 옵션 (-r)은 샘플이 얼마나 자주 수집되는지를 설정합니다. 기본값은 1 kHz (초당 1,000개의 샘플)입니다:

python -m profiling.sampling run -r 20khz script.py

더 높은 전율은 더 많은 샘플을 캡처하고 약간 더 높은 프로파일러 CPU 사용량의 대가로 더 정밀한 데이터를 제공합니다. 더 낮은 전율은 프로파일러 오버헤드를 줄이지만 짧게 사는 함수를 놓칠 수 있습니다. 대부분의 응용 프로그램에 대해, 기본 전율이 정확성과 오버헤드 사이 좋은 균형을 제공합니다.

--duration 옵션 (-d)은 프로파일링할 시간을 초 단위로 설정합니다. 기본적으로, 프로파일링은 대상 프로세스가 종료되거나 중단될 때까지 계속됩니다:

`python -m profiling.sampling run -d 60 script.py`

기간을 지정하는 것은 장시간 실행되는 프로세스에 첨부하거나 특정 시간 범위로 프로파일링을 제한하려는 경우 유용합니다. 스크립트를 프로파일링할 때, 기본 동작인 완료까지 실행하는 것이 일반적으로 원하는 것입니다.

쓰레드 선택¶

파이썬 프로그램은 threading 모듈을 통해 명시적으로 또는 스레드 풀을 관리하는 라이브러리를 통해 암묵적으로 여러 개의 쓰레드를 사용할 때가 많습니다.

기본적으로, 프로파일러는 메인 쓰레드의 샘플링만 수행합니다. --all-threads 옵션 (-a)은 프로세스의 모든 쓰레드에 대한 샘플링을 활성화합니다:

`python -m profiling.sampling run -a script.py`

다중 쓰레드 프로파일링은 작업이 쓰레드에 걸쳐 어떻게 분산되는지 보여주며, 블록 또는 기아 상태인 쓰레드를 식별할 수 있습니다. 각 쓰레드의 샘플은 출력에 결합되며, 일부 형식에서는 쓰레드로 필터링하는 기능도 제공됩니다. 이 옵션은 동시성 문제를 조사하거나 작업이 스레드 풀에 걸쳐 분산되는 경우 특히 유용합니다.

블로킹 모드¶

기본적으로 Tachyon은 대상 프로세스를 중단하지 않고 메모리를 읽습니다. 이 비차단 방식은 프로파일링 시나리오 대부분에 이상적입니다. 왜냐하면 대상 애플리케이션에 사실상 제로 오버헤드를 부과하기 때문입니다. 즉, 프로파일링된 프로그램은 최대 속도로 실행되며 관찰되고 있다는 사실을 모릅니다.

그러나 비차단 샘플링은 생성기 또는 코루틴이 많은 애플리케이션에서(여기서 yield 지점 사이를 빠르게 전환하는 경우) 또는 함수가 단일 스택 읽기의 시작과 끝 사이에 진입하고 종료되는 매우 빠르게 변화하는 호출 스택을 가진 프로그램에서 간헐적으로 불완전하거나 일관성 없는 스택 추적을 생성할 수 있습니다. 그 결과, 서로 다른 실행 상태의 프레임이 섞였거나 실제로 존재하지 않은 재구성된 스택이 생길 수 있습니다.

이러한 경우, --blocking 옵션은 각 샘플 동안 대상 프로세스를 중단합니다:

python -m profiling.sampling run --blocking script.py
python -m profiling.sampling attach --blocking 12345

블로킹 모드가 활성화되면 프로파일러는 대상 프로세스를 일시 중지하고, 스택을 읽은 다음 재개합니다. 이를 통해 캡처된 각 스택이 해당 순간에 프로세스가 수행하던 실제적이고 일관된 스냅샷을 나타냄이 보장됩니다. 단점은 대상 프로세스가 반복적으로 일시 정지되기 때문에 더 느리게 실행된다는 것입니다.

경고

매우 높은 샘플링 속도(낮은 --interval 값)를 블로킹 모드와 함께 사용하지 마십시오. 프로세스를 일시 중지하고 다시 시작하는 데 시간이 걸리므로, 샘플링 간격이 너무 짧으면 대상에서 실행하는 시간보다 멈춰 있는 시간이 더 많아집니다. 블로킹 모드의 경우 1000 마이크로초(1밀리초) 이상의 간격이 권장됩니다. 기본 100 마이크로초 간격은 대상 애플리케이션에 눈에 띄는 속도 저하를 유발할 수 있습니다.

블로킹 모드는 프로필에서 일관성 없는 스택을 관찰하는 경우, 특히 생성기가 많거나 코루틴이 많은 코드에 대해서만 사용하십시오. 대부분의 애플리케이션의 경우 기본 비차단 모드가 대상 프로세스에 영향을 주지 않으면서 정확한 결과를 제공합니다.

특수 프레임¶

프로파일러는 캡처된 스택에 인공적인 프레임을 주입하여 각 샘플이 촬영되는 순간 인터프리터가 무엇을 하고 있는지에 대한 추가 컨텍스트를 제공할 수 있습니다. 이러한 합성 프레임은 달리 보이지 않을 종류의 다양한 실행을 구분하는 데 도움을 줍니다.

--native 옵션은 파이썬이 C 코드(확장 모듈, 내장 함수 또는 인터프리터 자체)를 호출했을 때를 나타내는 <native> 프레임을 추가합니다:

`python -m profiling.sampling run --native script.py`

이러한 프레임은 파이썬 코드에서 소비된 시간과 네이티브 라이브러리에서 소비된 시간을 구별하는 데 도움이 됩니다. 이 옵션이 없으면, 네이티브 코드 실행은 호출을 수행한 파이썬 함수 내의 시간으로 나타납니다. 이는 NumPy와 같은 C 확장 모듈 또는 데이터베이스 드라이버를 많이 사용하는 코드를 최적화할 때 유용합니다.

기본적으로, 프로파일러는 가비지 컬렉션이 활성화될 때 <GC> 프레임을 포함합니다. --no-gc 옵션은 이러한 프레임을 억제합니다:

`python -m profiling.sampling run --no-gc script.py`

GC 프레임은 가비지 컬렉션이 상당한 시간을 소비하는 프로그램을 식별하는 데 도움이 되며, 이는 최적화할 만한 메모리 할당 패턴을 나타낼 수 있습니다. <GC> 프레임에서 상당한 시간이 발견되면 객체 할당률을 조사하거나 객체 풀링을 사용하는 것을 고려하십시오.

오피코드 기반 프로파일링¶

--opcodes 옵션은 각 샘플에서 실행 중인 파이썬 바이트코드 명령어를 캡처하는 명령어 수준 프로파일링을 활성화합니다:

python -m profiling.sampling run --opcodes --flamegraph script.py

This feature provides visibility into Python’s bytecode execution, including adaptive specialization optimizations. When a generic instruction like LOAD_ATTR is specialized at runtime into a more efficient variant like LOAD_ATTR_INSTANCE_VALUE, the profiler shows both the specialized name and the base instruction.

오피코드 정보는 여러 출력 형식에서 나타납니다:

  • Flame graphs: 프레임 위로 마우스를 가져가면 해당 함수에서 어느 오피코드가 시간을 소비했는지 보여주는 바이트코드 명령어 분석 툴팁이 표시됩니다.

  • Heatmap: 소스 코드 라인별 확장 가능한 바이트코드 패널은 특수화 백분율과 함께 명령어 분석을 보여줍니다.

  • Live mode: 오피코드 패널은 선택된 함수에 대한 명령어 수준 통계를 보여주며, 키보드 탐색을 통해 접근할 수 있습니다.

  • Gecko format: 오피코드 전환은 파이어폭스 프로파일러 타임라인에서 간격 마커로 방출됩니다.

이 수준의 세부 정보는 다음 용도에 특히 유용합니다:

  • 파이썬의 적응형 특수화가 성능에 미치는 영향을 이해하는 것

  • 최적화로 이점을 얻을 수 있는 뜨거운 바이트코드 명령어를 식별하는 것

  • 명령어 수준에서 다양한 코드 패턴의 효과를 분석하는 것

  • 바이트코드 레벨에서 발생하는 성능 문제를 디버깅하는 것

--opcodes 옵션은 --live, --flamegraph, --heatmap, 및 --gecko 형식과 호환됩니다. 오피코드 정보를 저장하기 위해 추가 메모리가 필요할 수 있으며 샘플링 성능을 약간 저하시킬 수 있지만, 파이썬 실행 모델에 대한 전례 없는 가시성을 제공합니다.

자식 프로세스 프로파일링¶

--subprocesses 옵션은 대상 프로세스가 생성한 자식 프로세스의 자동 프로파일링을 활성화합니다:

python -m profiling.sampling run --subprocesses script.py
python -m profiling.sampling attach --subprocesses 12345

When enabled, the profiler monitors the target process for child process creation. When a new Python child process is detected, a separate profiler instance is automatically spawned to profile it. This is useful for applications that use multiprocessing, subprocess, concurrent.futures with ProcessPoolExecutor, or other process spawning mechanisms.

worker_pool.py¶
from concurrent.futures import ProcessPoolExecutor
import math

def compute_factorial(n):
    total = 0
    for i in range(50):
        total += math.factorial(n)
    return total

if __name__ == "__main__":
    numbers = [5000 + i * 100 for i in range(50)]
    with ProcessPoolExecutor(max_workers=4) as executor:
        results = list(executor.map(compute_factorial, numbers))
    print(f"Computed {len(results)} factorials")

python -m profiling.sampling run --subprocesses --flamegraph worker_pool.py

이 명령어는 메인 프로세스와 각 워커 프로세스에 대한 별도의 플레임 그래프를 생성합니다: flamegraph_<main_pid>.html, flamegraph_<worker1_pid>.html 등입니다.

각 자식 프로세스는 자체 출력 파일을 받습니다. 파일 이름은 지정된 출력 경로(또는 기본값)에 자식 프로세스의 프로세스 ID가 추가되어 파생됩니다:

  • –o profile.html`을 지정하면, 자식 프로세스는 `profile_12345.html, profile_12346.html 등과 같은 파일을 생성합니다.

  • With default output, subprocesses produce files like flamegraph_12345.html or directories like heatmap_12345

  • For pstats format (which defaults to stdout), subprocesses produce files like profile_12345.pstats

자식 프로세스 프로파일러는 부모로부터 대부분의 샘플링 옵션을 상속받습니다(샘플링 속도, 지속 시간, 스레드 선택, 네이티브 프레임, GC 프레임, 비동기 인식 모드 및 출력 형식). 모든 파이썬 후손 프로세스는 손주와 그 이하의 모든 후손을 포함하여 재귀적으로 프로파일링됩니다.

자식 프로세스 감지는 대상 프로세스의 새 후손을 주기적으로 스캔하고, 프로세스 메모리를 파이썬 런타임 구조체에 대한 탐색을 통해 각 새 프로세스가 파이썬 프로세스인지 확인하여 작동합니다. 비파이썬 자식 프로세스(쉘 명령어 또는 외부 도구 등)는 무시됩니다.

많은 프로세스를 생성하는 프로그램에서 리소스 고갈을 방지하기 위해 동시 서브프로세스 프로파일러의 최대 개수가 100개로 제한됩니다. 이 한계에 도달하면 추가 서브프로세스는 프로파일링되지 않으며 경고가 출력됩니다.

--subprocesses 옵션은 --live 모드와 호환되지 않습니다. 라이브 모드는 다수의 동시 프로파일러 표시를 수용할 수 없는 대화형 터미널 인터페이스를 사용하기 때문입니다.

Sampling efficiency metrics help assess the quality of the collected data. These metrics appear in the profiler’s terminal output and in the flame graph sidebar.

Sampling efficiency is the percentage of sample attempts that succeeded. Each sample attempt reads the target process’s call stack from memory. An attempt can fail if the process is in an inconsistent state at the moment of reading, such as during a context switch or while the interpreter is updating its internal structures. A low efficiency may indicate that the profiler could not keep up with the requested sampling rate, often due to system load or an overly aggressive interval setting.

Missed samples is the percentage of expected samples that were not collected. Based on the configured interval and duration, the profiler expects to collect a certain number of samples. Some samples may be missed if the profiler falls behind schedule, for example when the system is under heavy load. A small percentage of missed samples is normal and does not significantly affect the statistical accuracy of the profile.

Both metrics are informational. Even with some failed attempts or missed samples, the profile remains statistically valid as long as enough samples were collected. The profiler reports the actual number of samples captured, which you can use to judge whether the data is sufficient for your analysis.

Wall-clock mode (--mode=wall) captures all samples regardless of what the thread is doing. This is the default mode and provides a complete picture of where time passes during program execution:

===
python -m profiling.sampling run --mode=wall script.py

In wall-clock mode, samples are recorded whether the thread is actively executing Python code, waiting for I/O, blocked on a lock, or sleeping. This makes wall-clock profiling ideal for understanding the overall time distribution in your program, including time spent waiting.

If your program spends significant time in I/O operations, network calls, or sleep, wall-clock mode will show these waits as time attributed to the calling function. This is often exactly what you want when optimizing end-to-end latency.

CPU mode (--mode=cpu) records samples only when the thread is actually executing on a CPU core:

===
python -m profiling.sampling run --mode=cpu script.py

Samples taken while the thread is sleeping, blocked on I/O, or waiting for a lock are discarded. The resulting profile shows where CPU cycles are consumed, filtering out idle time.

CPU mode is useful when you want to focus on computational hotspots without being distracted by I/O waits. If your program alternates between computation and network calls, CPU mode reveals which computational sections are most expensive.

Running both wall-clock and CPU mode profiles can reveal whether a function’s time is spent computing or waiting.

If a function appears prominently in both profiles, it is a true computational hotspot—actively using the CPU. Optimization should focus on algorithmic improvements or more efficient code.

If a function is high in wall-clock mode but low or absent in CPU mode, it is I/O-bound or waiting. The function spends most of its time waiting for network, disk, locks, or sleep. CPU optimization won’t help here; consider async I/O, connection pooling, or reducing wait time instead.

GIL 모드¶

GIL 모드 (--mode=gil)는 스레드가 Python의 전역 해석기 잠금(global interpreter lock)을 보유할 때만 샘플을 기록합니다:

python -m profiling.sampling run --mode=gil script.py

GIL은 Python 바이트코드를 실행하는 동안에만 보유됩니다. Python이 C 확장으로 호출하거나, I/O 작업을 수행하거나, 네이티브 코드를 실행할 때에는 일반적으로 GIL이 해제됩니다. 이는 GIL 모드가 순수하게 Python 코드 실행에 소요된 시간을 측정하고 네이티브 라이브러리의 시간은 걸러냄을 의미합니다.

다중 스레드 프로그램에서, GIL 모드는 어떤 코드가 다른 스레드가 Python 바이트코드를 실행하지 못하게 방해하는지 밝혀줍니다. 오직 하나의 스레드만이 한 번에 GIL을 보유할 수 있으므로, GIL 모드 프로필에서 자주 나타나는 함수들은 인터프리터를 독점하고 있음을 의미합니다.

GIL 모드는 “어떤 함수들이 GIL을 독점하는가?” 또는 “다른 스레드가 왜 기아 상태에 빠지는가?”와 같은 질문에 답하는 데 도움을 줍니다. 또한, 단일 스레드 프로그램에서도 Python 실행 시간과 C 확장이나 I/O에 소요된 시간을 구별하는 데 유용할 수 있습니다.

import hashlib

def hash\_work():
    # C 확장이므로 계산 중에 GIL을 해제합니다
    for \_ in range(200):
        hashlib.sha256(b"data" * 250000).hexdigest()

def python\_work():
    # 순수 Python이므로 계산 중에 GIL을 보유합니다
    for \_ in range(3):
        sum(i**2 for i in range(1000000))

if __name__ == "__main__":
    hash\_work()
    python\_work()

python -m profiling.sampling run --mode=cpu script.py  # hash\_work ~42%, python\_work ~38%
python -m profiling.sampling run --mode=gil script.py  # hash\_work ~5%, python\_work ~60%

예외 모드¶

예외 모드 (--mode=exception)는 스레드가 활성 예외를 가지고 있을 때만 샘플을 기록합니다:

python -m profiling.sampling run --mode=exception script.py

샘플은 두 가지 상황에서 기록됩니다: 예외가 호출 스택을 따라 전파될 때(raise 이후, 잡히기 이전), 또는 코드가 예외 정보가 여전히 스레드 상태에 존재하는 except 블록 내부에서 실행되는 경우입니다.

다음 예제는 어떤 코드 영역이 캡처되는지 보여줍니다:

def example():
    try:
        raise ValueError("error")    # 캡처됨: 발생 중인 예외
    except ValueError:
        process\_error()              # 캡처됨: except 블록 내부
    finally:
        cleanup()                    # 캡처되지 않음: 이미 예외가 처리됨

def example\_propagating():
    try:
        try:
            raise ValueError("error")
        finally:
            cleanup()                # 캡처됨: 전파되는 예외를 통과함
    except ValueError:
        pass

def example\_no\_exception():
    try:
        do\_work()
    finally:
        cleanup()                    # 캡처되지 않음: 예외가 관여하지 않음

finally 블록은 예외가 활발하게 전파되는 경우에만 캡처된다는 점에 유의하십시오. except 블록이 실행을 완료하면, Python은 후속 finally 블록을 실행하기 전에 예외 정보를 지웁니다. 유사하게, 정상 실행(예외가 발생하지 않은 경우) 중에 실행되는 finally 블록은 예외 상태가 존재하지 않기 때문에 캡처되지 않습니다.

이 모드는 프로그램이 오류를 처리하는 데 시간을 어디에 쓰는지 이해하는 데 유용합니다. 예외 처리는 흐름 제어를 위해 예외를 사용하는 코드(예: 이터레이터의 StopIteration)나 많은 오류 조건을 처리하는 애플리케이션(예: 연결 실패를 처리하는 네트워크 서버)에서 상당한 오버헤드를 발생시킬 수 있는 원인이 됩니다.

예외 모드는 “예외 처리에 얼마나 많은 시간이 소요되는가?” 또는 “어떤 예외 핸들러가 가장 비용이 많이 드는가?”와 같은 질문에 답하는 데 도움을 줍니다. 이 모드는 해당 예외를 처리하더라도, 코드가 많은 예외를 잡고 처리할 때 숨겨진 성능 비용을 드러낼 수 있습니다. 예를 들어, 파싱 라이브러리가 형식 오류 신호를 위해 내부적으로 예외를 사용한다면, 호출 코드가 예외를 결코 보지 못하더라도 해당 핸들러에서 소요된 시간을 이 모드는 캡처합니다.

출력 형식¶

프로파일러는 다양한 형식으로 출력을 생성하며, 각 형식은 다른 분석 워크플로에 적합합니다. 형식은 명령줄 플래그로 선택되며, 출력은 형식에 따라 stdout, 파일 또는 디렉터리로 전송됩니다.

pstats 형식¶

pstats 형식 (--pstats)은 결정론적 프로파일러가 생성하는 것과 유사한 텍스트 테이블을 생성합니다. 이것이 기본 출력 형식입니다:

python -m profiling.sampling run script.py
python -m profiling.sampling run --pstats script.py

기본적으로 stdout에 출력이 나타납니다:

Profile Stats (Mode: wall):
     nsamples  sample%    tottime (ms)  cumul%   cumtime (ms)  filename:lineno(function)
       234/892    11.7%       234.00     44.6%       892.00    server.py:145(handle_request)
       156/156     7.8%       156.00      7.8%       156.00    <built-in>:0(socket.recv)
        98/421     4.9%        98.00     21.1%       421.00    parser.py:67(parse_message)

열들은 샘플 수와 추정 시간을 보여줍니다:

  • nsamples: direct/cumulative 로 표시됩니다 (예: 10/50). 직접(Direct) 샘플은 함수가 스택의 최상단에 활발하게 실행된 경우를 나타냅니다. 누적(Cumulative) 샘플은 함수가 호출한 함수를 기다리는 경우를 포함하여 모든 위치에서 스택에 나타난 경우입니다. 함수가 10/50 을 보여주면, 10개의 샘플 동안 직접 실행되었고 전체 호출 스택에서는 총 50개 샘플에 걸쳐 존재했음을 의미합니다.

  • sample% 및 cumul%: 각각 직접 및 누적 카운트에 대한 전체 샘플 비율입니다.

  • tottime 및 cumtime: 샘플 수와 프로파일링 기간을 기반으로 추정한 벽시계 시간입니다. 시간 단위는 크기에 따라 자동으로 선택됩니다: 큰 값에는 초, 적당한 값에는 밀리초, 작은 값에는 마이크로초가 사용됩니다.

출력은 각 열을 설명하는 범례와 다음 사항이 강조 표시된 흥미로운 함수들의 요약 정보를 포함합니다:

  • 핫스팟(Hot spots): 높은 직접/누적 샘플 비율(1.0에 가까운 비율)을 가진 함수입니다. 이러한 함수들은 호출된 함수를 기다리기보다 자체 코드를 실행하는 데 대부분의 시간을 사용합니다. 높은 비율은 실제로 CPU 시간이 소비되는 곳을 나타냅니다.

  • 간접 호출(Indirect calls): 누적 샘플과 직접 샘플 사이에 큰 차이가 있는 함수입니다. 이들은 다른 함수에 작업을 위임하는 오케스트레이션 함수입니다. 스택에는 자주 나타나지만 최상단에서는 거의 나타나지 않습니다.

  • 호출 확대(Call magnification): 누적 샘플이 직접 샘플을 훨씬 초과하는 함수입니다 (높은 누적/직접 승수). 이들은 많은 호출 체인의 깊은 곳에 나타나는 빈번하게 중첩된 함수입니다.

Use --no-summary to suppress both the legend and summary sections.

pstats 출력을 stdout 대신 바이너리 파일로 저장하려면:

python -m profiling.sampling run -o profile.pstats script.py

pstats 형식은 표시를 제어하기 위한 여러 옵션을 지원합니다. --sort 옵션은 결과 정렬에 사용되는 열을 결정합니다:

python -m profiling.sampling run --sort=tottime script.py
python -m profiling.sampling run --sort=cumtime script.py
python -m profiling.sampling run --sort=nsamples script.py

--limit 옵션으로 출력을 상위 N개 항목으로 제한할 수 있습니다:

python -m profiling.sampling run --limit=30 script.py

--no-summary 옵션은 통계 테이블 앞에 위치하는 헤더 요약 정보를 억제합니다.

축소된 스택 형식¶

축소된 스택 형식 (--collapsed)은 고유한 호출 스택마다 한 줄을 생성하며, 해당 스택이 샘플링된 횟수를 포함합니다:

python -m profiling.sampling run --collapsed script.py

출력은 다음과 같습니다:

main;process_data;parse_json;decode_utf8 42
main;process_data;parse_json 156
main;handle_request;send_response 89

각 줄에는 밑에서 위로의 호출 스택을 나타내는 세미콜론으로 구분된 함수 이름이 따르고, 그 뒤에 공백과 샘플 수가 붙어 있습니다. 이 형식은 특히 Brendan Gregg의 flamegraph.pl 스크립트를 포함한 외부 플레임 그래프 도구와의 호환성을 위해 설계되었습니다.

축소된 스택에서 플레임 그래프를 생성하려면:

python -m profiling.sampling run --collapsed script.py > stacks.txt
flamegraph.pl stacks.txt > profile.svg

결과 SVG는 모든 웹 브라우저에서 볼 수 있으며, 클릭하여 특정 호출 경로를 확대할 수 있는 대화형 시각화를 제공합니다.

플레임 그래프 형식¶

플레임 그래프 형식 (--flamegraph)은 대화형 플레임 그래프 시각화를 포함하는 자체 포함 HTML 파일을 생성합니다:

python -m profiling.sampling run --flamegraph script.py
python -m profiling.sampling run --flamegraph -o profile.html script.py

대화형 예제! 를 사용해 보세요:

출력 파일을 지정하지 않으면, 프로파일러는 프로세스 ID를 기반으로 파일 이름을 생성합니다 (예: flamegraph.12345.html).

생성된 HTML 파일은 외부 종속성이 필요하지 않아 웹 브라우저에서 바로 열 수 있습니다. 시각화는 호출 스택을 중첩된 사각형으로 표시하며, 너비는 소요 시간에 비례합니다. 직사각형 위에 마우스를 올리면 해당 함수의 소스 코드 컨텍스트를 포함한 세부 정보가 표시되며, 클릭하면 호출 트리에서 해당 부분으로 확대됩니다.

플레임 그래프 인터페이스에는 다음 내용이 포함되어 있습니다:

  • A sidebar showing profile summary, thread statistics, sampling efficiency metrics (see Possible incomplete section title. Treating the overline as ordinary text because it’s so short.), and top hotspot functions

  • 함수 이름 일치와 file.py:42 라인 패턴 모두를 지원하는 검색 기능입니다.

  • 드롭다운 메뉴를 통한 스레드별 필터링입니다.

  • 다크/라이트 테마 토글 (세션 간 환경 설정 저장)

  • 현재 뷰를 저장하기 위한 SVG 내보내기 기능입니다.

스레드 통계 섹션은 다음과 같은 런타임 동작 메트릭을 보여줍니다:

  • GIL 보유: 스레드가 전역 인터프리터 잠금(실제 파이썬 코드를 실행하는 경우)을 보유한 샘플의 백분율

  • GIL 방출: 어떤 스레드도 GIL을 보유하지 않은 샘플의 백분율

  • 대기 중인 GIL: 스레드가 GIL 획득을 기다리고 있던 샘플의 백분율

  • GC: 가비지 컬렉션 중인 샘플의 백분율

이러한 통계는 GIL 경쟁을 식별하고 파이썬 실행, 네이티브 코드 및 대기 사이에서 시간이 어떻게 분산되는지 이해하는 데 도움이 됩니다.

플레임 그래프는 깊은 호출 스택을 확인하고 시간 소비의 계층적 구조를 파악하는 데 특히 효과적입니다. 상단에 넓은 사각형은 직접적으로 또는 하위 함수를 통해 상당한 시간을 소비하는 함수를 나타냅니다.

차분 플레임 그래프¶

차분 플레임 그래프는 두 개의 프로파일 실행을 비교하여 성능이 변경된 부분을 강조합니다. 이를 통해 코드 변경으로 인해 발생한 회귀를 식별하고 최적화가 의도한 효과를 달성했는지 검증하는 데 도움이 됩니다:

# 기준선 프로파일 캡처
python -m profiling.sampling run --binary -o baseline.bin script.py

# 코드 수정 후, 차분 플레임 그래프 생성
python -m profiling.sampling run --diff-flamegraph baseline.bin -o diff.html script.py

시각화는 현재 시간 소비를 보여주는 프레임 너비로 현재 프로파일을 그린 다음, 각 함수가 기준선 대비 어떻게 변경되었는지 표시하기 위해 색상을 적용합니다.

색상 코딩:

  • 빨간색: 시간이 더 많이 소요되는 함수 (회귀). 옅은 색상은 적당한 증가를 나타내고, 어두운 색상은 심각한 회귀를 보여줍니다.

  • 파란색: 시간이 더 적게 소요되는 함수 (개선). 옅은 색상은 적당한 감소를, 어두운 색상은 상당한 속도 향상을 보여줍니다.

  • 회색: 변화가 미미하거나 없는 경우입니다.

  • 보라색: 기준선에 존재하지 않는 새로운 함수를 의미합니다.

프레임 색상은 직접 시간 (함수가 스택의 최상단에 있었고 활발하게 실행되던 시간)의 변화를 나타내며, 하위 함수가 포함된 누적 시간을 의미하지 않습니다. 프레임 위에 마우스를 올리면 기준선 시간, 현재 시간 및 백분율 변화를 포함한 비교 세부 정보가 표시됩니다.

일부 호출 경로는 프로파일 간에 완전히 사라질 수 있습니다. 이를 생략된 스택 이라고 하며, 최적화가 코드 경로를 제거하거나 특정 분기가 실행을 중지할 때 발생합니다. 생략된 스택이 존재하는 경우, 주 차분 뷰와 사라진 경로만 보여주는 생략 전용 뷰 간에 전환할 수 있는 ‘생략’ 토글이 나타납니다 (보라색으로 표시).

Gecko 형식¶

Gecko 형식 (--gecko)은 Firefox Profiler와 호환되는 JSON 출력을 생성합니다:

python -m profiling.sampling run --gecko script.py
python -m profiling.sampling run --gecko -o profile.json script.py

The Firefox Profiler is a sophisticated web-based tool originally built for profiling Firefox itself. It provides features beyond basic flame graphs, including a timeline view, call tree exploration, and marker visualization. See the Firefox Profiler documentation for detailed usage instructions.

출력을 사용하려면 브라우저에서 Firefox Profiler를 열고 JSON 파일을 로드하세요. 프로파일러는 전적으로 클라이언트 측에서 실행되므로, 프로파일링 데이터가 절대 기기를 벗어나지 않습니다.

Gecko 형식은 GIL 상태 및 CPU 활동에 대한 추가 메타데이터를 자동으로 수집하여 파이썬의 스레딩 모델에 특화된 분석 기능을 가능하게 합니다. 프로파일러는 Firefox 프로파일러 타임라인에서 색상 밴드로 나타나는 인터벌 마커를 방출합니다:

  • GIL 마커: 스레드가 전역 인터프리터 록을 보유하거나 해제하는 시점을 표시합니다.

  • CPU 마커: 스레드가 CPU에서 실행 중인지 유휴 상태인지 표시합니다.

  • 코드 유형 마커: 파이썬 코드와 네이티브 (C 확장) 코드를 구분합니다.

  • GC 마커: 가비지 컬렉션 활동을 나타냅니다.

이러한 이유로, --mode 옵션은 Gecko 형식에서 사용 가능하지 않으며 모든 관련 데이터는 자동으로 수집됩니다.

히트맵 형식¶

히트맵 형식 (--heatmap)은 소스 코드 라인 수준에서 샘플 개수를 보여주는 대화형 HTML 시각화를 생성합니다.

python -m profiling.sampling run --heatmap script.py
python -m profiling.sampling run --heatmap -o my_heatmap script.py

다른 형식들은 단일 파일을 생성하는 것과 달리, 히트맵 출력은 각 프로파일링된 소스 파일에 대한 HTML 파일을 포함하는 디렉터리를 생성합니다. 출력 경로를 지정하지 않으면 이 디렉터리는 heatmap_PID 라는 이름을 갖습니다.

히트맵 시각화는 각 라인에서 수집된 샘플이 얼마나 많은지를 나타내는 색상 그라디언티와 함께 소스 코드를 표시합니다. 뜨거운 라인은 (샘플이 많으면) 따뜻한 색으로, 차가운 라인은 (샘플이 적거나 없으면) 차가운 색으로 표시됩니다. 이 뷰는 시간 소비의 책임 있는 코드 라인을 정확하게 찾아내는 데 도움이 됩니다.

히트맵 인터페이스는 여러 가지 대화형 기능을 제공합니다:

  • 색상 지정 모드: “자체 시간” (직접 실행)과 “총 시간” (호출된 함수의 시간을 포함하여 누적) 간에 전환합니다.

  • 저온 코드 필터링: 모든 라인을 표시하거나 샘플이 있는 라인만 표시합니다.

  • 호출 그래프 탐색: 각 라인은 (▲는 호출자, ▼는 피호출자를 나타내는) 탐색 버튼을 보여주어 코드의 실행 경로를 추적할 수 있도록 합니다. 한 라인에서 여러 함수가 호출되었거나 호출된 경우, 모든 옵션과 해당 샘플 개수를 보여주는 메뉴가 표시됩니다.

  • 스크롤 미니맵: 파일 전체에 걸친 열 분포를 보여주는 수직 개요입니다.

  • 계층적 인덱스: 유형별 (stdlib, site-packages, project)로 정리된 파일과 폴더당 집계 샘플 개수를 보여줍니다.

  • 다크/라이트 테마: 세션 전반에 걸쳐 선호도를 토글합니다.

  • 라인 링크: 라인 번호를 클릭하여 공유 가능한 URL을 생성합니다.

When opcode-level profiling is enabled with --opcodes, each hot line can be expanded to show which bytecode instructions consumed time:

상호작용 예제 <../_static/tachyon-example-heatmap.html>을 사용해 보세요!

히트맵은 성능 문제가 있는 파일을 알고 있지만 구체적인 라인을 식별해야 할 때 특히 유용합니다. 개발자들은 히트맵이 소스 코드에 직접 매핑되어 읽고 탐색하기 쉬우기 때문에 이 형식을 선호하는 경우가 많습니다. 더 작거나 집중적인 분석의 경우, 계층적 시각화 해석을 요구하지 않고 시간이 정확히 어디에 쓰이는지를 보여주는 직관적인 뷰를 제공합니다.

바이너리 형식¶

바이너리 형식 (--binary)은 프로파일링 데이터의 효율적인 저장을 위해 압축된 바이너리 파일을 생성합니다:

python -m profiling.sampling run --binary -o profile.bin script.py
python -m profiling.sampling attach --binary -o profile.bin 12345

--compression 옵션은 데이터 압축을 제어합니다:

  • auto (default): Use zstd compression if available, otherwise no compression

  • zstd: Zstd 압축을 강제합니다 ( compression.zstd 지원 필요)

  • none: 압축 비활성화

python -m profiling.sampling run --binary --compression=zstd -o profile.bin script.py

To analyze binary profiles, use the replay 명령어 to convert them to other formats like flame graphs or pstats output.

기록 및 재생 워크플로우¶

바이너리 형식과 리플레이 명령을 결합하면 데이터 캡처와 분석을 분리하는 기록-및-재생(record-and-replay) 워크플로우를 사용할 수 있습니다. 프로파일링 중에 시각화를 생성하기보다는, 원시 데이터를 압축된 바이너리 파일로 캡처한 다음 나중에 다른 형식으로 변환합니다.

이 접근 방식은 세 가지 주요 이점이 있습니다:

  • 샘플링은 시각화를 위한 데이터 구조를 구축하는 작업이 리플레이 시점까지 연기되므로 더 빠르게 작동합니다.

  • 단일 바이너리 캡처는 다시 프로파일링할 필요 없이 여러 출력 형식으로 변환될 수 있습니다: 간편한 개요를 위한 pstats, 시각적 탐색을 위한 flame 그래프, 라인 레벨 세부 정보를 위한 히트맵.

  • 바이너리 파일은 작고 동료들과 쉽게 공유하여 선호하는 형식으로 변환할 수 있습니다.

일반적인 워크플로우:

# 운영 환경이나 테스트 중에 프로파일 캡처
python -m profiling.sampling attach --binary -o profile.bin 12345

# 나중에 다른 형식으로 분석합니다
python -m profiling.sampling replay profile.bin
python -m profiling.sampling replay --flamegraph -o profile.html profile.bin
python -m profiling.sampling replay --heatmap -o heatmap profile.bin

실시간 모드¶

실시간 모드 (--live)는 시스템 프로세스의 top 명령어와 유사하게 터미널 기반의 프로파일링 데이터 실시간 보기를 제공합니다:

python -m profiling.sampling run --live script.py
python -m profiling.sampling attach --live 12345

실시간 모드는 여러 스레드가 있는 애플리케이션에서 다양한 스레드의 결합된 데이터와 실시간 프로파일링 통계를 표시합니다.

샘플이 도착함에 따라 표시가 지속적으로 업데이트되며, 현재 가장 활발한 함수를 보여줍니다. 이 모드에는 유닉스 계열 시스템에서 사용할 수 있지만 윈도우에서는 사용할 수 없는 curses 모듈이 필요합니다. 터미널은 최소 60열 너비와 12줄 높이가 되어야 하며, 더 큰 터미널은 더 많은 열을 표시합니다.

헤더에는 상위 3개 가장 활발한 함수, 샘플링 효율성 지표 및 스레드 상태 통계(GIL 점유 비율, CPU 사용량, GC 시간)가 표시됩니다. 메인 테이블은 현재 정렬된 열에 의해 화살표(▼)로 표시되는 함수의 통계를 보여줍니다.

When --opcodes is enabled, an additional opcode panel appears below the main table, showing instruction-level statistics for the currently selected function. This panel displays which bytecode instructions are executing most frequently, including specialized variants and their base opcodes.

실시간 모드에서 --opcodes 를 활성화하면 선택된 함수에 대한 바이트코드 명령어 분석을 보여주는 opcode 패널이 표시됩니다.

키보드 명령어¶

실시간 모드 내에서 키보드 명령은 디스플레이를 제어합니다:

q

프로파일러를 종료하고 셸로 돌아갑니다.

s / S

정렬 순서 간 이동 (샘플 개수, 비율, 총 시간, 누적 비율, 누적 시간).

p

디스플레이 업데이트를 일시 중지하거나 재개합니다. 디스플레이가 일시 중지된 동안에도 샘플링은 백그라운드에서 계속되므로, 데이터 수집을 중단하지 않고도 결과를 검토하기 위해 보기를 고정할 수 있습니다.

r

모든 통계를 초기화하고 다시 시작합니다. 이 기능은 우발적인 데이터 손실을 방지하기 위해 프로파일링이 완료된 후 비활성화됩니다.

/

필터 모드로 진입하여 이름으로 함수를 검색합니다. 필터는 파일 이름 및 함수 이름에 대해 대소문자를 구분하지 않는 부분 문자열 일치를 사용합니다. 패턴을 입력하고 Enter를 누르면 적용되고, Escape 키를 누르면 취소됩니다. Glob 패턴과 정규 표현식은 지원되지 않습니다.

c

현재 필터를 지우고 모든 함수를 다시 표시합니다.

t

모든 스레드를 합산하여 보거나 스레드별 통계를 보는 것을 전환합니다. 스레드별 모드에서는 (예: 1/4) 사용 가능한 스레드 중 위치를 보여주는 스레드 카운터가 나타납니다.

← → 또는 ↑ ↓

개별 스레드 보기에서는 스레드 간을 탐색할 수 있습니다. 탐색은 마지막 스레드에서 첫 번째 스레드로, 그리고 그 역순으로 순환합니다.

+ / -

디스플레이 새로 고침 속도를 증가시키거나 감소시킵니다. 범위는 0.05초(20Hz, 매우 반응성이 좋음)부터 1.0초(1Hz, 오버헤드가 낮음)까지입니다. 더 빠른 새로 고침 속도는 CPU를 더 많이 사용합니다. 기본값은 0.1초(10Hz)입니다.

x

시간이 지남에 따라 함수가 더 뜨거워지거나 식어지는지를 보여주는 추세 표시줄을 토글합니다. 활성화되면, 증가하는 측정 항목은 녹색으로, 감소하는 측정 항목은 빨간색으로 표시되며 이전과 비교하여 각 업데이트를 표시합니다.

h 또는 ?

사용 가능한 모든 명령어를 포함하는 도움말 화면을 표시합니다.

j / k (또는 Up / Down)

(--opcodes 가 활성화된 경우) 옵코드 패널에서 오피코드 항목을 탐색합니다. 이 키들은 현재 선택된 함수의 명령어 수준 통계를 스크롤 방식으로 보여줍니다.

When profiling finishes (duration expires or target process exits), the display shows a “PROFILING COMPLETE” banner and freezes the final results. You can still navigate, sort, and filter the results before pressing q to exit.

실시간 모드는 파일 출력을 생성하는 대신 상호 작용적인 터미널 인터페이스를 사용하기 때문에 출력 형식 옵션(--collapsed, --flamegraph 등)과 호환되지 않습니다.

비동기 인식 프로파일링¶

For programs using asyncio, the profiler offers async-aware mode (--async-aware) that reconstructs call stacks based on the task structure rather than the raw Python frames:

python -m profiling.sampling run --async-aware async_script.py

비동기 코드를 표준 프로파일링하는 것은 혼란스러울 수 있습니다. 실제 콜 스택은 논리적 제너레이터 흐름보다 이벤트 루프 내부를 보여주기 때문입니다. 비동기 인식 모드는 어떤 태스크가 실행 중인지 추적하고 await 체인을 반영하는 스택을 제시하여 이를 해결합니다.

import asyncio

async def fetch(url):
    await asyncio.sleep(0.1)
    return url

async def main():
    for _ in range(50):
        await asyncio.gather(fetch("a"), fetch("b"), fetch("c"))

if __name__ == "__main__":
    asyncio.run(main())

python -m profiling.sampling run --async-aware --flamegraph -o out.html script.py

참고

비동기 인식 프로파일링은 대상 프로세스가 asyncio 모듈을 로드해야 합니다. asyncio를 가져오기 전에 스크립트를 프로파일하면, 비동기 인식 모드는 태스크 정보를 캡처할 수 없습니다.

비동기 모드¶

--async-mode 옵션은 프로파일에 표시되는 태스크를 제어합니다:

python -m profiling.sampling run --async-aware --async-mode=running async_script.py
python -m profiling.sampling run --async-aware --async-mode=all async_script.py

With --async-mode=running (the default), only the task currently executing on the CPU is profiled. This shows where your program is actively spending time and is the typical choice for performance analysis.

--async-mode 가 =all 인 경우, 일시 중지된 태스크(I/O, 락 또는 다른 태스크를 기다리는)도 포함됩니다. 이 모드는 프로그램이 무엇을 기다리고 있는지 이해하는 데 유용하지만, 모든 일시 중지된 태스크가 각 샘플에 나타나기 때문에 더 큰 프로파일을 생성합니다.

태스크 마커 및 스택 재구성¶

비동기 인식 프로파일에서는 asyncio 태스크 사이의 경계를 표시하는 <task> 프레임을 볼 수 있습니다. 이들은 프로파일러가 삽입한 합성 프레임으로, 태스크 구조를 보여줍니다. 태스크 이름은 이 프레임에서 함수 이름으로 나타납니다.

하나의 태스크가 다른 태스크를 기다릴 때(await), 프로파일러는 await 관계를 따라 논리적인 호출 체인을 재구성합니다. “리프” 태스크만 (현재 기다리고 있는 다른 태스크가 없는 태스크) 자체 스택 항목을 생성합니다. 다른 태스크에 의해 기다려지는 태스크는 그 대기자(awaiter)의 스택 일부로 나타납니다.

태스크가 여러 대기자(태스크 그래프에서 마름모 패턴)를 가질 경우, 프로파일러는 결정론적으로 한 개의 부모를 선택하고 태스크 마커에 부모의 개수(예: MyTask (2 parents))로 주석을 달아줍니다. 이는 대체 실행 경로가 존재하지만 이 특정 스택에는 표시되지 않음을 나타냅니다.

옵션 제한 사항¶

비동기 인식 모드는 다른 스택 재구성 메커니즘을 사용하며 다음 옵션과 호환되지 않습니다: --native, --no-gc, --all-threads, 그리고 --mode 가 =cpu 또는 --mode 가 =gil 인 경우.

replay¶

옵션들을 덤프합니다.¶

다음 옵션들은 dump 서브커맨드에 적용됩니다:

-a, --all-threads¶

주 스레드가 아닌 대상 프로세스의 모든 스레드를 덤프합니다.

--native¶

비-Python 코드에 대한 <native> 프레임을 포함합니다.

--no-gc¶

활성 가비지 수거에 대한 <GC> 프레임을 제외합니다.

--opcodes¶

사용 가능한 경우 바이트코드 옵코드 이름을 표시합니다.

--async-aware¶

asyncio 애플리케이션의 await 경계를 가로질러 스택을 재구성합니다.

--async-mode <mode>¶

비동기 스택 모드: running (실행 중인 작업만) 또는 all (대기 중인 작업을 포함한 모든 작업). dump 의 기본값은 all 입니다. --async-aware 가 필요합니다.

--blocking¶

스택을 읽는 동안 대상 프로세스의 모든 스레드를 일시 중지합니다.

표본 추출 옵션¶

-r <rate>, --sampling-rate <rate>¶

샘플링 비율(예: 10000, 10khz, 10k). 기본값: 1khz.

-d <seconds>, --duration <seconds>¶

프로파일링 지속 시간(초 단위). 기본값: 완료까지 실행합니다.

-a, --all-threads¶

메인 스레드뿐만 아니라 모든 스레임을 샘플에서 합니다.

--realtime-stats¶

프로파일링 중에 샘플링 통계를 표시합니다.

--native¶

비-Python 코드에 대한 <native> 프레임을 포함합니다.

--no-gc¶

가비지 수거에 대한 <GC> 프레임을 제외합니다.

--async-aware¶

asyncio 프로그램용 비동기 인식 프로파일링을 활성화합니다.

--opcodes¶

명령어 수준 프로파일링을 위해 바이트코드 옵코드 정보를 수집합니다. 특수화된 것을 포함하여 실행 중인 바이트코드 명령어를 보여줍니다. --live, --flamegraph, --heatmap, 그리고 --gecko 형식과만 호환됩니다.

--subprocesses¶

서브 프로세스도 프로파일링합니다. 각 서브 프로세스는 자체 프로파일러 인스턴스와 출력 파일을 갖습니다. --live 와는 호환되지 않습니다.

--blocking¶

Pause the target process during each sample. This ensures consistent stack traces at the cost of slowing down the target. Use with longer intervals (1000 µs or higher) to minimize impact. See 블로킹 모드 for details.

--async-mode <mode>¶

비동기 프로파일링 모드: running (기본값) 또는 all. --async-aware 가 필요합니다.

-o <path>, --output <path>¶

Output file or directory path. Default behavior varies by format: --pstats prints a text table to stdout, while -o writes a binary pstats file. Other formats generate a file named <format>_<PID>.<ext> (for example, flamegraph_12345.html). --heatmap creates a directory named heatmap_<PID>.

--browser¶

Automatically open HTML output (--flamegraph and --heatmap) in your default web browser after generation. When profiling with --subprocesses, only the main process opens the browser; subprocess outputs are never auto-opened.
