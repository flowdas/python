typing — 타입 힌트 지원¶

Added in version 3.5.

소스 코드: Lib/typing.py

참고

Python 런타임은 함수 및 변수 타입 어노테이션을 강제하지 않습니다. 이는 :term:`static type checkers <static type checker>`와 IDE, linter 등 타사 도구에 의해 사용될 수 있습니다.

이 모듈은 형 힌트에 대한 런타임 지원을 제공합니다.

다음 함수를 고려하십시오:

def surface_area_of_cube(edge_length: float) -> str:
    return f"The surface area of the cube is {6 * edge_length ** 2}."

함수 surface_area_of_cube 는 type hint edge_length: float 에 명시된 대로 float 의 인스턴스가 될 것으로 예상되는 인수를 받습니다. 이 함수는 -> str 힌트에 명시된 바와 같이 str 의 인스턴스를 반환할 것으로 예상됩니다.

타입 힌트는 :class:`float 또는 :class:`str`과 같은 간단한 클래스일 수 있지만, 더 복잡할 수도 있습니다. :mod:`typing 모듈은 보다 고급 타입 힌트의 어휘를 제공합니다.`

새 기능은 빈번하게 typing 모듈에 추가됩니다. typing_extensions 패키지는 이러한 새로운 기능을 이전 버전의 파이썬으로 백포트합니다.

Python 타입 시스템 사양¶

Python 타입 시스템의 표준적이고 최신 사양은 `Specification for the Python type system <https://typing.python.org/en/latest/spec/index.html>`에서 찾을 수 있습니다.

형 에일리어스¶

형 에일리어스는 :keyword: type`’ 문을 사용하여 정의되며, TypeAliasType 의 인스턴스를 생성합니다. 이 예제에서 Vector 와 list[float] 는 정적 타입 검사기에 의해 동등하게 취급될 것입니다:

type Vector = list[float]

def scale(scalar: float, vector: Vector) -> Vector:
    return [scalar * num for num in vector]

# 타입 검사를 통과합니다. 플로트 리스트가 벡터로 간주됩니다.
new_vector = scale(2.0, [1.0, -4.2, 5.4])

형 에일리어스는 복잡한 형 서명을 단순화하는 데 유용합니다. 예를 들면:

from collections.abc import Sequence

# ConnectionOptions는 문자열 키와 문자열 값을 갖는 딕셔너리입니다.
type ConnectionOptions = dict[str, str]
# 주소는 문자열과 정수를 갖는 튜플입니다.
type Address = tuple[str, int]
# 서버는 (주소, 연결 옵션) 튜플입니다.
type Server = tuple[Address, ConnectionOptions]

def broadcast_message(message: str, servers: Sequence[Server]) -> None:
    ...

# 정적 타입 검사기는 이전 타입 시그니처가 다음과 완전히 동등하다고 간주할 것입니다.
def broadcast_message(
    message: str,
    servers: Sequence[tuple[tuple[str, int], dict[str, str]]]
) -> None:
    ...

type 문은 Python 3.12에서 새로 도입되었습니다. 하위 호환성을 위해 타입 별칭을 단순 할당(simple assignment)을 통해서도 생성할 수 있습니다:

Vector = list[float]

또는 :data:`TypeAlias`로 표시하여 일반 변수 할당이 아닌 타입 별칭임을 명시합니다:

from typing import TypeAlias

Vector: TypeAlias = list[float]

NewType¶

NewType 헬퍼를 사용하여 고유한 타입을 생성하십시오:

from typing import NewType

UserId = NewType('UserId', int)
some_id = UserId(524313)

정적 형 검사기는 새 형을 원래 형의 서브 클래스인 것처럼 다룹니다. 논리 에러를 잡는 데 유용합니다:

def get_user_name(user_id: UserId) -> str:
    ...

# 타입 검사를 통과합니다.
user_a = get_user_name(UserId(42351))

# 타입 검사에 실패합니다. int는 UserId가 아닙니다.
user_b = get_user_name(-1)

UserId 형의 변수에 대해 모든 int 연산을 여전히 수행할 수 있지만, 결과는 항상 int 형이 됩니다. 이것은 int가 기대되는 모든 곳에 UserId를 전달할 수 있지만, 잘못된 방식으로 의도하지 않게 UserId를 만들지 않도록 합니다:

# 'output'은 'UserId'가 아닌 'int' 타입입니다.
output = UserId(23413) + UserId(54341)

이러한 검사는 정적 타입 검사기에 의해서만 강제된다는 점에 유의하세요. 런타임 시, Derived = NewType(‘Derived’, Base’) 문은 Derived 를 즉시 전달받은 매개변수를 반환하는 호출 가능한 객체로 만듭니다. 이는 표현식 Derived(some_value) 가 새 클래스를 생성하거나 일반 함수 호출보다 많은 오버헤드를 유발하지 않음을 의미합니다.

더욱 정확하게, 표현식 some_value is Derived(some_value)는 실행 시간에 항상 참입니다.

Derived 의 서브 타입을 만드는 것은 올바르지 않습니다:

from typing import NewType

UserId = NewType('UserId', int)

# 런타임에 실패하며 타입 검사를 통과하지 못합니다.
class AdminUserId(UserId): pass

However, it is possible to create a NewType based on a ‘derived’ NewType:

from typing import NewType

UserId = NewType('UserId', int)

ProUserId = NewType('ProUserId', UserId)

그리고 ProUserId에 대한 형 검사는 예상대로 작동합니다.

자세한 내용은 PEP 484를 참조하십시오.

참고

타입 별칭 사용은 두 타입이 서로 동등*하다는 것을 선언한다는 점을 상기해 주십시오. ``type Alias = Original``를 실행하면 정적 타입 검사기는 모든 경우에 ``Alias``를 ``Original``와 *정확히 동등한 것으로 취급합니다. 이는 복잡한 타입 서명을 단순화하고 싶을 때 유용합니다.

반면에, NewType은 한 형을 다른 형의 서브 형으로 선언합니다. Derived = NewType('Derived', Original)은 정적 형 검사기가 Derived를 Original의 서브 클래스로 취급하게 합니다. 이는 Original 형의 값이 Derived 형의 값이 예상되는 위치에서 사용될 수 없음을 의미합니다. 실행 시간 비용을 최소화하면서 논리 에러를 방지하려는 경우에 유용합니다.

Added in version 3.5.2.

버전 3.10에서 변경: NewType``은 이제 함수가 아니라 클래스입니다. 그 결과, ``NewType 호출 시 일반 함수보다 추가적인 런타임 비용이 발생합니다.

버전 3.11에서 변경: NewType 호출의 성능이 Python 3.9 레벨로 복원되었습니다.

콜러블 객체에 주석 달기¶

함수 또는 다른 callable 객체는 collections.abc.Callable 을 사용하거나 폐기된 typing.Callable 을 사용하여 주석 처리할 수 있습니다. Callable[[int], str] 은 단일 인자 타입이 int 이고 반환 타입이 str 인 함수를 의미합니다.

예:

from collections.abc import Callable, Awaitable

def feeder(get_next_item: Callable[[], str]) -> None:
    ...  # 본문 함수 정의에 대한 설명

def async_query(on_success: Callable[[int], None],
                on_error: Callable[[int, Exception], None]) -> None:
    ...  # 본문

async def on_update(value: str) -> None:
    ...  # 본문

callback: Callable[[str], Awaitable[None]] = on_update

서브스크립션 문법은 항상 정확히 두 개의 값, 즉 인자 목록과 반환 유형을 사용해야 합니다. 인자 목록은 타입 리스트, ParamSpec, Concatenate, 또는 생략 부호(...)여야 합니다. 반환 유형은 단일 타입이어야 합니다.

인자 목록으로 리터럴 생략 부호 ... 가 주어지면, 임의의 매개변수 목록을 가진 콜러블이 허용됨을 의미합니다:

def concat(x: str, y: str) -> str:
    return x + y

x: Callable[..., str]
x = str     # OK
x = concat  # 이 또한 OK

Callable 은 가변 인자 개수를 받는 함수, overloaded functions 과 같은 복잡한 서명이나 키워드 전용 매개변수를 가진 함수를 표현할 수 없습니다. 하지만 이러한 서명은 Protocol 클래스를 정의하고 그에 __call__() 메서드를 추가함으로써 표현할 수 있습니다:

from collections.abc import Iterable
from typing import Protocol

class Combiner(Protocol):
    def __call__(self, *vals: bytes, maxlen: int | None = None) -> list[bytes]: ...

def batch_proc(data: Iterable[bytes], cb_results: Combiner) -> bytes:
    for item in data:
        ...  # 처리 로직 본문 함수에 대한 주석

def good_cb(*vals: bytes, maxlen: int | None = None) -> list[bytes]:
    ... # 정상 콜백 함수의 정의를 나타냄
def bad_cb(*vals: bytes, maxitems: int | None) -> list[bytes]:
    ... # 잘못된 매개변수 개수의 콜백 함수

batch_proc([], good_cb)  # OK
batch_proc([], bad_cb)   # 오류! 콜백에서 이름과 종류가 달라 두 번째 인자가 부적합합니다.

콜러블 간에 다른 콜러블을 매개변수로 받는 경우는 ParamSpec`을 사용하여 해당 매개변수 타입들이 서로 의존적임을 나타낼 수 있습니다. 또한, 만약 그 콜러블이 다른 콜러블의 인자를 추가하거나 제거하는 경우, :data:`Concatenate 연산자를 사용할 수 있습니다. 이들은 각각 Callable[ParamSpecVariable, ReturnType] 및 Callable[Concatenate[Arg1Type, Arg2Type, ..., ParamSpecVariable], ReturnType] 형태를 가집니다.

버전 3.10에서 변경: Callable 은 이제 ParamSpec 및 Concatenate 을 지원합니다. 자세한 내용은 PEP 612 를 참조하십시오.

제네릭¶

컨테이너에 보관된 객체에 대한 타입 정보는 제네릭 방식으로 정적으로 추론할 수 없기 때문에, 표준 라이브러리의 많은 컨테이너 클래스들은 컨테이너 요소의 예상되는 타입을 표시하기 위해 서브스크립션을 지원합니다.

from collections.abc import Mapping, Sequence

class Employee: ...

# Sequence[Employee]는 시퀀스의 모든 요소가 "Employee"의 인스턴스여야 함을 나타냅니다.
# Mapping[str, str]는 매핑의 모든 키와 모든 값이 문자열이어야 함을 나타냅니다.
def notify_by_email(employees: Sequence[Employee],
                    overrides: Mapping[str, str]) -> None: ...

제네릭 함수와 클래스는 타입 매개 변수 구문\를 사용하여 매개 변수화될 수 있습니다:

from collections.abc import Sequence

def first[T](l: Sequence[T]) -> T:  # 함수가 TypeVar "T"에 대해 제네릭입니다.
    return l[0]

또는 TypeVar 팩토리를 직접 사용하여:

from collections.abc import Sequence
from typing import TypeVar

U = TypeVar('U')                  # 타입 변수 "U"를 선언합니다.

def second(l: Sequence[U]) -> U:  # 함수가 TypeVar "U"에 대해 제네릭입니다.
    return l[1]

버전 3.12에서 변경: 제네릭에 대한 구문 지원은 Python 3.12에서 새로 추가되었습니다.

튜플 어노테이션¶

Python의 대부분의 컨테이너에 대해, 타입 시스템은 컨테이너의 모든 요소가 동일한 타입을 가질 것이라고 가정합니다. 예를 들어:

from collections.abc import Mapping

# 타입 검사기는 ``x``의 모든 요소가 int일 것으로 추론할 것입니다.
x: list[int] = []

# 타입 검사기 오류: ``list``는 단일 타입 인수만 허용합니다:
y: list[int, str] = [1, 'foo']

# 타입 검사기는 ``z``의 모든 키가 문자열이며,
# 그리고 ``z``의 모든 값이 문자열 또는 int일 것으로 추론할 것입니다.
z: Mapping[str, str | int] = {}

하지만 list`는 하나의 타입 인수만 허용하므로, 타입 검사기는 위 ``y` 할당에서 오류를 발생시킵니다. 유사하게, :class:`~collections.abc.Mapping`은 두 개의 타입 인수만 허용합니다: 첫 번째는 키의 타입을 나타내고, 두 번째는 값의 타입을 나타냅니다.

하지만 다른 대부분의 Python 컨테이너와 달리, 튜플은 요소들이 모두 동일한 타입을 가지지 않는 경우도 일반적인 방식을 따릅니다. 이러한 이유로, 튜플은 Python의 타입 시스템에서 특별 취급됩니다. tuple 은 임의의 수 의 타입 인수를 허용합니다:

# OK: ``x``가 단일 요소만 가진 길이 1 튜플에 할당됩니다.
x: tuple[int] = (5,)

# OK: ``y``가 길이 2의 튜플에 할당됩니다;
# 요소 1은 int이고, 요소 2는 str입니다.
y: tuple[int, str] = (5, "foo")

# 오류: 타입 어노테이션이 길이 1인 튜플을 나타내지만,
# ``z``는 길이 3의 튜플에 할당되었습니다.
z: tuple[int] = (1, 2, 3)

임의의 길이가 될 수 있는 튜플을 나타내고 모든 요소가 동일한 타입 T 인 경우, 리터럴 생략 부호라 ... 를 사용합니다: tuple[T, ...] 입니다. 빈 튜플을 나타내려면 tuple[()] 를 사용하십시오. 일반적인 tuple 를 어노테이션으로 사용하는 것은 tuple[Any, ...] 를 사용하는 것과 동등합니다:

x: tuple[int, ...] = (1, 2)
# 이 재할당은 OK입니다: ``tuple[int, ...]``는 x가 어떤 길이일 수 있음을 나타냅니다.
x = (1, 2, 3)
x = ()
# 이 재할당은 오류입니다: ``x``의 모든 요소는 int여야 합니다.
x = ("foo", "bar")

# ``y``는 빈 튜플에만 할당될 수 있습니다.
y: tuple[()] = ()

z: tuple = ("foo", "bar")
# 이 재할당은 OK입니다: 일반 ``tuple``는 ``tuple[Any, ...]``와 동등합니다.
z = (1, 2, 3)
z = ()

클래스 객체의 타입¶

C 로 어노테이션된 변수는 C 타입을 가진 값을 허용할 수 있습니다. 반면, type[C] (또는 폐지된 typing.Type[C]:)로 어노테이션된 변수는 클래스 자체인 값—구체적으로 C 의 클래스 객체 —을 허용할 수 있습니다. 예를 들어:

a = 3         # 타입은 ``int``입니다.
b = int       # 타입은 ``type[int]``입니다.
c = type(a)   # 이 역시 타입은 ``type[int]``입니다.

`type[C]`가 공변적(covariant)임을 유념하십시오:

class User: ...
class ProUser(User): ...
class TeamUser(User): ...

def make_new_user(user_class: type[User]) -> User:
    # ...
    return user_class()

make_new_user(User)      # OK
make_new_user(ProUser)   # Also OK: ``type[ProUser]``은 ``type[User]``의 서브타입입니다.
make_new_user(TeamUser)  # 여전히 괜찮습니다
make_new_user(User())    # 오류: ``type[User]``가 예상되지만 ``User``를 받았습니다.
make_new_user(int)       # 오류: ``type[int]``는 ``type[User]``의 서브타입이 아닙니다.

type`의 유효한 매개 변수는 클래스, :data:`Any, 형 변수, 그리고 이 유형 중 무엇이든의 합집합뿐입니다. 예를 들어:

def new_non_team_user(user_class: type[BasicUser | ProUser]): ...

new_non_team_user(BasicUser)  # OK
new_non_team_user(ProUser)    # OK
new_non_team_user(TeamUser)   # 오류: ``type[TeamUser]``는 서브타입이 아닙니다.
                              # ``type[BasicUser | ProUser]``의
new_non_team_user(User)       # 이 또한 오류입니다지

type[Any] 는 Python의 메타클래스 계층 의 루트인, type 와 동일합니다.

제너레이터와 코루틴 주석 처리하기¶

제너레이터는 제네릭 유형 :class:`Generator[YieldType, SendType, ReturnType] <collections.abc.Generator>`를 사용하여 주석 처리할 수 있습니다. 예를 들어:

def echo_round() -> Generator[int, float, str]:
    sent = yield 0
    while sent >= 0:
        sent = yield round(sent)
    return 'Done'

표준 라이브러리의 다른 많은 제네릭 클래스와 달리, Generator 의 SendType 은 공변적(covariant)이 아닌 반변적(contravariant), 또는 불변적(invariant)으로 동작합니다.

SendType``과 ``ReturnType 매개 변수는 기본값이 :const:`!None`입니다:

def infinite_stream(start: int) -> Generator[int]:
    while True:
        yield start
        start += 1

이러한 유형들을 명시적으로 설정하는 것도 가능합니다:

def infinite_stream(start: int) -> Generator[int, None, None]:
    while True:
        yield start
        start += 1

값을 항상 생성(yield)만 하는 간단한 제너레이터는 Iterable[YieldType] 또는 :class:`Iterator[YieldType] <collections.abc.Iterator>`의 반환형을 갖도록 주석 처리할 수도 있습니다:

def infinite_stream(start: int) -> Iterator[int]:
    while True:
        yield start
        start += 1

비동기 제너레이터도 유사한 방식으로 처리되지만, ReturnType 유형 인수는 기대되지 않습니다 (AsyncGenerator[YieldType, SendType]). SendType 인수의 기본값은 :const:`!None`이므로 다음 정의들은 동일합니다:

async def infinite_stream(start: int) -> AsyncGenerator[int]:
    while True:
        yield start
        start = await increment(start)

async def infinite_stream(start: int) -> AsyncGenerator[int, None]:
    while True:
        yield start
        start = await increment(start)

동기적인 경우와 마찬가지로, AsyncIterable[YieldType] 및 :class:`AsyncIterator[YieldType] <collections.abc.AsyncIterator>`도 사용 가능합니다:

async def infinite_stream(start: int) -> AsyncIterator[int]:
    while True:
        yield start
        start = await increment(start)

코루틴은 :class:`Coroutine[YieldType, SendType, ReturnType] <collections.abc.Coroutine>`를 사용하여 주석 처리할 수 있습니다. 제네릭 인수는 예를 들어 :class:`~collections.abc.Generator`의 것과 일치합니다:

from collections.abc import Coroutine
c: Coroutine[list[str], str, int]  # 다른 곳에서 정의된 코루틴
x = c.send('hi')                   # 'x'의 추론된 유형은 list[str]입니다.
async def bar() -> None:
    y = await c                    # 'y'의 추론된 유형은 int입니다.

사용자 정의 제네릭 형¶

사용자 정의 클래스는 제네릭 클래스로 정의 할 수 있습니다.

from logging import Logger

class LoggedVar[T]:
    def __init__(self, value: T, name: str, logger: Logger) -> None:
        self.name = name
        self.logger = logger
        self.value = value

    def set(self, new: T) -> None:
        self.log('Set ' + repr(self.value))
        self.value = new

    def get(self) -> T:
        self.log('Get ' + repr(self.value))
        return self.value

    def log(self, message: str) -> None:
        self.logger.info('%s: %s', self.name, message)

이 구문은 LoggedVar 클래스가 단일 형 변수 인 T 를 중심으로 매개 변수화되었음을 나타냅니다. 이는 또한 T 가 클래스 내부에서 유효한 유형임을 의미합니다.

제네릭 클래스는 암묵적으로 :class:`Generic`으로부터 상속받습니다. Python 3.11 이하와의 호환성을 위해, 제네릭 클래스임을 나타내기 위해 명시적으로 :class:`Generic`을 상속하는 것도 가능합니다:

from typing import TypeVar, Generic

T = TypeVar('T')

class LoggedVar(Generic[T]):
    ...

제네릭 클래스는 __class_getitem__() 메서드를 가지고 있어 런타임에 매개 변수화될 수 있습니다 (예: 아래의 LoggedVar[int]):

from collections.abc import Iterable

def zero_all_vars(vars: Iterable[LoggedVar[int]]) -> None:
    for var in vars:
        var.set(0)

제네릭 유형은 임의 개수의 형 변수를 가질 수 있습니다. :class:`TypeVar`의 모든 변종이 제네릭 유형의 매개 변수로 허용됩니다:

from typing import TypeVar, Generic, Sequence

class WeirdTrio[T, B: Sequence[bytes], S: (int, str)]:
    ...

OldT = TypeVar('OldT', contravariant=True)
OldB = TypeVar('OldB', bound=Sequence[bytes], covariant=True)
OldS = TypeVar('OldS', int, str)

class OldWeirdTrio(Generic[OldT, OldB, OldS]):
    ...

Generic에 대한 각 형 변수 인자는 달라야 합니다. 그래서 이것은 잘못되었습니다:

from typing import TypeVar, Generic
...

class Pair[M, M]:  # SyntaxError
    ...

T = TypeVar('T')

class Pair(Generic[T, T]):   # INVALID
    ...

제네릭 클래스는 다른 클래스로부터 상속받을 수도 있습니다:

from collections.abc import Sized

class LinkedList[T](Sized):
    ...

제네릭 클래스로부터 상속받을 때, 일부 유형 매개 변수는 고정될 수 있습니다:

from collections.abc import Mapping

class MyDict[T](Mapping[str, T]):
    ...

이 경우 MyDict는 단일 매개 변수 T를 갖습니다.

타입 매개 변수를 명시하지 않고 제네릭 클래스를 사용하면 각각의 위치에 대해 Any 를 가정합니다. 다음 예제에서 MyIterable 는 제네릭이 아니지만 암묵적으로 Iterable[Any] 으로부터 상속받습니다:

from collections.abc import Iterable

class MyIterable(Iterable): # Same as Iterable[Any]
    ...

사용자 정의 제네릭 유형 별칭도 지원됩니다. 예시:

from collections.abc import Iterable

type Response[S] = Iterable[S] | int

# 반환 타입은 Iterable[str] | int와 동일합니다.
def response(query: str) -> Response[str]:
    ...

type Vec[T] = Iterable[tuple[T, T]]

def inproduct[T: (int, float, complex)](v: Vec[T]) -> T: # 같은 iterable이므로
    return sum(x*y for x, y in v)

하위 호환성을 위해 일반 타입 별칭은 간단한 할당을 통해서도 생성할 수 있습니다:

from collections.abc import Iterable
from typing import TypeVar

S = TypeVar("S")
Response = Iterable[S] | int

버전 3.7에서 변경: Generic에는 더는 사용자 정의 메타 클래스가 없습니다.

버전 3.12에서 변경: 제네릭 및 타입 별칭에 대한 구문적 지원이 3.12 버전부터 추가되었습니다. 이전에는 제네릭 클래스가 `:class:`Generic`을 명시적으로 상속하거나 기반 중 하나에 타입 변수를 포함해야 했습니다.

매개변수 식이 있는 사용자 정의 제네릭 또한 [**P] 형태의 매개변수 지정 변수를 통해 지원됩니다. 그 동작 방식은 위에서 설명된 타입 변수와 일관되어서, 매개변수 지정 변수는 typing 모듈에 의해 특수한 타입 변수로 취급됩니다. 다만 한 가지 예외는 타입 목록이 :class:`ParamSpec`을 대체하는 데 사용될 수 있다는 점입니다:

>>> class Z[T, **P]: ...  # T는 TypeVar이며, P는 ParamSpec입니다.
...
>>> Z[int, [dict, float]]
__main__.Z[int, [dict, float]]

ParamSpec 에 대한 제네릭 클래스는 Generic 으로부터 명시적 상속을 사용해서도 생성할 수 있습니다. 이 경우 ** 를 사용하지 않습니다:

from typing import ParamSpec, Generic

P = ParamSpec('P')

class Z(Generic[P]):
    ...

TypeVar`와 :class:`ParamSpec`의 또 다른 차이점은, 단 하나의 매개변수 지정 변수만 가진 제네릭은 미적인 이유로 ``X[[Type1, Type2, ...]]` 형태로는 물론 X[Type1, Type2, ...] 형태의 목록도 받아들인다는 것입니다. 내부적으로 후자는 전자로 변환되므로 다음 사항들은 동등합니다:

>>> class X[**P]: ...
...
>>> X[int, str]
__main__.X[[int, str]]
>>> X[[int, str]]
__main__.X[[int, str]]

ParamSpec 을 가진 제네릭은 주로 정적 타입 검사를 위해 사용되기 때문에, 때로는 대체 후 올바른 __parameters__ 를 갖지 못할 수 있다는 점에 유의하세요.

버전 3.10에서 변경: Generic`이 이제 매개변수 식을 통해 파라미터화될 수 있습니다. 자세한 내용은 :class:`ParamSpec 및 :pep:`612`를 참조하세요.

사용자 정의 제네릭 클래스는 메타클래스 충돌 없이 ABC를 기반 클래스로 가질 수 있습니다. 제네릭 메타클래스는 지원되지 않습니다. 제네릭 파라미터화 결과는 캐시되고, typing 모듈의 대부분의 타입은 :term:`hashable`하며 동등 비교가 가능합니다.

Any 형¶

특수한 종류의 형이 바로 :data:`Any`입니다. 정적 타입 검사기는 모든 타입을 :data:`Any`에 할당 가능한 것으로, :data:`Any`는 모든 타입에 할당 가능한 것으로 취급합니다.

이것은 Any 형의 값에 대해 어떤 연산이나 메서드 호출을 수행하고, 그것을 임의의 변수에 대입할 수 있다는 것을 의미합니다:

from typing import Any

a: Any = None
a = []          # OK
a = 2           # OK

s: str = ''
s = a           # OK

def foo(item: Any) -> int:
    # 타입 검사를 통과합니다. 'item'은 어떤 타입일 수 있으며,
    # 그 타입에 'bar' 메서드가 있을 수도 있습니다.
    item.bar()
    ...

Any 타입의 값을 더 구체적인 타입에 할당할 때 타입 검사가 수행되지 않는다는 점에 주목하세요. 예를 들어, 개발 시 s 는 str 타입으로 선언되었지만 런타임에 int 값이 전달되었음에도 불구하고 정적 타입 검사기는 a 를 s 에 할당할 때 오류를 보고하지 않았습니다!

또한, 반환형이나 매개 변수 형이 없는 모든 함수는 묵시적으로 Any 기본값을 사용합니다:

def legacy_parser(text):
    ...
    return data

# 정적 타입 검사기는 위 코드를 다음과 같은 시그니처를 갖는 것처럼 처리할 것입니다.
def legacy_parser(text: Any) -> Any:
    ...
    return data

이 동작은 여러분이 동적으로 형이 지정되는 코드와 정적으로 형이 지정되는 코드를 혼합해야 할 때 Any를 탈출구로 사용할 수 있도록 합니다.

Any의 동작과 object의 동작을 대조하십시오. Any와 유사하게, 모든 형은 object의 서브 형입니다. 그러나, Any와는 달리, 그 반대는 사실이 아닙니다: object는 다른 모든 형의 서브 형이 아닙니다.

이것은 값의 형이 object일 때, 형 검사기가 그것에 대한 거의 모든 연산을 거부하고, 그것을 더 특수한 형의 변수에 대입(또는 그것을 반환 값으로 사용)하는 것이 형 에러임을 의미합니다. 예를 들면:

def hash_a(item: object) -> int:
    # 타입 검사에 실패합니다. 객체는 'magic' 메서드를 가지고 있지 않습니다.
    item.magic()
    ...

def hash_b(item: Any) -> int:
    # 타입 검사를 통과합니다
    item.magic()
    ...

# int와 str은 object의 서브클래스이므로 타입 검사를 통과합니다.
hash_a(42)
hash_a("foo")

# Any는 모든 타입에 할당 가능하므로 타입 검사를 통과합니다.
hash_b(42)
hash_b("foo")

값이 형 안전한 방식으로 모든 형이 될 수 있음을 표시하려면 object를 사용하십시오. 값이 동적으로 형이 지정됨을 표시하려면 Any를 사용하십시오.

명목적 대 구조적 서브 타이핑¶

초기에 PEP 484 에서는 파이썬 정적 타입 시스템을 명목적 서브타이핑 을 사용한다고 정의했습니다. 이는 클래스 A 가 예상되는 클래스 B 의 경우에 오직 A 가 B 의 서브클래스일 때만 허용됨을 의미합니다.

이 요구 사항은 이전에 Iterable과 같은 추상 베이스 클래스에도 적용되었습니다. 이 접근 방식의 문제점은 이것을 지원하려면 클래스를 명시적으로 표시해야만 한다는 점입니다. 이는 파이썬답지 않고 관용적인 동적으로 형이 지정된 파이썬 코드에서 일반적으로 수행하는 것과는 다릅니다. 예를 들어, 이것은 PEP 484를 만족합니다:

from collections.abc import Sized, Iterable, Iterator

class Bucket(Sized, Iterable[int]):
    ...
    def __len__(self) -> int: ...
    def __iter__(self) -> Iterator[int]: ...

PEP 544 는 사용자가 클래스 정의에서 명시적인 베이스 클래스 없이 위의 코드를 작성할 수 있게 함으로써 이 문제를 해결하며, 정적 타입 검사기가 Bucket 을 Sized 와 Iterable[int] 의 하위 타입으로 암묵적으로 간주하도록 합니다. 이것은 구조적 서브타이핑 (또는 정적 덕 타이핑)으로 알려져 있습니다:

from collections.abc import Iterator, Iterable

class Bucket:  # 주의: 기본 클래스가 없습니다.
    ...
    def __len__(self) -> int: ...
    def __iter__(self) -> Iterator[int]: ...

def collect(items: Iterable[int]) -> int: ...
result = collect(Bucket())  # 타입 검사를 통과합니다.

또한, 특별한 클래스 Protocol을 서브 클래싱 함으로써, 사용자는 새로운 사용자 정의 프로토콜을 정의하여 구조적 서브 타이핑을 완전히 누릴 수 있습니다 (아래 예를 참조하십시오).

특수 타이핑 프리미티브¶

특수형¶

이들은 어노테이션에서 유형으로 사용될 수 있습니다. [] 를 사용한 구독을 지원하지 않습니다.

typing.Any¶

제한되지 않는 형을 나타내는 특수형.

  • 모든 형은 :data:`Any`와 호환됩니다.

  • :data:`Any`는 모든 유형에 할당될 수 있습니다.

버전 3.11에서 변경: :data:`Any`는 이제 기본 클래스로 사용될 수 있습니다. 이는 아무 곳에서 덕 타이핑할 수 있는 클래스나 매우 동적인 클래스를 가진 경우 타입 검사기 오류를 방지하는 데 유용합니다.

typing.AnyStr¶

:ref:`제한된 유형 변수 <typing-constrained-typevar>`입니다.

정의:

AnyStr = TypeVar('AnyStr', str, bytes)

AnyStr 는 str 또는 bytes 인수를 수락할 수 있지만 둘이 혼합되는 것을 허용할 수 없는 함수에 사용하도록 되어 있습니다.

예를 들면:

def concat(a: AnyStr, b: AnyStr) -> AnyStr:
    return a + b

concat("foo", "bar")    # OK, 결과의 타입은 'str'입니다.
concat(b"foo", b"bar")  # OK, 결과의 타입은 'bytes'입니다.
concat("foo", b"bar")   # 오류, str과 bytes를 혼합할 수 없습니다.

이름과는 달리 AnyStr 는 Any 유형이나 “임의의 문자열”과는 관련이 없습니다. 특히, AnyStr 과 str | bytes 는 서로 다르며 사용 사례도 다릅니다:

# AnyStr을 잘못 사용하는 예:
# 유형 변수는 함수 시그니처에서 한 번만 사용되므로,
# 타입 검사기에 의해 "해결"될 수 없습니다.
def greet_bad(cond: bool) -> AnyStr:
    return "hi there!" if cond else b"greetings!"

# 이 함수를 주석 처리하는 더 좋은 방법:
def greet_proper(cond: bool) -> str | bytes:
    return "hi there!" if cond else b"greetings!"

버전 3.13에서 폐지되었고, 버전 3.18에서 제거됩니다: 새로운 유형 매개변수 문법 으로 대체되었습니다. AnyStr 을 임포트하는 대신 class A[T: (str, bytes)]: ... 를 사용하십시오. 자세한 내용은 PEP 695 를 참조하십시오.

파이썬 3.16에서 AnyStr 은 typing.__all__ 에서 제거되며, typing 으로부터 액세스하거나 임포트할 때 사용 중단 경고가 런타임에 발생합니다. AnyStr 은 파이썬 3.18에서 typing 에서 완전히 제거될 예정입니다.

typing.LiteralString¶

리터럴 문자열만 포함하는 특수 유형입니다.

임의의 문자열 리터럴은 LiteralString 과 호환되며, 또 다른 LiteralString 도 마찬가지입니다. 그러나 단순히 str 으로 지정된 객체는 그렇지 않습니다. LiteralString 유형의 객체를 조합하여 생성된 문자열 또한 LiteralString 으로 허용됩니다.

예제:

def run_query(sql: LiteralString) -> None:
    ...

def caller(arbitrary_string: str, literal_string: LiteralString) -> None:
    run_query("SELECT * FROM students")  # OK
    run_query(literal_string)  # OK
    run_query("SELECT * FROM " + literal_string)  # OK
    run_query(arbitrary_string)  # 타입 검사기 오류
    run_query(  # 타입 검사기 오류
        f"SELECT * FROM students WHERE name = {arbitrary_string}"
    )

LiteralString 은 임의의 사용자 생성 문자열이 문제를 일으킬 수 있는 민감한 API에 유용합니다. 예를 들어, 위의 두 가지 경우 모두에서 타입 검사기 오류가 발생할 수 있으며, 이는 SQL 인젝션 공격에 취약할 수 있습니다.

자세한 내용은 :pep:`675`를 참조하십시오.

Added in version 3.11.

typing.Never¶
typing.NoReturn¶

Never`와 :data:!NoReturn`은 멤버가 없는 유형인 `bottom type <https://en.wikipedia.org/wiki/Bottom_type>`을 나타냅니다.

이는 함수가 절대 반환하지 않음을 나타내는 데 사용될 수 있습니다. 예를 들어 sys.exit():

from typing import Never  # 또는 NoReturn

def stop() -> Never:
    raise RuntimeError('no way')

또는 절대로 호출되어서는 안 되는 함수를 정의하는 데 사용될 수 있습니다. 유효한 인수가 없기 때문입니다. 예를 들어 assert_never():

from typing import Never  # 또는 NoReturn

def never_call_me(arg: Never) -> None:
    pass

def int_or_str(arg: int | str) -> None:
    never_call_me(arg)  # 타입 검사기 오류
    match arg:
        case int():
            print("It's an int")
        case str():
            print("It's a str")
        case _:
            never_call_me(arg)  # OK, arg는 Never (또는 NoReturn) 유형입니다.

Never`와 :data:!NoReturn`은 타입 시스템에서 같은 의미를 가지며 정적 타입 검사기는 둘 다 동등하게 취급합니다.

Added in version 3.6.2: :data:`NoReturn`을 추가했습니다.

Added in version 3.11: :data:`Never`를 추가했습니다.

typing.Self¶

현재 포함된 클래스를 나타내는 특수 유형입니다.`

예를 들면:

from typing import Self, reveal_type

class Foo:
    def return_self(self) -> Self:
        ...
        return self

class SubclassOfFoo(Foo): pass

reveal_type(Foo().return_self())  # 확인된 유형은 "Foo"입니다.
reveal_type(SubclassOfFoo().return_self())  # 확인된 유형은 "SubclassOfFoo"입니다.

이 어노테이션은 다음 표현과 의미상 동등하며, 다만 더 간결한 방식을 사용합니다:

from typing import TypeVar

Self = TypeVar("Self", bound="Foo")

class Foo:
    def return_self(self: Self) -> Self:
        ...
        return self

일반적으로 무언가가 self 를 반환하는 경우(위 예시와 같이), 반환 어노테이션으로 Self 를 사용하는 것이 좋습니다. 만약 Foo.return_self 가 "Foo" 를 반환하도록 어노테이션 되어 있었다면, 타입 체커는 SubclassOfFoo.return_self 에서 반환되는 객체의 타입을 SubclassOfFoo 가 아닌 Foo 로 추론할 것입니다.

다른 일반적인 사용 사례에는 다음이 포함됩니다:

  • cls 파라미터의 인스턴스를 반환하는 대체 생성자로 사용되는 :class:`classmethod`입니다.

  • self를 반환하는 __enter__() 메서드를 어노테이션 하는 경우입니다.

클래스가 서브클래스화될 때 메서드가 항상 서브클래스의 인스턴스를 반환한다고 보장되지 않는다면, 반환 어노테이션으로 Self 를 사용해서는 안 됩니다:

class Eggs:
    # Self를 사용할 경우 반환 어노테이션이 잘못되므로,
    # 반환되는 객체는 항상 Eggs 인스턴스이기 때문입니다.
    def returns_eggs(self) -> "Eggs":
        return Eggs()

더 자세한 내용은 :pep:`673`을 참조하십시오.

Added in version 3.11.

typing.TypeAlias¶

:ref:`<type-aliases>`를 명시적으로 선언하기 위한 특수 어노테이션입니다.

예를 들면:

from typing import TypeAlias

Factors: TypeAlias = list[int]

TypeAlias 는 특히 구형 Python 버전에서 포워드 레퍼런스를 사용하는 별칭을 어노테이션 하는 데 유용합니다. 타입 체커가 이를 일반 변수 할당과 구별하기 어려울 수 있기 때문입니다:

from typing import Generic, TypeAlias, TypeVar

T = TypeVar("T")

# "Box"는 아직 존재하지 않으므로, Python <3.12에서는 포워드 레퍼런스에 따옴표를 사용해야 합니다.
# ``TypeAlias``를 사용하면 타입 체커에게 이것이 문자열에 대한 변수 할당이 아니라 타입 별칭 선언임을 알립니다.
BoxOfStrings: TypeAlias = "Box[str]"

class Box(Generic[T]):
    @classmethod
    def make_box_of_strings(cls) -> BoxOfStrings: ...

더 자세한 내용은 :pep:`613`을 참조하십시오.

Added in version 3.10.

버전 3.12부터 폐지됨: TypeAlias`는 이제 :keyword:`type 구문에 의해 사용이 중단되었으며, 이 구문은 TypeAliasType 인스턴스를 생성하고 포워드 레퍼런스를 기본적으로 지원합니다. TypeAlias`와 :class:`TypeAliasType`가 유사한 목적과 이름으로 서비스하지만 구분되며, 후자가 전자의 타입은 아니라는 점에 유의하십시오. :data:`TypeAlias 제거는 현재 계획되어 있지 않지만, 사용자들은 type 구문으로 마이그레이션하는 것이 권장됩니다.

특수 형태¶

이 값들은 어노테이션에서 타입으로 사용될 수 있습니다. 모두 [] 를 사용하여 서브스크립션을 지원하지만, 각각 고유한 문법을 가지고 있습니다.

class typing.Union¶

Union 형식입니다; Union[X, Y] 는 X | Y 와 같으며 X 또는 Y 중 하나를 의미합니다.

유니언을 정의하려면 예: Union[int, str] 또는 줄임 표현 int | str 를 사용하십시오. 줄임 표현을 사용하는 것이 권장됩니다. 세부 정보:

  • 인자는 형이어야 하며 적어도 하나 있어야 합니다.

  • 공용체의 공용체는 펼쳐집니다, 예를 들어:

    Union[Union[int, str], float] == Union[int, str, float]

    그러나 이는 타입 별칭을 통해 참조되는 유니언에는 적용되지 않는데, 이는 근본적인 :class:`TypeAliasType`의 평가를 강제하는 것을 방지하기 위해서입니다:

    type A = Union[int, str]
Union[A, float] != Union[int, str, float]

  • 단일 인자의 공용체는 사라집니다. 예를 들어:

    Union[int] == int  # 생성자는 실제로 int를 반환합니다.

  • 중복 인자는 건너뜁니다. 예를 들어:

    Union[int, str, int] == Union[int, str] == int | str

  • 공용체를 비교할 때, 인자 순서가 무시됩니다, 예를 들어:

    Union[int, str] == Union[str, int]

  • Union 은 서브클래스화하거나 인스턴스화할 수 없습니다.

  • Union[X][Y]라고 쓸 수 없습니다.

버전 3.7에서 변경: 실행 시간에 공용체의 명시적 서브 클래스를 제거하지 않습니다.

버전 3.10에서 변경: 유니언을 이제 X | Y 로 작성할 수 있습니다. union type expressions 를 참조하십시오.

버전 3.14에서 변경: types.UnionType is now an alias for Union, and both Union[int, str] and int | str create instances of the same class. To check whether an object is a Union at runtime, use isinstance(obj, Union). For compatibility with earlier versions of Python, use get_origin(obj) is typing.Union or get_origin(obj) is types.UnionType.

typing.Optional¶

Optional[X]``은 ``X | None``(또는 ``Union[X, None])와 같습니다.

이는 기본값을 갖는 선택적 인자와 같은 개념이 아님에 유의하십시오. 단지 선택적이기 때문에 기본값을 갖는 선택적 인자가 형 어노테이션에 Optional 한정자가 필요하지는 않습니다. 예를 들면:

def foo(arg: int = 0) -> None:
    ...

한편, 명시적인 None 값이 허용되면, 인자가 선택적인지와 관계없이 Optional을 사용하는 것이 적합합니다. 예를 들면:

def foo(arg: Optional[int] = None) -> None:
    ...

버전 3.10에서 변경: 이제 Optional을 X | None 으로 작성할 수 있습니다. union type expressions 를 참조하십시오.

typing.Concatenate¶

고차 함수를 어노테이션 하는 특수 형태입니다.

Concatenate``는 :ref:`Callable <annotating-callables>` 및 :class:`ParamSpec`과 함께 사용되어 다른 호출 가능 객체의 파라미터를 추가, 제거 또는 변환하는 고차 호출 가능 객체에 어노테이션할 때 사용할 수 있습니다. 사용 방법은 ``Concatenate[Arg1Type, Arg2Type, ..., ParamSpecVariable] 형태입니다. Callable 타입 힌트에서 사용되거나 ParamSpec 매개변수를 가진 사용자 정의 제네릭 클래스를 인스턴스화할 때 Concatenate``를 사용할 수 있습니다. ``Concatenate``의 마지막 파라미터는 반드시 :class:`ParamSpec` 또는 틸드(…``)이어야 합니다.

예를 들어, 데코레이터 with_lock 은 장식된 함수에 threading.Lock 을 제공하며, 이로부터 Concatenate 는 with_lock 이 Lock을 첫 번째 인자로 받는 호출 가능 객체를 예상하고, 다른 타입 시그니처를 가진 호출 가능 객체를 반환함을 나타내는 데 사용될 수 있습니다. 이 경우, ParamSpec 은 반환되는 호출 가능 객체의 매개변수 타입이 전달되는 호출 가능 객체의 파라미터 타입에 의존한다는 것을 나타냅니다:

from collections.abc import Callable
from threading import Lock
from typing import Concatenate

# 이 락을 사용하여 한 번에 하나의 스레드만 함수를 실행하도록 보장합니다.
my_lock = Lock()

def with_lock[**P, R](f: Callable[Concatenate[Lock, P], R]) -> Callable[P, R]:
    '''임계 영역을 제공하는 타입 안전 데코레이터.'''
    def inner(*args: P.args, **kwargs: P.kwargs) -> R:
        # 락을 첫 번째 인자로 제공합니다.
        return f(my_lock, *args, **kwargs)
    return inner

@with_lock
def sum_threadsafe(lock: Lock, numbers: list[float]) -> float:
    '''숫자 리스트를 스레드 안전한 방식으로 모두 더합니다.'''
    with lock:
        return sum(numbers)

# 데코레이터 덕분에 락을 직접 전달할 필요가 없습니다.
sum_threadsafe([1.1, 2.2, 3.3])

Added in version 3.10.

typing.Literal¶

“리터럴 타입”을 정의하기 위한 특별한 타입 구조입니다.

Literal 는 어노테이션된 객체가 제공된 리터럴 중 하나와 동일한 값을 가진다는 것을 타입 검사기에 나타내는 데 사용될 수 있습니다.

예를 들면:

def validate_simple(data: Any) -> Literal[True]:  # 항상 True를 반환합니다.
    ...

type Mode = Literal['r', 'rb', 'w', 'wb']
def open_helper(file: str, mode: Mode) -> str:
    ...

open_helper('/some/path', 'r')      # 타입 검사 통과
open_helper('/other/path', 'typo')  # 타입 검사기 오류

Literal[...]은 서브 클래싱 될 수 없습니다. 실행 시간에는, 임의의 값이 Literal[...]에 대한 형 인자로 허용되지만, 형 검사기는 제한을 부과할 수 있습니다. 리터럴 형에 대한 자세한 내용은 PEP 586을 참조하십시오.

추가 세부 사항:

  • 인자는 리터럴 값이어야 하며 적어도 하나 있어야 합니다.

  • 중첩된 Literal 타입은 평탄화됩니다. 예를 들면:

    assert Literal[Literal[1, 2], 3] == Literal[1, 2, 3]

    하지만 이는 타입 별칭을 통해 참조되는 Literal 타입에는 적용되지 않습니다. 기본이 되는 :class:`TypeAliasType`의 평가를 강제하는 것을 피하기 위함입니다:

    type A = Literal[1, 2]
assert Literal[A, 3] != Literal[1, 2, 3]

  • 중복 인자는 건너뜁니다. 예를 들어:

    assert Literal[1, 2, 1] == Literal[1, 2]

  • 리터럴을 비교할 때 인자 순서는 무시됩니다. 예를 들면:

    assert Literal[1, 2] == Literal[2, 1]

  • Literal 은 서브클래싱하거나 인스턴스화할 수 없습니다.

  • Literal[X][Y] 를 작성할 수 없습니다.

Added in version 3.8.

버전 3.9.1에서 변경: Literal``는 이제 파라미터의 중복을 제거합니다. ``Literal 객체의 동등성 비교는 더 이상 순서와 무관합니다. Literal 객체는 이제 매개변수 중 하나라도 해시 가능 <hashable>`이 아니면 동등성 비교 중에 :exc:`TypeError 예외를 발생시킵니다.

typing.ClassVar¶

클래스 변수를 표시하기 위한 특수 형 구조물.

PEP 526에서 소개된 것처럼, ClassVar로 감싼 변수 어노테이션은 주어진 어트리뷰트가 클래스 변수로 사용되도록 의도되었으며 해당 클래스의 인스턴스에 설정되어서는 안 됨을 나타냅니다. 용법:

class Starship:
    stats: ClassVar[dict[str, int]] = {} # 클래스 변수
    damage: int = 10                     # 인스턴스 변수

ClassVar는 형만 받아들이며 더는 서브 스크립트 할 수 없습니다.

ClassVar is not a class itself, and cannot be used with isinstance() or issubclass(). ClassVar does not change Python runtime behavior, but it can be used by static type checkers. For example, a type checker might flag the following code as an error:

enterprise_d = Starship(3000)
enterprise_d.stats = {} # 오류: 클래스 변수를 인스턴스에 설정합니다.
Starship.stats = {}     # 이것은 괜찮습니다.

Added in version 3.5.3.

typing.Final¶

타입 검사기에게 최종 이름임을 나타내는 특별한 타입 구조물입니다.

Final 이름은 어떤 스코프에서도 재할당될 수 없습니다. 클래스 스코프에서 선언된 Final 이름은 서브 클래스에서 덮어쓸 수 없습니다.

예를 들면:

MAX_SIZE: Final = 9000
MAX_SIZE += 1  # 형 검사기에서 보고된 오류

class Connection:
    TIMEOUT: Final[int] = 10

class FastConnector(Connection):
    TIMEOUT = 1  # 형 검사기에서 보고된 오류

이러한 속성에 대한 실행 시간 검사는 없습니다. 자세한 내용은 PEP 591을 참조하십시오.

Added in version 3.8.

typing.Annotated¶

주석에 문맥별 메타데이터를 추가하기 위한 특수 타이핑 형식입니다.

어노테이션 Annotated[T, x] 를 사용하여 주어진 타입 T 에 메타데이터를 추가할 수 있습니다. Annotated 로 추가된 메타데이터는 정적 분석 도구나 실행 시간에서 사용할 수 있습니다. 실행 시간에는 이 메타데이터가 __metadata__ 속성에 저장됩니다.

라이브러리나 도구가 어노테이션 Annotated[T, x] 를 만났을 때 메타데이터에 대한 특별한 논리가 없으면, 해당 메타데이터를 무시하고 주석을 단순히 T 로 처리해야 합니다. 따라서 Annotated 는 파이썬의 정적 타입 시스템 외부 목적으로 어노테이션을 사용하고자 하는 코드에 유용할 수 있습니다.

Annotated[T, x] 를 주석으로 사용하는 것은 여전히 T 의 정적 타입 검사를 허용합니다. 왜냐하면 형 검사기는 메타데이터 x 를 단순히 무시할 것이기 때문입니다. 이런 방식으로, Annotated 는 타이핑 시스템 범위 외부에서 어노테이션 추가에 사용될 수 있지만 함수나 클래스에 대한 타입 검사를 완전히 비활성화하는 @no_type_check 데코레이터와 다릅니다.

메타데이터를 해석하는 것은 해당 Annotated 어노테이션을 만나는 도구나 라이브러리에 달려 있습니다. Annotated 타입을 만나는 도구나 라이브러리는 관심 대상인지 확인하기 위해 메타데이터 요소를 검사할 수 있습니다(예: isinstance() 사용).

Annotated[<type>, <metadata>]

범위 분석을 수행하는 경우, Annotated 를 사용하여 타입 어노테이션에 메타데이터를 추가하는 방법을 예로 보여드립니다.

@dataclass
class ValueRange:
    lo: int
    hi: int

T1 = Annotated[int, ValueRange(-10, 5)]
T2 = Annotated[T1, ValueRange(-20, 3)]

Annotated 의 첫 번째 인자는 유효한 타입이어야 합니다. Annotated 는 가변 인자를 지원하므로 여러 메타데이터 요소를 제공할 수 있습니다. 메타데이터 요소의 순서가 유지되며 동등성 검사에서 중요합니다:

@dataclass
class ctype:
     kind: str

a1 = Annotated[int, ValueRange(3, 10), ctype("char")]
a2 = Annotated[int, ctype("char"), ValueRange(3, 10)]

assert a1 != a2  # 순서가 중요합니다

어노테이션을 소비하는 도구의 책임에 따라 클라이언트가 하나의 어노테이션에 여러 메타데이터 요소를 추가할 수 있는지, 그리고 해당 어노테이션들을 어떻게 병합할지는 결정됩니다.

중첩된 Annotated 타입은 플랫하게 되어 있습니다. 메타데이터 요소의 순서는 내부의 주석부터 시작합니다:

assert Annotated[Annotated[int, ValueRange(3, 10)], ctype("char")] == Annotated[
    int, ValueRange(3, 10), ctype("char")
]

하지만, 이는 근본적인 TypeAliasType`의 평가를 강제하는 것을 방지하기 위해 타입 별칭을 통해 참조되는 ``Annotated` 타입에는 적용되지 않습니다.

type From3To10[T] = Annotated[T, ValueRange(3, 10)]
assert Annotated[From3To10[int], ctype("char")] != Annotated[
   int, ValueRange(3, 10), ctype("char")
]

중복된 메타데이터 요소는 제거되지 않습니다:

assert Annotated[int, ValueRange(3, 10)] != Annotated[
    int, ValueRange(3, 10), ValueRange(3, 10)
]

Annotated 는 중첩 및 제네릭 별칭과 함께 사용될 수 있습니다:

@dataclass
class MaxLen:
    value: int

type Vec[T] = Annotated[list[tuple[T, T]], MaxLen(10)]

# 타입 어노테이션에서 사용될 때도 형 검사기는 "V"를 다음과 동일하게 취급합니다.
# ``Annotated[list[tuple[int, int]], MaxLen(10)]``:
type V = Vec[int]

Annotated 는 언패킹된 TypeVarTuple 와 함께 사용할 수 없습니다:

type Variadic[*Ts] = Annotated[*Ts, Ann1] = Annotated[T1, T2, T3, ..., Ann1]  # NOT valid

where T1, T2, … are TypeVars. This is invalid as only one type should be passed to Annotated.

By default, get_type_hints() strips the metadata from annotations. Pass include_extras=True to have the metadata preserved:

>>> from typing import Annotated, get_type_hints
>>> def func(x: Annotated[int, "metadata"]) -> None: pass
...
>>> get_type_hints(func)
{'x': <class 'int'>, 'return': <class 'NoneType'>}
>>> get_type_hints(func, include_extras=True)
{'x': typing.Annotated[int, 'metadata'], 'return': <class 'NoneType'>}

실행 시간(runtime)에, Annotated 타입과 관련된 메타데이터는 __metadata__ 속성을 통해 검색할 수 있습니다.

>>> from typing import Annotated
>>> X = Annotated[int, "very", "important", "metadata"]
>>> X
typing.Annotated[int, 'very', 'important', 'metadata']
>>> X.__metadata__
('very', 'important', 'metadata')

만약 Annotated 로 래핑된 원래 타입을 검색하고 싶다면, __origin__ 속성을 사용하십시오.

>>> from typing import Annotated, get_origin
>>> Password = Annotated[str, "secret"]
>>> Password.__origin__
<class 'str'>

get_origin`을 사용하면 ``Annotated`() 자체가 반환됨에 유의하십시오:

>>> get_origin(Password)
typing.Annotated

typing.TypeForm¶

타입 표현식의 평가 결과로 나오는 값을 표현하는 특수 형식입니다.

이 값은 타입 표현식에 제공된 정보를 인코딩하며, 해당 타입 표현식이 설명하는 타입을 나타냅니다.

타입 표현식 내에서 TypeForm 은 일련의 타입 형식 객체들을 기술합니다. 단일 타입 인수를 받으며, 이는 유효한 타입 표현식이어야 합니다. TypeForm[T] 는 타입 T 또는 T 에 할당 가능한 모든 타입을 나타내는 타입 형식 객체들의 집합을 기술합니다.

TypeForm(obj) 는 단순히 obj 를 변경하지 않고 반환합니다. 이것은 정적 타입 검사기에게 값을 타입 형식으로 명시적으로 표시할 때 유용합니다.

예제:

from typing import Any, TypeForm

def cast[T](typ: TypeForm[T], value: Any) -> T: ...

reveal_type(cast(int, "x"))  # 공개된 타입은 "int"입니다.

자세한 내용은 :pep:`747`을 참조하십시오.

Added in version 3.15.

typing.TypeIs¶

사용자가 정의한 타입 술어 함수를 표시하기 위한 특수 타이핑 구조체입니다.

TypeIs 는 사용자가 정의한 타입 술어 함수의 반환 타입을 주석 처리하는 데 사용할 수 있습니다. TypeIs 는 단일 타입 인수만 허용합니다. 실행 시간(runtime)에 이 방식으로 표시된 함수는 불리언 값을 반환하고 적어도 하나의 위치 인수를 받아야 합니다.

TypeIs 는 타입 좁히기 (type narrowing)에 도움을 주는 것을 목표로 합니다. 타입 좁히기는 정적 타입 검사기가 프로그램 코드 흐름 내에서 표현식의 더 정확한 타입을 결정하는 데 사용하는 기술입니다. 일반적으로 조건부 코드 흐름을 분석하고 해당 결과를 코드 블록에 적용하여 타입 좁히기를 수행합니다. 여기서 조건부 표현식은 때때로 “타입 술어”라고 불립니다:

def is_str(val: str | float):
    # "isinstance" 타입 술어
    if isinstance(val, str):
        # ``val``의 타입은 ``str``로 좁혀집니다.
        ...
    else:
        # 그렇지 않으면, ``val``의 타입은 ``float``으로 좁혀집니다.
        ...

Sometimes it would be convenient to use a user-defined boolean function as a type predicate. Such a function should use TypeIs[...] or TypeGuard as its return type to alert static type checkers to this intention. TypeIs usually has more intuitive behavior than TypeGuard, but it cannot be used when the input and output types are incompatible (e.g., list[object] to list[int]) or when the function does not return True for all instances of the narrowed type.

`-> TypeIs[NarrowedType]`을 사용하면 정적 타입 검사기에게 주어진 함수가 다음과 같다는 것을 알려줍니다:

  1. 반환 값은 불리언입니다.

  2. 반환 값이 True 이면, 그 인수의 타입은 인수 원래 타입과 NarrowedType 의 교집합(intersection)이 됩니다.

  3. 반환 값이 False 이면, 그 인수의 타입은 NarrowedType 을 제외하도록 좁혀집니다.

예를 들면:

from typing import assert_type, final, TypeIs

class Parent: pass
class Child(Parent): pass
@final
class Unrelated: pass

def is_parent(val: object) -> TypeIs[Parent]:
    return isinstance(val, Parent)

def run(arg: Child | Unrelated):
    if is_parent(arg):
        # ``arg``의 타입은 ``Parent``와 ``Child``의 교집합으로 좁혀지며,
        # 이는 ``Child``와 동등합니다.
        assert_type(arg, Child)
    else:
        # ``Parent``를 제외하도록 ``arg``의 타입이 좁혀져,
        # ``Unrelated``만 남게 됩니다.
        assert_type(arg, Unrelated)

TypeIs 내부의 타입은 함수 인수의 타입과 일관성이 있어야 합니다. 그렇지 않으면 정적 타입 검사기가 오류를 발생시킵니다. 잘못 작성된 TypeIs 함수는 타입 시스템에 불안정한 동작을 초래할 수 있으며, 이러한 함수를 타입 안전 방식으로 작성하는 것은 사용자에게 책임이 있습니다.

만약 TypeIs 함수가 클래스 또는 인스턴스 메서드인 경우, TypeIs 의 타입은 두 번째 매개변수(cls 또는 self 이후)의 타입과 매핑됩니다.

요약하자면, def foo(arg: TypeA) -> TypeIs[TypeB]: ... 형태는 foo(arg) 가 True 를 반환하면 그리는 arg 가 TypeB 의 인스턴스이며, False 를 반환하면 TypeB 의 인스턴스가 아님을 의미합니다.

TypeIs 는 타입 변수와도 함께 작동합니다. 더 자세한 내용은 PEP 742 (TypeIs 를 이용한 타입 축소)를 참조하십시오.

Added in version 3.13.

typing.TypeGuard¶

사용자가 정의한 타입 술어 함수를 표시하기 위한 특수 타이핑 구조체입니다.

타입 술어 함수(Type predicate functions)는 인자가 특정 타입의 인스턴스인지를 반환하는 사용자 정의 함수입니다. TypeGuard 는 TypeIs 와 유사하게 작동하지만, 타입 검사 동작에 미묘하게 다른 영향을 주므로 (아래 참조) 주의가 필요합니다.

-> TypeGuard 를 사용하면 정적 타입 검사기에 주어진 함수에 대해 다음과 같다고 알려줍니다:

  1. 반환 값은 불리언입니다.

  2. 반환 값이 True``이면, 그 인자의 타입은 ``TypeGuard 안에 있는 타입입니다.

TypeGuard 역시 타입 변수와 함께 작동합니다. 더 자세한 내용은 :pep:`647`을 참조하십시오.

예를 들면:

def is_str_list(val: list[object]):
    '''리스트의 모든 객체가 문자열인지 판단합니다'''
    return all(isinstance(x, str) for x in val)

def func1(val: list[object]):
    if is_str_list(val):
        # val의 타입이 ``list[str]``로 축소됩니다.
        print(" ".join(val))
    else:
        # val의 타입은 ``list[object]``로 유지됩니다.
        print("문자열 리스트가 아닙니다!")

TypeIs 와 TypeGuard 는 다음 측면에서 다릅니다:

  • TypeIs 는 축소된 타입이 입력 타입의 서브타입(subtype)이어야 하는 반면, TypeGuard 는 그렇지 않습니다. 주요 이유는 list 가 불변성이기 때문에 후자가 전자의 서브타입은 아닐지라도 list[object] 를 list[str] 로 축소하는 등의 상황을 허용하기 위함입니다.

  • 만약 TypeGuard 함수가 True``를 반환하면, 타입 검사기는 변수의 타입을 정확히 ``TypeGuard 타입으로 축소합니다. 만약 TypeIs 함수가 True``를 반환하면, 타입 검사기는 이전에 알려진 변수 타입과 ``TypeIs 타입을 결합하여 더 정확한 타입을 추론할 수 있습니다. (기술적으로 이는 교집합 타입으로 알려져 있습니다.)

  • 만약 TypeGuard 함수가 False``를 반환하면, 타입 검사기는 변수의 타입을 전혀 축소할 수 없습니다. 만약 ``TypeIs 함수가 False``를 반환하면, 타입 검사기는 변수의 타입을 ``TypeIs 타입을 제외하도록 축소할 수 있습니다.

Added in version 3.10.

typing.Unpack¶

객체에 언패킹되었음을 개념적으로 표시하는 타입 힌트 연산자입니다.

예를 들어, 타입 변수 튜플 에 언패킹 연산자 * 을 사용하는 것은 해당 타입 변수 튜플을 언패킹된 것으로 표시하기 위해 Unpack 을 사용하는 것과 동일합니다:

Ts = TypeVarTuple('Ts')
tup: tuple[*Ts]
# 사실상 다음 동작 수행:
tup: tuple[Unpack[Ts]]

사실 Unpack 은 typing.TypeVarTuple 및 builtins.tuple 타입의 컨텍스트에서 *``과 상호 교환적으로 사용할 수 있습니다. ``* `이 특정 위치에서 사용될 수 없었던 이전 버전의 Python에서는 ``Unpack` 을 명시적으로 사용하는 것을 볼 수도 있습니다:

# 이전 버전의 Python에서는 TypeVarTuple과 Unpack이
# `typing_extensions` 백포트 패키지에 위치합니다.
from typing_extensions import TypeVarTuple, Unpack

Ts = TypeVarTuple('Ts')
tup: tuple[*Ts]         # Python <= 3.10에서 구문 오류!
tup: tuple[Unpack[Ts]]  # 의미론적으로 동등하며, 후방 호환성이 있습니다.

Unpack 은 함수 시그니처에서 **kwargs 를 타입 지정할 때 typing.TypedDict 와 함께 사용할 수도 있습니다:

from typing import TypedDict, Unpack

class Movie(TypedDict):
    name: str
    year: int

# 이 함수는 두 개의 키워드 인자(argument)인 타입이 `str`인 `name`과, 타입이 `int`인 `year``을 기대합니다.
def foo(**kwargs: Unpack[Movie]): ...

**kwargs 타입을 위해 Unpack 사용에 대한 더 자세한 내용은 :pep:`692`를 참조하십시오.

Added in version 3.11.

제네릭 타입과 타입 별칭 생성하기¶

다음 클래스는 어노테이션으로 직접 사용해서는 안 됩니다. 이들의 의도된 목적은 제네릭 타입과 타입 별칭을 생성하는 빌딩 블록이 되는 것입니다.

이 객체들은 특별 구문 (타입 매개변수 목록 <type-params>`와 :keyword:`type 문)을 통해 생성될 수 있습니다. Python 3.11 이전 버전과의 호환성을 위해, 아래 문서에서 설명하듯이 전용 구문 없이도 생성될 수 있습니다.

class typing.Generic¶

제네릭 형을 위한 추상 베이스 클래스.

제네릭 타입은 일반적으로 클래스 이름 뒤에 타입 매개변수 목록을 추가하여 선언됩니다:

class Mapping[KT, VT]:
    def __getitem__(self, key: KT) -> VT:
        ...
        # 기타 코드 내용

그러한 클래스는 Generic 으로부터 암묵적으로 상속 받습니다. 이 구문의 런타임 의미론은 Language Reference 에서 논의합니다.

이 클래스는 다음과 같이 사용할 수 있습니다:

def lookup_name[X, Y](mapping: Mapping[X, Y], key: X, default: Y) -> Y:
    try:
        return mapping[key]
    except KeyError:
        return default

여기서 함수 이름 뒤의 대괄호는 :ref:`generic function <generic-functions>`를 나타냅니다.

하위 호환성을 위해, 제네릭 클래스는 또한 Generic 으로부터 명시적으로 상속받아 선언할 수도 있습니다. 이 경우, 타입 매개변수는 별도로 선언되어야 합니다:

KT = TypeVar('KT')
VT = TypeVar('VT')

class Mapping(Generic[KT, VT]):
    def __getitem__(self, key: KT) -> VT:
        ...
        # 기타 코드 내용
class typing.TypeVar(name, *constraints, bound=None, covariant=False, contravariant=False, infer_variance=False, default=typing.NoDefault)¶

형 변수.

타입 변수를 구성하는 가장 선호되는 방법은 generic functions, 및 :ref:`generic type aliases <generic-type-aliases>`를 이용하는 것입니다:

class Sequence[T]:  # T는 TypeVar입니다.
    ...

이 구문은 바운디드(bounded) 및 제약된(constrained) 타입 변수를 생성하는 데에도 사용될 수 있습니다:

class StrSequence[S: str]:  # S는 `str` 상한을 가진 TypeVar입니다.;
    ...                     # S가 "str에 의해 바운드되었다"고 말할 수 있습니다.


class StrOrBytesSequence[A: (str, bytes)]:  # A는 str 또는 bytes로 제약된 TypeVar입니다.
    ...

하지만 원하는 경우, 재사용 가능한 타입 변수는 다음과 같이 수동으로 구성할 수도 있습니다:

T = TypeVar('T')  # 무엇이든 될 수 있습니다.
S = TypeVar('S', bound=str)  # str의 모든 서브타입이 될 수 있습니다.
A = TypeVar('A', str, bytes)  # 반드시 str 또는 bytes여야 합니다.

타입 변수는 주로 정적 타입 검사기(static type checker)의 이점을 위해 존재합니다. 이는 제네릭 유형뿐만 아니라 제네릭 함수 및 타입 별칭 정의에 대한 매개변수 역할을 합니다. 제네릭 유형에 대한 더 자세한 정보는 :class:`Generic`을 참조하십시오. 제네릭 함수는 다음과 같이 작동합니다:

def repeat[T](x: T, n: int) -> Sequence[T]:
    """n개의 x를 포함하는 리스트를 반환합니다."""
    return [x]*n


def print_capitalized[S: str](x: S) -> S:
    """x를 대문자로 출력하고 x를 반환합니다."""
    print(x.capitalize())
    return x


def concatenate[A: (str, bytes)](x: A, y: A) -> A:
    """두 문자열 또는 바이트 객체를 합칩니다."""
    return x + y

참고로 타입 변수는 바운디드 하거나, 제약 되거나 둘 중 어느 것도 아니지만, 둘 다 바운디드하고 제약될 수는 없습니다.

타입 변수의 분산은 type parameter syntax <type-params>`를 통해 생성되거나 ``infer_variance=True``가 전달될 때 타입 검사기에 의해 추론됩니다. 수동으로 생성된 타입 변수는 ``covariant=True``나 ``contravariant=True``를 전달하여 명시적으로 공변적 또는 반변적으로 표시할 수 있습니다. 기본적으로, 수동으로 생성된 타입 변수는 불변(invariant)입니다. 더 자세한 내용은 :pep:`484 및 :pep:`695`를 참조하십시오.

바운디드 타입 변수와 제약된 타입 변수는 몇 가지 중요한 측면에서 다른 의미론을 가집니다. 바운디드 타입 변수를 사용한다는 것은 TypeVar 가 가능한 가장 구체적인 타입을 사용하여 해결된다는 것을 의미합니다:

x = print_capitalized('a string')
reveal_type(x)  # 밝혀진 타입은 str입니다.

class StringSubclass(str):
    pass

y = print_capitalized(StringSubclass('another string'))
reveal_type(y)  # 밝혀진 타입은 StringSubclass입니다.

z = print_capitalized(45)  # 오류: int는 str의 서브타입이 아닙니다.

타입 변수의 상한은 구체적인 타입, 추상 타입(ABC 또는 Protocol), 또는 심지어 타입들의 합집합일 수 있습니다:

# __abs__ 메서드를 가진 무엇이든 될 수 있습니다.
def print_abs[T: SupportsAbs](arg: T) -> None:
    print("절댓값:", abs(arg))

U = TypeVar('U', bound=str|bytes)  # str|bytes 합집합의 모든 서브타입이 될 수 있습니다.
V = TypeVar('V', bound=SupportsAbs)  # __abs__ 메서드를 가진 무엇이든 될 수 있습니다.

반면에 제약된 타입 변수를 사용한다는 것은 TypeVar 가 주어진 제약 조건 중 정확히 하나로만 해결될 수 있다는 것을 의미합니다:

a = concatenate('one', 'two')
reveal_type(a)  # 밝혀진 타입은 str입니다.

b = concatenate(StringSubclass('one'), StringSubclass('two'))
reveal_type(b)  # StringSubclass가 전달되었음에도 불구하고 밝혀진 타입은 str입니다.

c = concatenate('one', b'two')  # 오류: 함수 호출에서 타입 변수 'A'는 str일 수도 있고 bytes일 수도 있지만, 둘 다 될 수는 없습니다.

실행 시간에, isinstance(x, T)\는 TypeError\를 발생시킵니다.

class typing.TypeVarTuple(name, *, bound=None, covariant=False, contravariant=False, infer_variance=False, default=typing.NoDefault)¶

유형 변수 튜플입니다. 가변적 제네릭을 활성화하는 특화된 type variable 형태입니다.

유형 변수 튜플은 단일 별표(<code>*</code>)를 이름 앞에 사용하여 :ref:`type parameter lists <type-params>`에 선언할 수 있습니다:

def move_first_element_to_last[T, *Ts](tup: tuple[T, *Ts]) -> tuple[*Ts, T]:
    return (*tup[1:], tup[0])

또는 TypeVarTuple 생성자를 명시적으로 호출하여 할 수도 있습니다:

T = TypeVar("T")
Ts = TypeVarTuple("Ts")

def move_first_element_to_last(tup: tuple[T, *Ts]) -> tuple[*Ts, T]:
    return (*tup[1:], tup[0])

일반적인 유형 변수는 단일 유형으로 매개변수화할 수 있습니다. 반면, 유형 변수 튜플은 튜플로 묶인 임의 개수의 유형을 사용하여 임의의 수의 유형으로 매개변수화할 수 있습니다. 예를 들어:

# T는 int에 바인딩되고, Ts는 ()에 바인딩됩니다.
# 반환 값은 type tuple[int]을 가지는 (1,)입니다.
move_first_element_to_last(tup=(1,))

# T는 int에 바인딩되고, Ts는 (str,)에 바인딩됩니다.
# 반환 값은 type tuple[str, int]을 가지는 ('spam', 1)입니다.
move_first_element_to_last(tup=(1, 'spam'))

# T는 int에 바인딩되고, Ts는 (str, float)에 바인딩됩니다.
# 반환 값은 type tuple[str, float, int]을 가지는 ('spam', 3.0, 1)입니다.
move_first_element_to_last(tup=(1, 'spam', 3.0))

# 이 코드는 타입 검사에 실패합니다 (실행 시간에도 실패함).
# because tuple[()] is not compatible with tuple[T, *Ts]
# (at least one element is required)
move_first_element_to_last(tup=())

참고로 파라미터 언패킹 연산자 * 가 tuple[T, *Ts] 에서 사용되는 점에 유의하십시오. 개념적으로, Ts 는 형식 변수들의 튜플 (T1, T2, ...) 로 생각할 수 있습니다. 그러면 tuple[T, *Ts] 는 tuple[T, *(T1, T2, ...)] 가 되며, 이는 tuple[T, T1, T2, ...] 와 같습니다. (참고로 파이썬 구버전에서는 대신 Unpack 을 사용하여 작성할 수도 있었습니다.)

형 변수 튜플은 항상 언패킹되어야 합니다. 이렇게 해야 형 변수 튜플과 일반 형식 변수를 구별할 수 있습니다:

x: Ts          # 유효하지 않음
x: tuple[Ts]   # 유효하지 않음
x: tuple[*Ts]  # 올바른 방법입니다

형 변수 튜플은 일반 형식 변수가 사용되는 것과 동일한 컨텍스트에서 사용할 수 있습니다. 예를 들어, 클래스 정의, 인자 및 반환 유형 등에서 사용할 수 있습니다:

class Array[*Shape]:
    def __getitem__(self, key: tuple[*Shape]) -> float: ...
    def __abs__(self) -> "Array[*Shape]": ...
    def get_shape(self) -> tuple[*Shape]: ...

형 변수 튜플은 일반 형식 변수와 자유롭게 조합하여 사용할 수 있습니다:

class Array[DType, *Shape]:  # 이것은 괜찮습니다
    pass

class Array2[*Shape, DType]:  # 이것 역시 괜찮을 것입니다
    pass

class Height: ...
class Width: ...

float_array_1d: Array[float, Height] = Array()     # 완전히 괜찮습니다
int_array_2d: Array[int, Height, Width] = Array()  # 네, 이것도 괜찮습니다

하지만, 단일 타입 인자 목록이나 타입 매개 변수 목록에는 최대 하나의 형 변수 튜플만 나타날 수 있다는 점에 유의하십시오:

x: tuple[*Ts, *Ts]            # 유효하지 않음
class Array[*Shape, *Shape]:  # 유효하지 않음
    pass

마지막으로, 언패킹된 형식 변수 튜플은 *args 의 타입 어노테이션으로 사용될 수 있습니다:

def call_soon[*Ts](
    callback: Callable[[*Ts], None],
    *args: *Ts
) -> None:
    ...
    callback(*args)

*args 의 비언패킹된 어노테이션(예: *args: int)과는 달리, 이는 모든 인자가 int 임을 지정하는 반면, *args: *Ts 는 *args 에 전달되는 개별 인자의 타입을 참조할 수 있게 합니다. 여기서 이는 call_soon 에 전달된 *args 의 타입이 callback 의 (위치적) 인자들의 타입과 일치하는지 확인할 수 있도록 해줍니다.

형 변수 튜플에 대한 자세한 내용은 :pep:`646`을 참조하십시오.

class typing.ParamSpec(name, *, bound=None, covariant=False, contravariant=False, infer_variance=False, default=typing.NoDefault)¶

매개 변수 지정 형변수입니다. :ref:`형 변수 <typevar>`의 전문화된 버전입니다.

타입 매개 변수 목록 <type-params>`에서, 파라미터 지정은 두 개의 별표(``**`)로 선언될 수 있습니다:

type IntFunc[**P] = Callable[P, int]

Python 3.11 이전 버전과의 호환성을 위해, ParamSpec 객체는 다음과 같이 생성할 수도 있습니다:

P = ParamSpec('P')

매개 변수 사양 변수는 주로 정적 타입 검사기의 이점을 위해 존재합니다. 이는 한 호출 가능자의 매개 변수 형식을 다른 호출 가능자로 전달하는 데 사용되는 패턴으로, 일반적으로 고차 함수와 데코레이터에서 발견됩니다. 이들은 Concatenate 내에서만 유효하거나, Callable 의 첫 번째 인자 또는 사용자 정의 제네릭의 매개 변수로 사용될 때만 유효합니다. 제네릭 타입에 대한 자세한 내용은 Generic 을 참조하십시오.

예를 들어, 함수에 기본적인 로깅을 추가하려면, 함수 호출을 기록하는 add_logging 데코레이터를 만들 수 있습니다. 매개 변수 사양 변수는 데코레이터 내부로 전달되는 호출 가능자와 이로 인해 반환되는 새로운 호출 가능자가 상호 의존적인 타입 매개 변수를 가지고 있음을 타입 검사기에 알립니다:

from collections.abc import Callable
import logging

def add_logging[T, **P](f: Callable[P, T]) -> Callable[P, T]:
    '''함수에 로깅을 추가하는 타입 안전한 데코레이터.'''
    def inner(*args: P.args, **kwargs: P.kwargs) -> T:
        logging.info(f'{f.__name__}가 호출되었습니다')
        return f(*args, **kwargs)
    return inner

@add_logging
def add_two(x: float, y: float) -> float:
    '''두 숫자를 더합니다.'''
    return x + y

ParamSpec 없이는 이전에 주석을 달하는 가장 간단한 방법은 상한이 Callable[..., Any] 인 TypeVar 를 사용하는 것이었습니다. 하지만 이는 두 가지 문제를 야기합니다:

  1. The type checker can’t type check the inner function because *args and **kwargs have to be typed Any.

  2. add_logging 데코레이터 내부에서 inner 함수를 반환할 때 cast() 가 필요하거나, 정적 타입 검사기에 return inner 를 무시하도록 알려야 합니다.

kwargs¶

ParamSpec 은 위치적 및 키워드 매개 변수 모두를 캡처하기 때문에, P.args 와 P.kwargs 를 사용하여 ParamSpec 을 구성 요소로 분할할 수 있습니다. P.args 는 주어진 호출의 위치적 매개 변수 튜플을 나타내며 *args 에만 사용되어야 합니다. class typing.ParamSpecArgs¶
class typing.ParamSpecKwargs¶

Arguments and keyword arguments attributes of a ParamSpec. The P.args attribute of a ParamSpec is an instance of ParamSpecArgs, and P.kwargs is an instance of ParamSpecKwargs. They are intended for runtime introspection and have no special meaning to static type checkers.

이들 객체 중 어느 하나에 get_origin() 을 호출하면 원래의 ParamSpec 을 반환합니다:

>>> from typing import ParamSpec, get_origin
>>> P = ParamSpec("P")
>>> get_origin(P.args) is P
True
>>> get_origin(P.kwargs) is P
True

Added in version 3.10.

class typing.NamedTuple¶

형 지정된(typed) collections.namedtuple() 버전.

용법:

class Employee(NamedTuple):
    name: str
    id: int

이것은 다음과 동등합니다:

Employee = collections.namedtuple('Employee', ['name', 'id'])

필드에 기본값을 부여하려면, 클래스 바디에서 그 값을 대입할 수 있습니다:

class Employee(NamedTuple):
    name: str
    id: int = 3

employee = Employee('Guido')
assert employee.id == 3

기본값이 있는 필드는 기본값이 없는 모든 필드 뒤에 와야 합니다.

각 필드 이름에 대한 타입은 결과 클래스에서 annotationlib.get_annotations`를 호출하여 검색할 수 있습니다. (필드 이름은 ``_fields`() 어트리뷰트에, 기본값은 o _field_defaults 어트리뷰트에 포함되어 있으며, 둘 다 namedtuple() API의 일부입니다.)

NamedTuple 서브 클래스는 독스트링과 메서드도 가질 수 있습니다:

class Employee(NamedTuple):
    """직원을 나타냅니다."""
    name: str
    id: int = 3

    def __repr__(self) -> str:
        return f'<Employee {self.name}, id={self.id}>'

NamedTuple 서브 클래스는 제네릭할 수 있습니다:

class Group[T](NamedTuple):
    key: T
    group: list[T]

이전 버전과 호환되는 사용법:

# Python 3.11에서 일반화된 NamedTuple을 생성하는 방법
T = TypeVar("T")

class Group(NamedTuple, Generic[T]):
    key: T
    group: list[T]

# 함수형 구문도 지원됩니다.
Employee = NamedTuple('Employee', [('name', str), ('id', int)])

버전 3.6에서 변경: PEP 526 변수 어노테이션 문법 지원을 추가했습니다.

버전 3.6.1에서 변경: 기본값, 메서드 및 독스트링에 대한 지원을 추가했습니다.

버전 3.8에서 변경: _field_types와 __annotations__ 어트리뷰트는 이제 OrderedDict 인스턴스가 아닌 일반 딕셔너리입니다.

버전 3.9에서 변경: _field_types 어트리뷰트를 제거하고, 같은 정보를 가지는 더 표준적인 __annotations__ 어트리뷰트로 대체했습니다.

버전 3.9에서 변경: NamedTuple 은 이제 클래스라기보다는 함수입니다. 여전히 위에서 설명한 것처럼 클래스 베이스로 사용될 수 있습니다.

class typing.Protocol(Generic)¶

프로토콜 클래스의 기본 클래스입니다.

프로토콜 클래스는 다음과 같이 정의됩니다:

class Proto(Protocol):
    def meth(self) -> int:
        ...

이러한 클래스는 주로 구조적 서브 타이핑(정적 덕 타이핑)을 인식하는 정적 형 검사기와 함께 사용됩니다, 예를 들어:

class C:
    def meth(self) -> int:
        return 0

def func(x: Proto) -> int:
    return x.meth()

func(C())  # 정적 타입 검사를 통과합니다

자세한 내용은 PEP 544 를 참조하십시오. @runtime_checkable 으로 데코레이션된 프로토콜 클래스(나중에 설명됨)는 주어진 어트리뷰트의 존재 여부만 확인하는 간단한 런타임 프로토콜 역할을 하며, 타입 시그니처는 무시합니다. 이 데코레이터가 없는 프로토콜 클래스는 isinstance() 또는 issubclass() 의 두 번째 인수로 사용될 수 없습니다.

프로토콜 클래스는 제네릭일 수 있습니다, 예를 들어:

class GenProto[T](Protocol):
    def meth(self) -> T:
        ...

Python 3.11 이전 버전과 호환되어야 하는 코드에서는 다음과 같이 일반화된 프로토콜을 작성할 수 있습니다:

T = TypeVar("T")

class GenProto(Protocol[T]):
    def meth(self) -> T:
        ...

Added in version 3.8.

버전 3.15에서 폐지되었고, 버전 3.20에서 제거됩니다: It is deprecated to call isinstance() and issubclass() checks on protocol classes that were not explicitly decorated with runtime_checkable() but that inherit from a runtime-checkable protocol class. This will throw a TypeError in Python 3.20.

@typing.runtime_checkable¶

프로토콜 클래스를 실행 시간 프로토콜로 표시합니다.

그러한 프로토콜은 isinstance()\와 issubclass()\를 통해 사용할 수 있습니다. 이것은 간단한 구조적 검사를 허용하며, collections.abc`에 있는 :class:`~collections.abc.Iterable 같은 “일거양장”과 매우 유사합니다. 예를 들어 다음과 같습니다:

@runtime_checkable
class Closable(Protocol):
    def close(self): ...

assert isinstance(open('/some/file'), Closable)

@runtime_checkable
class Named(Protocol):
    name: str

import threading
assert isinstance(threading.Thread(name='Bob'), Named)

프로토콜의 런타임 가역성은 상속되지 않습니다. 런타임에서 검사 가능한 프로토콜의 서브클래스는 클래스 계층 구조와 관계없이 명시적으로 표시된 경우에만 런타임에서 검사 가능합니다:

@runtime_checkable
class Iterable(Protocol):
    def __iter__(self): ...

# @runtime_checkable이 없으면, Reversible은 더 이상 런타임에서 검사 가능하지 않습니다.
@runtime_checkable
class Reversible(Iterable, Protocol):
    def __reversed__(self): ...

이 데코레이터는 프로토콜이 아닌 클래스에 적용될 때 :exc:`TypeError`를 발생시킵니다:

참고

@runtime_checkable will check only the presence of the required methods or attributes, not their type signatures or types. For example, ssl.SSLObject is a class, therefore it passes an issubclass() check against Callable. However, the ssl.SSLObject.__init__ method exists only to raise a TypeError with a more informative message, therefore making it impossible to call (instantiate) ssl.SSLObject.

참고

런타임에서 검사 가능한 프로토콜에 대한 isinstance() 검사는 비프로토콜 클래스를 대상으로 하는 isinstance() 검사에 비해 놀라울 정도로 느릴 수 있습니다. 성능에 민감한 코드에서는 구조적 검사를 위해 hasattr() 호출과 같은 대체 관용구 사용을 고려하십시오:

class typing.TypedDict(dict)¶

딕셔너리에 형 힌트를 추가하는 특수 구조입니다. 실행 시간에는 “TypedDict 인스턴스”는 단순히 :class:`dicts <dict>`입니다:

TypedDict는 모든 인스턴스가 각 키가 일관된 형의 값에 연관되는, 특정한 키 집합을 갖도록 기대되는 딕셔너리 형을 선언합니다. 이 기대는 실행 시간에는 검사되지 않고, 형 검사기에서만 강제됩니다. 사용법:

class Point2D(TypedDict):
    x: int
    y: int
    label: str

a: Point2D = {'x': 1, 'y': 2, 'label': 'good'}  # OK
b: Point2D = {'z': 3, 'label': 'bad'}           # 타입 검사 실패

assert Point2D(x=1, y=2, label='first') == dict(x=1, y=2, label='first')

TypedDict 를 생성하는 또 다른 방법은 함수 호출 구문을 사용하는 것입니다. 두 번째 인자는 리터럴 dict 여야 합니다:

Point2D = TypedDict('Point2D', {'x': int, 'y': int, 'label': str})

이 기능적 구문은 키가 유효한 :ref:`identifier <identifiers>`가 아닌 경우 (예를 들어 예약어이거나 하이픈을 포함하는 경우) 또는 키 이름이 일반적인 비공개 이름처럼 :ref:`mangled <private-name-mangling>`되어서는 안 되는 경우에 정의할 수 있게 해줍니다:

# SyntaxError를 발생시킴
class Point2D(TypedDict):
    in: int  # 'in'은 예약어임
    x-y: int  # 하이픈이 포함된 이름

class Definition(TypedDict):
    __schema: str  # `_Definition__schema`로 변경됨 (mangled)

# OK, 기능적 구문 사용
Point2D = TypedDict('Point2D', {'in': int, 'x-y': int})
Definition = TypedDict('Definition', {'__schema': str})  # 변경되지 않음

기본적으로 모든 키는 TypedDict 에 존재해야 합니다. NotRequired 를 사용하여 개별 키가 필수 요소가 아님을 표시할 수 있습니다:

class Point2D(TypedDict):
    x: int
    y: int
    label: NotRequired[str]

# 대체 구문 사용
Point2D = TypedDict('Point2D', {'x': int, 'y': int, 'label': NotRequired[str]})

이것은 Point2D TypedDict``에 ``label 키가 누락될 수 있음을 의미합니다.

또한 total 을 False 로 지정하여 모든 키를 기본적으로 필수 항목이 아닐 수 있도록 표시하는 것도 가능합니다:

class Point2D(TypedDict, total=False):
    x: int
    y: int

# 대체 구문
Point2D = TypedDict('Point2D', {'x': int, 'y': int}, total=False)

이것은 Point2D TypedDict 에 어떤 키가 누락될 수 있음을 의미합니다. 타입 검사기는 total 인수의 값으로 리터럴 False 또는 True 만 지원하는 것으로 예상됩니다. 기본값은 True 이며, 클래스 본문에 정의된 모든 항목을 필수로 만듭니다.

total=False 인 TypedDict 의 개별 키는 Required 를 사용하여 필수 항목으로 표시할 수 있습니다:

class Point2D(TypedDict, total=False):
    x: Required[int]
    y: Required[int]
    label: str

# 대체 구문
Point2D = TypedDict('Point2D', {
    'x': Required[int],
    'y': Required[int],
    'label': str
}, total=False)

기본 클래스 기반 구문을 사용하여 하나의 또는 여러 다른 TypedDict 타입을 상속받는 것이 가능합니다. 사용법:

class Point3D(Point2D):
    z: int

Point3D``는 세 개의 항목을 가집니다: ``x, y 및 z. 이는 다음 정의와 같습니다:

class Point3D(TypedDict):
    x: int
    y: int
    z: int

기본적으로, TypedDict 는 열려 있는 상태입니다. 즉, 클래스 본문에 정의된 것 외의 추가 키를 런타임에 포함할 수 있습니다. closed 클래스 인자를 사용하여 이를 제어할 수 있습니다. 만약 closed=True 이면, TypedDict 는 추가 키를 포함할 수 없습니다.

class ClosedPoint(TypedDict, closed=True):
    x: int
    y: int

class ClosedPoint3D(ClosedPoint):  # 타입 검사기 오류: 닫힌 TypedDict에 키를 추가할 수 없음
    z: int

closed=False 로 설정하는 것은 기본 열린 동작을 명시적으로 요청합니다. 이 인수가 전달되지 않으면, 이 상태는 부모 클래스로부터 상속됩니다.

열림 또는 닫힘 외에도, TypedDict 는 추가 항목을 갖도록 구성할 수 있습니다. extra_items 클래스 인자가 타입을 지정하는 경우, TypedDict 는 임의의 추가 키를 포함할 수 있지만, 해당 키들의 값은 지정된 타입이어야 합니다.

class ExtraItemsPoint(TypedDict, extra_items=int):
    x: int
    y: int

point: ExtraItemsPoint = {'x': 1, 'y': 2, 'anything': 3}  # OK

extra_items 인자도 서브클래싱을 통해 상속됩니다. 기본적으로 설정되지 않으며 closed 인자와 함께 사용할 수 없습니다.

TypedDict``는 :class:`Generic`의 경우를 제외하고는 비-``TypedDict 클래스를 상속할 수 없습니다. 예를 들어:

class X(TypedDict):
    x: int

class Y(TypedDict):
    y: int

class Z(object): pass  # 비-TypedDict 클래스

class XY(X, Y): pass  # OK

class XZ(X, Z): pass  # TypeError 발생

TypedDict 는 제네릭할 수 있습니다:

class Group[T](TypedDict):
    key: T
    group: list[T]

Python 3.11 이하 버전과 호환되는 제네릭 TypedDict 를 생성하려면, Generic 으로부터 명시적으로 상속받아야 합니다:

T = TypeVar("T")

class Group(TypedDict, Generic[T]):
    key: T
    group: list[T]

__total__¶

Point2D.__total__ 은 total 인수의 값을 제공합니다. 예시:

>>> from typing import TypedDict
>>> class Point2D(TypedDict): pass
>>> Point2D.__total__
True
>>> class Point2D(TypedDict, total=False): pass
>>> Point2D.__total__
False
>>> class Point3D(Point2D): pass
>>> Point3D.__total__
True

이 속성은 현재 TypedDict 클래스에 대한 total 인수 값 만 반영하며, 클래스가 의미론적으로 완전한지 여부는 아닐 수 있습니다. 예를 들어, __total__ 가 True 로 설정된 TypedDict 는 NotRequired 로 표시되거나, 또는 total=False 를 가진 다른 TypedDict 로부터 상속을 받을 수 있습니다. 그러므로 검사를 위해서는 일반적으로 __required_keys__ 와 __optional_keys__ 를 사용하는 것이 더 좋습니다.

__optional_keys__¶

Point2D.__required_keys__ 및 Point2D.__optional_keys__ 는 각각 필수 키 및 비필수 키를 포함하는 frozenset 객체를 반환합니다.

Required 로 표시된 키는 항상 __required_keys__ 에 나타날 것이고, NotRequired 로 표시된 키는 항상 __optional_keys__ 에 나타납니다.

Python 3.10 이하 버전과의 하위 호환성을 위해, 상속을 사용하여 필수 및 비필수 키를 같은 TypedDict 에서 선언하는 것도 가능합니다. 이것은 total 인수에 대한 하나의 값으로 TypedDict 를 선언한 다음, 다른 total 값을 가진 또 다른 TypedDict 에서 이를 상속받음으로써 수행됩니다:

>>> class Point2D(TypedDict, total=False):
...     x: int
...     y: int
...
>>> class Point3D(Point2D):
...     z: int
...
>>> Point3D.__required_keys__ == frozenset({'z'})
True
>>> Point3D.__optional_keys__ == frozenset({'x', 'y'})
True

Added in version 3.9.

참고

만약 from __future__ import annotations 가 사용되거나 주석이 문자열로 제공되면, TypedDict 가 정의될 때 주석은 평가되지 않습니다. 따라서 __required_keys__ 와 __optional_keys__ 의 런타임 인트로스펙션이 제대로 작동하지 않거나 속성의 값이 부정확할 수 있습니다.

typing.assert_type(val, typ, /)¶

정적 타입 검사기에게 val 이 typ 이라는 유추된 타입을 가지고 있음을 확인하도록 요청합니다.

런타임에서는 아무것도 하지 않습니다: 인자의 실제 타입에 상관없이 첫 번째 인자를 변경되지 않은 채 반환하며, 검사나 부작용도 없습니다.

정적 타입 검사기가 assert_type() 호출을 만나면, 값이 명시된 타입과 다르면 오류를 발생시킵니다:

def greet(name: str) -> None:
    assert_type(name, str)  # OK, `name`의 유추된 타입은 `str`입니다
    assert_type(name, int)  # 타입 검사기 에러

이 함수는 타입 검사기가 스크립트에 대한 이해가 개발자의 의도와 일치하는지 확인하는 데 유용합니다:

def complex_function(arg: object):
    # 복잡한 타입 좁히기 논리를 수행하고,
    # 그 후에 추론된 타입이 `int`이기를 기대합니다.
    ...
    # 타입 검사기가 우리의 함수를 올바르게 이해하는지 테스트합니다
    assert_type(arg, int)

Added in version 3.11.

typing.assert_never(arg, /)¶

정적 타입 검사기에게 코드 라인이 도달할 수 없는(unreachable)지 확인하도록 요청합니다.

예제:

def int_or_str(arg: int | str) -> None:
    match arg:
        case int():
            print("It's an int")
        case str():
            print("It's a str")
        case _ as unreachable:
            assert_never(unreachable)

여기서는 주석이 타입 검사기가 마지막 cases가 절대 실행될 수 없음을 추론하도록 허용합니다. 왜냐하면 arg 는 int 이거나 str 이기 때문에, 두 옵션 모두 이전 케이스들로 다루어졌기 때문입니다.

만약 타입 검사기가 assert_never() 호출이 도달 가능한지 발견하면 오류를 발생시킵니다. 예를 들어, arg``의 타입 주석이 대신 ``int | str | float``였다면, 타입 검사기는 ``unreachable``가 :class:`float` 타입이라고 지적하는 오류를 발생시킵니다. ``assert_never 호출이 타입 검사를 통과하려면 전달된 인자의 유추된 타입은 가장 낮은 타입인 :data:`Never`여야 하며, 다른 어떤 것도 아니어야 합니다.

호출 시 예외가 발생하면 해당 예외를 발생시킵니다.

typing.reveal_type(obj, /)¶

정적 형 검사기가 표현식의 추론된 타입을 알도록 요청합니다.

정적형 검사기가 이 함수 호출을 만나면, 인자의 추론된 타입이 포함된 진단 메시지를 생성합니다. 예를 들어:

x: int = 1
reveal_type(x)  # 파악된 타입은 "builtins.int"입니다.

이것은 형 검사기가 특정 코드 조각을 어떻게 처리하는지 디버깅하고 싶을 때 유용합니다.

실행 시, 이 함수는 인자의 실행 시간을 지정하여 :data:`sys.stderr`에 출력하고 인자는 변경되지 않은 상태로 반환합니다 (호출을 표현식 내에서 사용할 수 있도록 함):

x = reveal_type(1)  # "실행 시간 타입은 int입니다" 출력
print(x)  # "1"이 출력됩니다.

실행시간 타입이 형 검사기에 의해 정적으로 추론된 타입과 다를 수 있다는 점에 유의하십시오 (더 구체적이거나 덜 구체적일 수 있습니다).

대부분의 형 검사기는 이름이 typing 에서 임포트되지 않은 경우에도 어디서나 reveal_type() 를 지원합니다. 하지만 이름을 typing 에서 임포트하는 것은 코드에 런타임 오류가 발생하지 않도록 보장하고 의도를 더 명확하게 전달할 수 있습니다.

Added in version 3.11.

@typing.dataclass_transform(*, eq_default=True, order_default=False, kw_only_default=False, frozen_default=False, field_specifiers=(), **kwargs)¶

객체가 :func:`dataclass <dataclasses.dataclass>`와 같은 동작을 제공한다고 표시하는 데코레이터입니다.

@dataclass_transform 은 클래스, 메타클래스 또는 자체가 데코레이터인 함수를 데코레이트하는 데 사용될 수 있습니다. @dataclass_transform() 의 존재는 정적 형 검사기에게 해당 데코레이트된 객체가 @dataclasses.dataclass_ 와 유사하게 클래스를 변환하는 런타임 “마법”을 수행한다는 것을 알려줍니다.

데코레이터 함수를 사용한 예:

@dataclass_transform()
def create_model[T](cls: type[T]) -> type[T]:
    ...
    return cls

@create_model
class CustomerModel:
    id: int
    name: str

베이스 클래스에서:

@dataclass_transform()
class ModelBase: ...

class CustomerModel(ModelBase):
    id: int
    name: str

메타클래스에서:

@dataclass_transform()
class ModelMeta(type): ...

class ModelBase(metaclass=ModelMeta): ...

class CustomerModel(ModelBase):
    id: int
    name: str

위에 정의된 CustomerModel 클래스는 형 검사기에 의해 @dataclasses.dataclass`로 생성된 클래스와 유사하게 처리됩니다. 예를 들어, 형 검사기는 이 클래스들이 ``id``와 ``name``을 받는 ``__init__` 메서드를 가지고 있다고 가정합니다.

데코레이트된 클래스, 메타클래스 또는 함수는 다음과 같은 부울 인자를 받을 수 있으며, 형 검사기는 이들이 @dataclasses.dataclass 데코레이터에서와 동일한 효과를 가진다고 가정합니다: init, eq, order, unsafe_hash, frozen, match_args, kw_only, 및 slots. 이 인자들의 값(True 또는 False)은 정적으로 평가 가능해야 합니다.

@dataclass_transform 데코레이터의 인수는 데코레이트된 클래스, 메타클래스 또는 함수의 기본 동작을 사용자 정의하는 데 사용될 수 있습니다:

매개변수:

  • eq_default (bool) – 호출자가 이 인자를 생략할 경우 eq 매개 변수가 True 로 간주되는지 여부를 나타냅니다. 기본값은 True 입니다.

  • order_default (bool) – 호출자가 이 인자를 생략할 경우 order 매개 변수가 True 로 간주되는지 여부를 나타냅니다. 기본값은 False 입니다.

  • kw_only_default (bool) – 호출자가 이 인자를 생략할 경우 kw_only 매개 변수가 True 로 간주되는지 여부를 나타냅니다. 기본값은 False 입니다.

  • frozen_default (bool) – 호출자가 이 인자를 생략할 경우 frozen 매개 변수가 True``로 간주되는지 여부를 나타냅니다. 기본값은 ``False. .. versionadded:: 3.12

  • field_specifiers (tuple[Callable[..., Any], ...]) – dataclasses.field() 와 유사하게 필드를 설명하는 지원 클래스 또는 함수의 정적 목록을 지정합니다. 기본값은 () 입니다.

  • **kwargs (Any) – 예상되는 향후 확장성을 허용하기 위해 임의의 다른 키워드 인자가 허용됩니다.

형 검사기는 필드 지정자에 대해 다음 선택적 매개 변수들을 인식합니다:

@typing.overload¶

오버로드 함수 및 메서드를 생성하기 위한 데코레이터입니다.

@overload 데코레이터는 여러 가지 다양한 인자형의 조합을 지원하는 함수와 메서드를 기술할 수 있도록 합니다. 일련의 @overload\로 데코레이트 된 정의에는 (같은 함수/메서드에 대해) 정확히 하나의 @overload\로 데코레이트 되지 않은 정의가 뒤따라야 합니다.

@overload\로 데코레이트 된 정의는 (같은 함수/메서드에 대해) @overload\로 데코레이트 되지 않은 정의에 의해 덮어 쓰이기 때문에 형 검사기만을 위한 것입니다. 한편, @overload\로 데코레이트 되지 않은 정의는 실행 시간에 사용되지만, 형 검사기는 무시해야 합니다. 실행 시간에, @overload\로 데코레이트 된 함수를 직접 호출하면 NotImplementedError 가 발생합니다.

공용체(union)나 형 변수를 사용하여 표현할 수 있는 것보다 더 정밀한 형을 제공하는 오버로드의 예:

@overload
def process(response: None) -> None:
    ...
@overload
def process(response: int) -> tuple[int, str]:
    ...
@overload
def process(response: bytes) -> str:
    ...
def process(response):
    ...  # 실제 구현은 여기에 작성합니다.

다른 타입 어노테이션과 비교하여 자세한 내용은 PEP 484\를 참조하십시오.

버전 3.11에서 변경: 오버로드된 함수는 이제 get_overloads()\를 사용하여 실행 시간에 검사할 수 있습니다.

typing.get_overloads(func)¶

func 의 오버로드 데코레이트 된 정의 시퀀스를 반환합니다.

func 는 오버로드된 함수의 구현을 위한 함수 객체입니다. 예를 들어, @overload \ 관련 설명서의 process 정의가 주어지면, get_overloads(process) 은 세 가지 정의된 오버로드에 대한 세 개의 함수 객체 시퀀스를 반환합니다. 오버로드가 없는 함수에 호출되면, get_overloads() 는 빈 시퀀스를 반환합니다.

get_overloads() 은 오버로드된 함수를 실행 시간에 검사하는 데 사용될 수 있습니다.

Added in version 3.11.

@typing.final¶

최종 메서드 및 최종 클래스를 나타내는 데코레이터입니다.

메서드를 @final 로 데코레이트하는 것은 형 검사기에게 해당 메서드가 서브클래스에서 재정의될 수 없음을 나타냅니다. 클래스를 @final 로 데코레이트하는 것은 그것이 서브클래스로 사용될 수 없다는 것을 나타냅니다.

예를 들면:

class Base:
    @final
    def done(self) -> None:
        ...
class Sub(Base):
    def done(self) -> None:  # 형 검사기에 의해 보고된 오류
        ...

@final
class Leaf:
    ...
class Other(Leaf):  # 형 검사기에 의해 보고된 오류
    ...

이러한 속성에 대한 실행 시간 검사는 없습니다. 자세한 내용은 PEP 591을 참조하십시오.

Added in version 3.8.

버전 3.11에서 변경: 해당 데코레이터는 이제 데코레이트 된 객체에 __final__ 속성을 True 로 설정하려고 시도합니다. 따라서, if getattr(obj, "__final__", False) 와 같은 검사가 실행 시간에 객체 obj 가 final로 표시되었는지 확인할 수 있습니다. 만약 데코레이트된 객체가 속성 설정을 지원하지 않으면, 예외를 발생시키지 않고 변경되지 않은 객체를 반환합니다.

@typing.no_type_check¶

어노테이션이 형 힌트가 아님을 나타내는 데코레이터.

This works as a class or function decorator. With a class, it applies recursively to all methods and classes defined in that class (but not to methods defined in its superclasses or subclasses). Type checkers will ignore all annotations in a function or class with this decorator.

@no_type_check 는 데코레이트 된 객체를 제자리에서 수정합니다.

@typing.override¶

서브클래스의 메서드가 상위 클래스의 메서드나 속성을 재정의할 의도가 있음을 나타내는 데코레이터입니다.

형 검사기는 @override\로 데코레이트 된 메서드가 실제로 아무것도 재정의하지 않는 경우 오류를 발생시켜야 합니다. 이는 기본 클래스가 변경되었을 때 자식 클래스에 해당하는 변경 사항이 없는 상태에서 발생할 수 있는 버그를 방지하는 데 도움이 됩니다.

예:

class Base:
    def log_status(self) -> None:
        ...

class Sub(Base):
    @override
    def log_status(self) -> None:  # OK: Base.log_status 재정의
        ...

    @override
    def done(self) -> None:  # 형 검사기가 보고하는 오류
        ...

이 속성에 대한 실행 시간 검사는 없습니다.

이 데코레이터는 데코레이션된 객체에 __override__ 어트리뷰트를 True 로 설정하려고 시도합니다. 따라서 런타임에 if getattr(obj, "__override__", False) 와 같은 검사를 사용하여 객체 obj 가 재정의로 표시되었는지 여부를 확인할 수 있습니다. 데코레이션된 객체가 어트리뷰트 설정을 지원하지 않는 경우, 예외를 발생시키지 않고 객체를 변경 없이 반환합니다.

자세한 내용은 PEP 698 를 참고하십시오.

Added in version 3.12.

@typing.disjoint_base¶

클래스를 분리된 베이스로 표시하는 데코레이터입니다.

형 검사기는 분리된 베이스 C 의 자식 클래스가 부모 또는 자식 클래스가 아닌 다른 분리된 베이스를 상속하는 것을 허용하지 않습니다.

예를 들면:

@disjoint_base
class Disjoint1: pass

@disjoint_base
class Disjoint2: pass

class Disjoint3(Disjoint1, Disjoint2): pass  # 형 검사기 오류

형 검사기는 분리된 베이스에 대한 지식을 사용하여 도달할 수 없는 코드를 감지하고 두 타입이 중복될 수 있는지 여부를 결정할 수 있습니다.

The corresponding runtime concept is a solid base (see Multiple inheritance). Classes that are solid bases at runtime can be marked with @disjoint_base in stub files. Users may also mark other classes as disjoint bases to indicate to type checkers that multiple inheritance with other disjoint bases should not be allowed.

견고한 베이스의 개념은 CPython 구현 세부 사항이며, 런타임에서 분리된 베이스인 표준 라이브러리 클래스의 정확한 집합은 파이썬의 향후 버전에 변경될 수 있습니다.

Added in version 3.15.

@typing.type_check_only¶

클래스 또는 함수를 런타임에 사용 불가능하도록 표시하는 데코레이터입니다.

이 데코레이터 자체는 실행 시간에 사용할 수 없습니다. 주로, 구현이 비공개 클래스의 인스턴스를 반환할 때, 형 스텁 파일에 정의된 클래스를 표시하기 위한 용도입니다:

@type_check_only
class Response:  # private 또는 런타임에서 사용 불가
    code: int
    def get_header(self, name: str) -> str: ...

def fetch_response() -> Response: ...

비공개 클래스의 인스턴스를 반환하는 것은 좋지 않음에 유의하십시오. 일반적으로 그러한 클래스를 공개로 만드는 것이 바람직합니다.

인트로스펙션 도우미¶

typing.get_type_hints(obj, globalns=None, localns=None, include_extras=False, *, format=Format.VALUE)¶

함수, 메서드, 모듈, 클래스 객체 또는 다른 호출 가능한 객체의 형 힌트를 포함하는 딕셔너리를 반환합니다.

이것은 종종 :func:`annotationlib.get_annotations`와 같지만, 이 함수는 어노테이션 딕셔너리에 다음과 같은 변경을 적용합니다:

  • 문자열 리터럴 또는 ForwardRef 객체로 인코딩된 전방 참조는 globalns, localns 및 (적용 가능한 경우) obj ‘의 type parameter 이름 공간에서 이를 평가하여 처리합니다. globalns 또는 localns 가 주어지지 않은 경우, 적절한 네임스페이스 딕셔너리가 obj 로부터 추론됩니다.

  • None 은 types.NoneType \로 대체됩니다.

  • @no_type_check 가 obj 에 적용된 경우, 빈 딕셔너리가 반환됩니다.

  • 만약 obj 가 클래스 C 인 경우, 함수는 C 의 베이스 클래스의 어노테이션과 C 자체의 어노테이션을 병합하는 딕셔너리를 반환합니다. 이는 C.__mro__ 을 탐색하여 각 베이스 클래스의 annotations 을 반복적으로 결합함으로써 수행됩니다. method resolution order 에서 더 일찍 나타나는 클래스의 어노테이션은 메서드 해결 순서에서 나중에 나타나는 클래스의 어노테이션보다 항상 우선합니다.

  • include_extras 가 True 로 설정되지 않는 한, 이 함수는 Annotated[T, ...], Required[T], NotRequired[T] 및 ReadOnly[T] 의 모든 발생을 T 으로 재귀적으로 대체합니다 (자세한 내용은 Annotated <br> 참조).

조심

이 함수는 어노테이션에 포함된 임의의 코드를 실행할 수 있습니다. 자세한 내용은 :ref:`annotationlib-security`<br>를 참조하십시오.

참고

Format.VALUE <annotationlib.Format.VALUE>`이 사용되고 *obj*의 어노테이션에 포함된 전방 참조 중 해결할 수 없는 이름이 있는 경우, :exc:`NameError 예외가 발생합니다. 예를 들어, 이는 if TYPE_CHECKING 아래 임포트된 이름일 때 발생할 수 있습니다. 더 일반적으로, 어노테이션에 유효하지 않은 Python 코드가 포함된 경우 모든 종류의 예외가 발생할 수 있습니다.

참고

버전 3.9에서 변경: include_extras 매개변수를 PEP 593 의 일부로 추가했습니다. 자세한 내용은 Annotated 문서를 참조하십시오.

typing.get_origin(tp)¶

타입의 비제네릭 버전을 가져옵니다. X[Y, Z, …] 형태의 타이핑 객체에 대해 `X`를 반환합니다.

만약 X 가 내장 타입 또는 collections 클래스의 타이핑 모듈 별칭이라면, 이는 원본 클래스로 정규화됩니다. 만약 X 가 ParamSpecArgs 나 ParamSpecKwargs 의 인스턴스라면, 기본이 되는 ParamSpec 을 반환합니다. 지원되지 않는 객체에 대해서는 None 을 반환하십시오.

예제

assert get_origin(str) is None
assert get_origin(Dict[str, int]) is dict
assert get_origin(Union[int, str]) is Union
assert get_origin(Annotated[str, "metadata"]) is Annotated
P = ParamSpec('P')
assert get_origin(P.args) is P
assert get_origin(P.kwargs) is P

Added in version 3.8.

typing.TYPE_CHECKING¶

정적 타입 검사기에 의해 True 로 가정되는 특수 상수입니다. 런타임에는 False 입니다.

임포트하는 데 비용이 많이 들고 타이핑 어노테이션에 사용되는 타입만 포함하는 모듈은 if TYPE_CHECKING: 블록 내에서 안전하게 가져올 수 있습니다. 이는 런타임에 해당 모듈이 실제로 가져와지는 것을 방지합니다. 어노테이션은 지연 평가되지 않으므로(참조할 내용은 PEP 649), 따라서 나중에 검사하지 않는 한 어노테이션에 정의되지 않은 심볼을 사용하는 것은 무해합니다. 사용자의 정적 타입 분석 도구는 정적 타입 분석 중에 TYPE_CHECKING 을 True 로 설정하므로, 해당 분석 동안 모듈이 가져와지고 타입이 올바르게 검사됩니다.

용법:

if TYPE_CHECKING:
    import expensive_mod

def fun(arg: expensive_mod.SomeType) -> None:
    local_var: expensive_mod.AnotherType = other_fun()

정확히 정의되지 않은 심볼을 포함할 수 있는 타입 어노테이션을 런타임에 검사해야 하는 경우가 있다면, NameError 를 발생시키지 않고 해당 어노테이션을 안전하게 검색하기 위해 format 파라미터를 annotationlib.Format.STRING 또는 annotationlib.Format.FORWARDREF 로 사용하여 annotationlib.get_annotations() 메서드를 사용하십시오.

Added in version 3.5.2.

폐지된 에일리어스¶

이 모듈은 기존 표준 라이브러리 클래스의 여러 폐지된 에일리어스를 정의합니다. 이들은 원래 [] 를 사용하여 제네릭 클래스를 매개변수화하기 위해 typing 모듈에 포함되었습니다. 하지만, 해당 클래스들이 [] 지원을 하도록 개선되면서 (참고: PEP 585) 파이썬 3.9부터 에일리어스가 중복되어 폐지되었습니다.

중복된 형은 파이썬 3.9부터 폐지되었지만, 인터프리터에서 폐지 경고가 발생하지 않습니다. 검사되는 프로그램이 파이썬 3.9 이상을 대상으로 할 경우 타입 체크기가 폐지된 형에 플래그를 지정할 것으로 예상됩니다.

만약 이 폐지된 에일리어스들을 제거하기로 결정된다면, 제거보다 최소 두 버전 전부터 인터프리터에서 폐지 경고가 발생할 것입니다. 이 에일리어스들은 최소 파이썬 3.14까지 typing 모듈에 폐지 경고 없이 유지되는 것이 보장됩니다.

타입 검사기에서는 확인하는 프로그램이 최소 파이썬 버전 3.9 이상을 대상으로 하는 경우, 해당 폐지된 형의 사용에 플래그를 지정할 것을 권장합니다.

class typing.ByteString(Sequence[int])¶

:class:`collections.abc.ByteString`으로 향하는 사용 중단된 별칭입니다.

런타임에 obj``가 :ref:`buffer protocol <bufferobjects>`를 구현하는지 테스트하려면 ``isinstance(obj, collections.abc.Buffer)``를 사용하십시오. 타입 주석에서 사용할 경우, :class:`~collections.abc.Buffer`를 사용하거나 코드가 지원하는 타입을 명시적으로 지정하는 유니언을 사용하십시오 (예: ``bytes | bytearray | memoryview).

ByteString`은 원래 :class:`bytes`와 :class:`bytearray 모두의 상위 유형 역할을 하는 추상 클래스로 의도되었습니다. 그러나 ABC에 메서드가 전혀 없었기 때문에, 객체가 ByteString`의 인스턴스라는 사실만으로 그 객체에 대해 유용한 정보를 얻는 것은 아니었습니다. :class:`memoryview`와 같은 다른 일반적인 버퍼 타입들도 (런타임에서든 정적 타입 검사기에서든) :class:!ByteString`의 서브타입으로 간주되지 않았습니다.

더 자세한 내용은 :pep:`PEP 688 <688#current-options>`를 참고하십시오.

버전 3.9에서 폐지되었고, 버전 3.17에서 제거됩니다.
