자유 스레딩에 대한 파이썬 지원¶

Starting with the 3.13 release, CPython has support for a build of Python called free threading where the global interpreter lock (GIL) is disabled. Free-threaded execution allows for full utilization of the available processing power by running threads in parallel on available CPU cores. While not all software will benefit from this automatically, programs designed with threading in mind will run faster on multi-core hardware.

Some third-party packages, in particular ones with an extension module, may not be ready for use in a free-threaded build, and will re-enable the GIL.

This document describes the implications of free threading for Python code. See Free 스레딩을 위한 C API 확장 지원 for information on how to write C extensions that support the free-threaded build.

PEP 703 – CPython에서 글로벌 인터프리터 록을 선택 사항으로 만드는 방법에 대한 자유 스레딩 Python 전반의 설명.

설치 방법¶

Python 3.13 부터, 공식 macOS 및 Windows 설치 프로그램은 선택적으로 자유 스레딩 Python 바이너리를 설치하는 것을 지원합니다. 설치 프로그램은 https://www.python.org/downloads/ 에서 사용할 수 있습니다.

다른 플랫폼에 대한 정보는 자유 스레딩 Python 설치를 위한 커뮤니티 유지보수 설치 가이드인 Installing a Free-Threaded Python <https://py-free-threading.github.io/installing-cpython/>\를 참조하십시오.

CPython을 소스에서 빌드할 때, 자유 스레딩 Python 인터프리터 빌드를 위해 --disable-gil 구성 옵션을 사용해야 합니다.

자유 스레딩 Python 식별하기¶

To check if the current interpreter supports free-threading, python -VV and sys.version contain “free-threading build”. The new sys._is_gil_enabled() function can be used to check whether the GIL is actually disabled in the running process.

The sysconfig.get_config_var("Py_GIL_DISABLED") configuration variable can be used to determine whether the build supports free threading. If the variable is set to 1, then the build supports free threading. This is the recommended mechanism for decisions related to the build configuration.

자유 스레딩 Python의 글로벌 인터프리터 록¶

Free-threaded builds of CPython support optionally running with the GIL enabled at runtime using the environment variable PYTHON_GIL or the command-line option -X gil.

또한, 명시적으로 자유 스레딩을 지원한다고 표시되지 않은 C-API 확장 모듈을 임포트할 때 GIL이 자동으로 활성화될 수도 있습니다. 이 경우 경고가 출력됩니다.

개별 패키지 문서 외에도, 다음 웹사이트들이 인기 패키지가 자유 스레딩을 지원하는 상태를 추적합니다:

  • https://py-free-threading.github.io/tracking/

  • https://hugovk.github.io/free-threaded-wheels/

스레드 안전성¶

The free-threaded build of CPython aims to provide similar thread-safety behavior at the Python level to the default GIL-enabled build. Built-in types like dict, list, and set use internal locks to protect against concurrent modifications in ways that behave similarly to the GIL. However, Python has not historically guaranteed specific behavior for concurrent modifications to these built-in types, so this should be treated as a description of the current implementation, not a guarantee of current or future behavior.

참고

가능하다면, 기본형 타입의 내부 락에 의존하기보다는 threading.Lock 또는 다른 동기화 프리미티브를 사용하는 것이 좋습니다.

알려진 제한 사항¶

이 섹션에서는 자유 스레딩 CPython 빌드의 알려진 제한 사항을 설명합니다.

불멸화¶

In the free-threaded build, some objects are immortal. Immortal objects are not deallocated and have reference counts that are never modified. This is done to avoid reference count contention that would prevent efficient multi-threaded scaling.

3.14 릴리스 기준, 불멸화는 다음으로 제한됩니다:

  • 코드 상수: 숫자 리터럴, 문자열 리터럴 및 다른 상수들로 구성된 튜플 리터럴.

  • Strings interned by sys.intern().

프레임 객체¶

It is not safe to access frame.f_locals from a frame object if that frame is currently executing in another thread, and doing so may crash the interpreter.

이터레이터¶

여러 스레드에서 동일한 이터레이터 객체에 동시에 접근하는 것은 일반적으로 스레드 안전하지 않으며, 스레드는 중복되거나 누락된 요소를 볼 수 있습니다.

단일 스레드 성능¶

자유 스레딩 빌드는 기본 GIL 활성화 빌드와 비교하여 파이썬 코드를 실행할 때 추가적인 오버헤드를 가집니다. 오버헤드의 양은 워크로드와 하드웨어에 따라 다릅니다. pyperformance 벤치마크 스위트에서 평균 오버헤드는 macOS aarch64의 경우 약 1%에서 x86-64 Linux 시스템의 8%까지 변합니다.

동작 변경¶

이 섹션에서는 자유 스레딩 빌드와 관련된 CPython 동작 변경 사항을 설명합니다.

컨텍스트 변수¶

In the free-threaded build, the flag thread_inherit_context is set to true by default which causes threads created with threading.Thread to start with a copy of the Context() of the caller of start(). In the default GIL-enabled build, the flag defaults to false so threads start with an empty Context().

경고 필터¶

In the free-threaded build, the flag context_aware_warnings is set to true by default. In the default GIL-enabled build, the flag defaults to false. If the flag is true then the warnings.catch_warnings context manager uses a context variable for warning filters. If the flag is false then catch_warnings modifies the global filters list, which is not thread-safe. See the warnings module for more details.

메모리 사용량 증가¶

자유 스레딩 빌드는 일반적으로 기본 빌드보다 더 많은 메모리를 사용할 것입니다. 여기에는 여러 가지 이유가 있으며, 주로 설계 결정에서 비롯된 것입니다.

모든 인턴화된 문자열은 불멸합니다¶

For modern Python versions (since version 2.3), interning a string (e.g. with sys.intern()) does not cause it to become immortal. Instead, if the last reference to that string disappears, it will be removed from the interned string table. This is not the case for the free-threaded build and any interned string will become immortal, surviving until interpreter shutdown.

비 GC 객체는 더 큰 객체 헤더를 가집니다¶

자유 스레딩 빌드는 다른 PyObject 구조를 사용합니다. 기본 빌드와 달리 GC 관련 정보가 PyObject 구조 앞에 할당되는 대신, GC 관련 정보는 일반 객체 헤더의 일부를 이룹니다. 예를 들어, AMD64 플랫폼에서 None 은 자유 스레딩 빌드에서 32바이트를, 기본 빌드에서 16바이트를 사용합니다. GC 객체(딕셔너리 및 리스트와 같은)는 자유 스레딩 빌드가 GC 정보에 추가 공간을 사용하지 않기 때문에 두 빌드에서 동일한 크기입니다.

QSBR이 메모리 해제를 지연시킬 수 있습니다¶

충돌 없는 자료 구조를 안전하게 구현하기 위해서는 SMR(Safe Memory Reclamation) 기법, 즉 quiescent state 기반 재할당(QSBR) 방식이 사용됩니다. 이는 데이터에 접근할 때 충돌이 없도록 하는 메모리 영역이 즉시 메모리를 해제하는 대신 QSBR을 사용하여 free 연산을 지연시키기 때문입니다. 이러한 자료 구조의 예시로 리스트 객체와 딕셔너리 키 객체가 있습니다. QSBR이 어떻게 구현되는지에 대한 더 자세한 내용은 CPython 소스 트리 내의 InternalDocs/qsbr.md 를 참조하십시오. gc.collect() 를 실행하면 QSBR에 의해 보유된 모든 메모리가 실제로 해제되어야 합니다. QSBR이 메모리를 해제할 때에도, 밑단 메모리 할당자가 즉시 해당 메모리를 OS에 반환하지 않을 수 있으므로, 프로세스의 상주 집합 크기(RSS)가 감소하지 않을 수도 있다는 점에 유의하십시오.

mimalloc 할당자 대 pymalloc 할당자¶

기본 빌드는 일반적으로 작은 할당(512바이트 이하)에는 “pymalloc” 메모리 할당자를 사용합니다. free-threaded 빌드는 pymalloc을 사용하지 않으며 모든 Python 객체는 “mimalloc” 할당자를 사용하여 할당됩니다. pymalloc 할당자는 메모리 사용량을 낮게 유지하는 데 도움이 되는 다음 속성들을 가지고 있습니다: 할당 블록당 오버헤드가 작음, 효과적인 메모리 단편화 방지, 그리고 해제된 메모리를 운영 체제에 빠르게 반환합니다. mimalloc 할당자 또한 이 측면에서 훌륭하게 동작하지만, 약간 더 많은 오버헤드를 가질 수 있습니다.

free-threaded 빌드에서는 mimalloc이 여러 개의 분리된 힙(현재 네 개)에 걸쳐 메모리를 관리합니다. 예를 들어, 모든 GC 지원 객체는 자체 힙에서 할당됩니다. 별도의 힙을 사용한다는 것은 한 힙에서 해제된 메모리가 다른 힙을 사용하는 할당에 사용될 수 없다는 것을 의미합니다. 또한, 일부 힙들은 힙의 메모리를 해제할 때(mimalloc 용어로는 “페이지”라고 함) QSBR(quiescent-state based reclamation)을 사용하도록 설정되어 있습니다. QSBR의 사용은 페이지가 해제되는 모든 메모리 블록과 해당 메모리 페이지가 해제되는 시점(새로운 할당이나 OS로 반납되는 경우) 사이에 지연을 만듭니다.

mimalloc 할당자 또한 해제된 메모리를 OS에 반환하는 것을 지연시킵니다. 환경 변수 MIMALLOC_PURGE_DELAY 를 0 으로 설정하여 이 지연을 줄일 수 있습니다. 하지만 이 경우 할당자의 성능이 저하될 가능성이 높다는 점에 유의하십시오.

free-threaded 참조 횟수는 객체가 더 오래 생존하게 할 수 있습니다¶

In the default build, when an object’s reference count reaches zero, it is normally deallocated. The free-threaded build uses “biased reference counting”, with a fast-path for objects “owned” by the current thread and a slow path for other objects. See PEP 703 for additional details. Any time an object’s reference count ends up in a “queued” state, deallocation can be deferred. The queued state is cleared from the “eval breaker” section of the bytecode evaluator.

free-threaded 빌드는 또한 “지연 참조 횟수(deferred reference counting)”라는 다른 방식의 참조 횟수 계산을 허용합니다. 이 모드는 객체별로 플래그를 설정하여 활성화할 수 있습니다. 지연 참조 횟수는 다음 유형에 대해 활성화됩니다:

  • 모듈 객체

  • 모듈 최상위 함수

  • 클래스 범위에 정의된 클래스 메서드

  • 디스크립터 객체

  • thread-local objects, created by threading.local

지연 참조 횟수가 활성화되면, Python 함수 스택의 참조는 참조 횟수에 추가되지 않습니다. 이 방식은 특히 여러 스레드에서 사용되는 객체의 참조 횟수 오버헤드를 줄여줍니다. 스택 참조가 계산되지 않기 때문에, 지연 참조 횟수를 가진 객체들은 내부 참조 횟수가 0이 되더라도 즉시 해제되지 않습니다. 대신, 다음 GC 주기에서 검사되며, 해당 객체에 스택 참조가 없으면 해제됩니다. 이는 일반적인 경우와 달리, 이 객체들이 참조 횟수가 0이 될 때가 아니라 GC에 의해 해제됨을 의미합니다.

스레드별 참조 횟수는 객체의 해제를 지연시킬 수 있습니다¶

자주 공유되는 객체의 참조 카운트 필드에 대한 경쟁을 방지하기 위해, 자유 스레드 빌드도 선택된 일부 객체 유형에 대해 “스레드별 참조 카운팅”을 사용합니다. 단일 공유 참조 카운트를 업데이트하는 대신, 각 스레드는 자신만의 로컬 참조 카운트 배열을 유지하며, 이 배열은 객체에 할당된 고유한 id로 인덱싱됩니다. 실제 참조 카운트는 객체의 로컬 카운트가 0으로 떨어질 때 스레드별 카운트를 합산하여 계산됩니다. 스레드별 참조 카운팅은 현재 다음을 위해 사용됩니다:

  • 힙 할당 타입 객체 (Python에서 생성된 클래스)

  • 코드 객체

  • 모듈 객체의 __dict__

Because the per-thread counts must be merged back to the object before it can be deallocated, objects using per-thread reference counting are typically freed later than they would be in the default build. In particular, such an object is usually not freed until the thread that referenced it reaches a safe point (for example, in the “eval breaker” section of the bytecode evaluator) or exits. Running gc.collect() will merge the per-thread counts and allow these objects to be freed.
