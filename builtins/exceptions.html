내장 예외(Built-in Exceptions)¶

파이썬에서 모든 예외는 BaseException 을 상속하는 클래스의 인스턴스여야 합니다. 특정 클래스를 명시한 except 절이 포함된 try 문에서, 해당 절은 그 클래스에서 파생된 모든 예외 클래스를 처리합니다(단, 그 클래스가 상속받은 상위 예외 클래스는 포함하지 않습니다). 서브클래싱을 통해 관련되지 않은 두 예외 클래스는 이름이 같더라도 결코 동일하게 취급되지 않습니다.

이 장에 나열된 내장 예외는 인터프리터나 내장 함수에 의해 생성될 수 있습니다. 언급된 경우를 제외하고, 이들은 오류의 상세 원인을 나타내는 “연관된 값(associated value)”을 가집니다. 이 값은 문자열이거나 여러 정보 항목(예: 에러 코드와 이를 설명하는 문자열)의 튜플일 수 있습니다. 연관된 값은 보통 예외 클래스의 생성자에 인자로 전달됩니다.

사용자 코드는 내장 예외를 발생시킬 수 있습니다. 이는 예외 핸들러를 테스트하거나 인터프리터가 동일한 예외를 발생시키는 상황과 “마찬가지로” 오류 상황을 보고하는 데 사용될 수 있습니다. 하지만 사용자 코드가 부적절한 오류를 발생시키는 것을 방지할 수 있는 장치는 없으므로 주의하십시오.

내장 예외 클래스는 새로운 예외를 정의하기 위해 서브클래스화할 수 있습니다. 프로그래머는 BaseException 이 아닌 Exception 클래스나 그 서브클래스 중 하나에서 새로운 예외를 파생시킬 것을 권장합니다. 예외 정의에 대한 자세한 정보는 파이썬 튜토리얼의 사용자 정의 예외 에서 확인할 수 있습니다.

예외 컨텍스트¶

예외 객체의 세 가지 속성은 예외가 발생한 컨텍스트에 대한 정보를 제공합니다.

BaseException.__context__¶
BaseException.__cause__¶
BaseException.__suppress_context__¶

다른 예외가 처리되는 중에 새로운 예외를 발생시킬 때, 새 예외의 __context__ 속성은 자동으로 처리 중인 예형 예외로 설정됩니다. 예외는 except 또는 finally 절이나 with 문이 사용될 때 처리될 수 있습니다.

이 암시적 예외 컨텍스트는 raise`와 함께 :keyword:!from`을 사용하여 명시적인 원인으로 보완할 수 있습니다.

raise new_exc from original_exc

from 뒤의 표현식은 예외이거나 None 이어야 합니다. 이는 발생한 예외의 __cause__ 로 설정됩니다. __cause__ 를 설정하면 __suppress_context__ 속성도 암시적으로 True 로 설정되므로, raise new_exc from None 을 사용하면 표시 목적상(예: KeyError 를 AttributeError 로 변환) 기존 예외를 새 예외로 교체하면서도 디버깅 시 내부 조사를 위해 기존 예외를 __context__ 에 남겨둘 수 있습니다.

기본 트레이스백 표시 코드는 예외 자체의 트레이스백 외에도 이러한 체인된 예환들을 보여줍니다. __cause__ 에 명시적으로 체인된 예외는 존재하는 경우 항상 표시됩니다. __context__ 에 암시적으로 체인된 예외는 __cause__ 가 None 이고 __suppress_context__ 가 False인 경우에만 표시됩니다.

어느 경우든 예외 자체는 항상 체인된 예환 뒤에 표시되어, 트레이스백의 마지막 줄이 항상 마지막으로 발생한 예외를 보여줍니다.

내장 예외 상속¶

사용자 코드는 예외 유형을 상속받는 서브클래스를 생성할 수 있습니다. 상위 클래스들이 args 속성을 처리하는 방식 간의 충돌을 방지하고 메모리 레이아웃 호환성 문제를 피하기 위해 한 번에 하나의 예외 유형만 상속받는 것을 권장합니다.

대부분의 내장 예환은 효율성을 위해 C로 구현되어 있습니다(참고: Objects/exceptions.c). 일부는 사용자 정의 메모리 레이아웃을 가지고 있어 여러 예환 유형을 상속받는 서브클래스를 만드는 것이 불가능합니다. 타입의 메모리 레이아웃은 구현의 세부 사항이며 파이썬 버전마다 변경될 수 있어 향후 새로운 충돌이 발생할 수 있습니다. 따라서 여러 예환 유형을 상속받는 것을 지양할 것을 권장합니다.

기본 클래스¶

다음 예환들은 주로 다른 예환들의 베이스 클래스로 사용됩니다.

exception BaseException¶

모든 내장 예환의 베이스 클래스입니다. 사용자 정의 클래스가 직접 상속하도록 설계되지 않았습니다(이 경우 Exception 을 사용하십시오). 이 클래스의 인스턴스에 대해 str() 을 호출하면 인자에 대한 표현이 반환되며, 인자가 없는 경우 빈 문자열이 반환됩니다.

args¶

예외 생성자에 전달된 인자들의 튜플입니다. 일부 내장 예환(예: OSError)은 특정 수의 인자를 기대하고 이 튜플의 요소에 특별한 의미를 부여하는 반면, 다른 것들은 보통 오류 메시지를 제공하는 단일 문자열과 함께 호출됩니다.

with_traceback(tb)¶

이 메서드는 tb 를 예외의 새로운 트레이스백으로 설정하고 예외 객체를 반환합니다. 이 기능은 PEP 3134 의 예외 체인 기능이 도입되기 전에 더 흔히 사용되었습니다. 다음 예제는 트레이스백을 유지하면서 SomeException 인스턴스를 OtherException 인스턴스로 변환하는 방법을 보여줍니다. 일단 발생하면, 현재 프레임이 OtherException 의 트레이스백에 추가됩니다. 이는 원본 SomeException 이 호출자에게 전파되었을 때 발생했을 트레이스백과 동일한 상황입니다.

try:
    ...
except SomeException:
    tb = sys.exception().__traceback__
    raise OtherException(...).with_traceback(tb)
__traceback__¶

이 예환과 연결된 트레이스백 객체 를 보유하는 쓰기 가능한 필드입니다. 참고: raise 문.

add_note(note)¶

예외 문자열 뒤에 표준 트레이스백에 나타나는 예환의 노트에 note 문자열을 추가합니다. note 가 문자열이 아니면 TypeError 가 발생합니다.

Added in version 3.11.

__notes__¶

add_note() 로 추가된 이 예환의 노트 목록입니다. 이 어트리뷰트는 add_note() 가 호출될 때 생성됩니다.

Added in version 3.11.

exception Exception¶

모든 내장 시스템 종료 예외는 이 클래스에서 파생됩니다. 모든 사용자 정의 예환도 이 클래스에서 파생되어야 합니다.

exception ArithmeticError¶

다양한 산술 오류에 대해 발생하는 내장 예환들의 베이스 클래스입니다: OverflowError, ZeroDivisionError, FloatingPointError.

exception BufferError¶

버퍼 관련 작업을 수행할 수 없을 때 발생합니다.

exception LookupError¶

매핑 또는 시퀀스에서 사용되는 키나 인덱스가 유효하지 않을 때 발생하는 예환들의 베이스 클래스입니다: IndexError, KeyError. 이는 codecs.lookup() 에 의해 직접 발생할 수 있습니다.

구체적인 예환(Concrete exceptions)¶

다음은 통상적으로 발생하는 예환들입니다.

exception AssertionError¶

인정할 수 없는 assert 문이 실패할 때 발생합니다.

exception AttributeError¶

어트리뷰트 참조(참고: 어트리뷰트 참조)나 할당이 실패할 때 발생합니다. (객체가 어트리뷰트 참조나 할당을 전혀 지원하지 않는 경우, TypeError 가 발생합니다.)

선택적 name 및 obj 키워드 전용 인자는 해당 어트리뷰트를 설정합니다:

name¶

액세스를 시도한 어트리뷰트의 이름입니다.

obj¶

해당 이름의 어트리뷰트에 대해 접근한 객체입니다.

가능한 경우, name 과 obj 는 자동으로 설정됩니다.

버전 3.10에서 변경: 어트리뷰트 name 과 obj 를 추가했습니다.

exception EOFError¶

input() 함수가 데이터를 읽지 않은 채 파일 끝(EOF)에 도달했을 때 발생합니다. (참고: io.TextIOBase.read() 및 io.IOBase.readline() 메서드는 EOF에 도달하면 빈 문자열을 반환합니다.)

exception FloatingPointError¶

현재 사용되지 않습니다.

exception GeneratorExit¶

제너레이터 또는 코루틴 이 닫힐 때 발생합니다. 참조: generator.close() 및 coroutine.close(). 이는 기술적으로 오류가 아니므로 Exception 대신 BaseException 을 직접 상속합니다.

exception ImportError¶

import 문이 모듈을 로드하는 데 문제가 생길 때 발생합니다. 또한 from ... import 에서 “from 리스트”에 포함된 이름이 존재하지 않을 때 발생합니다.

선택적 name 및 path 키워드 전용 인자는 해당 어트리뷰트를 설정합니다:

name¶

임포트를 시도한 모듈의 이름입니다.

path¶

예황을 유발한 파일의 경로입니다.

버전 3.3에서 변경: 어트리뷰트 name 과 path 를 추가했습니다.

exception ModuleNotFoundError¶

import 시 모듈을 찾을 수 없을 때 발생하는 ImportError 의 서브 클래스입니다. sys.modules 에서 None 이 발견될 때도 발생합니다.

Added in version 3.6.

exception ImportCycleError¶

지연 로드(lazy import)가 (직접 또는 간접적으로) 자기 자신을 임포트하려다 실패할 때 발생하는 ImportError 의 서브 클래스입니다.

Added in version 3.15.

exception IndexError¶

시퀀스 인덱스가 범위를 벗어날 때 발생합니다. (슬라이스 인덱스는 허용된 범위로 자동 절단됩니다. 인덱스가 정수가 아닌 경우 TypeError 가 발생합니다.)

exception KeyError¶

매핑(딕셔너리) 키를 기존 키 세트에서 찾을 수 없을 때 발생합니다.

exception KeyboardInterrupt¶

사용자가 인터럽트 키(일반적으로 Control-C 또는 Delete)를 눌렀을 때 발생합니다. 실행 중에 인터럽트 확인이 정기적으로 수행됩니다. 이 예외는 BaseException 을 상속받으므로, Exception 을 잡는 코드에 의해 실수로 잡히는 것을 방지하여 인터프리터가 종료되지 않도록 합니다.

참고

KeyboardInterrupt 을 처리할 때는 특별한 주의가 필요합니다. 예측할 수 없는 시점에 발생할 수 있기 때문에, 어떤 상황에서는 실행 중인 프로그램이 일관성 없는 상태로 남을 수 있습니다. 일반적으로는 KeyboardInterrupt 가 프로그램이 가능한 한 빨리 종료되도록 허용하거나 아예 발생하지 않도록 하는 것이 가장 좋습니다. (신호 처리기와 예외에 대한 참고 사항 참조.)

exception MemoryError¶

작업 중에 메모리가 부족하지만 상황을 구제할 수 있는 경우(일부 객체를 삭제함으로써)에 발생합니다. 연관된 값은 어떤 종류의 (내부) 작업에서 메모리가 부족했는지를 나타내는 문자열입니다. 기본 메모리 관리 구조(C의 malloc() 함수)로 인해 인터프리터가 항상 이 상황에서 완전히 복구할 수 있는 것은 아니지만, 제어되지 않는 프로그램이 원인인 경우 스택 추적을 출력할 수 있도록 예외를 발생시킵니다.

exception NameError¶

로컬 또는 전역 이름을 찾을 수 없을 때 발생합니다. 이는 한정되지 않은(unqualified) 이름에만 적용됩니다. 연관된 값은 찾을 수 없는 이름을 포함하는 에러 메시지입니다.

선택적인 name 키워드 전용 인수는 다음 어트리뷰트를 설정합니다:

name¶

접근을 시도했던 변수의 이름.

버전 3.10에서 변경: 어트리뷰트 name 을 추가했습니다.

exception NotImplementedError¶

이 예외는 RuntimeError 에서 파생되었습니다. 사용자가 정의한 기본 클래스에서 추상 메서드가 하위 클래스에서 재정의를 요구하거나, 클래스 개발 중에 실제 구현이 아직 추가되어야 함을 나타낼 때 이 예외를 발생시켜야 합니다.

참고

연산자나 메서드가 아예 지원되지 않음을 나타내기 위해 이 예외를 사용해서는 안 됩니다. 그러한 경우 연산자/메서드를 정의하지 않은 상태로 두거나, 하위 클래스인 경우 None 으로 설정하십시오.

조심

NotImplementedError 와 NotImplemented 는 서로 대체할 수 없습니다. 이 예외는 위에 설명된 대로만 사용되어야 하며, 내장 상수의 올바른 사용법에 대한 자세한 내용은 NotImplemented 를 참조하십시오.

exception OSError([arg])¶
exception OSError(errno, strerror[, filename[, winerror[, filename2]]])

시스템 함수가 “file not found” 또는 “disk full”과 같은 I/O 실패를 포함하여 시스템 관련 에러를 반환할 때 이 예외가 발생합니다(부적절한 인자 유형이나 기타 부수적인 에러의 경우에는 발생하지 않습니다).

생성자의 두 번째 형태는 아래에 기술된 해당 어트리뷰트들을 설정합니다. 명시되지 않은 어트리뷰트는 기본적으로 None 이 됩니다. 하위 호환성을 위해 세 개의 인자가 전달되는 경우, args 어트리뷰트에는 처음 두 생성자 인자만 포함된 2-튜플이 들어 있습니다.

생성자는 아래 OS exceptions 섹션에서 설명된 바와 같이 실제로는 OSError 의 하위 클래스를 반환하는 경우가 많습니다. 구체적인 하위 클래스는 최종 errno 값에 따라 달라집니다. 이 동작은 OSError 를 직접 생성하거나 별칭을 통해 생성할 때만 발생하며, 하위 클래스 상속 시에는 상속되지 않습니다.

errno¶

C 변수 errno 의 숫자 에러 코드입니다.

winerror¶

Windows 환경에서 이는 네이티브 Windows 에러 코드를 제공합니다. errno 어트리뷰트는 그 네이티브 에러 코드를 POSIX 관점에서 근사하게 변환한 값입니다.

Windows 환경에서 winerror 생성자 인자가 정수이면, errno 어트리뷰트가 Windows 에러 코드로부터 결정되고 errno 인자는 무시됩니다. 다른 플랫폼에서는 winerror 인자가 무시되며, winerror 어트리뷰트가 존재하지 않습니다.

strerror¶

운영체제에서 제공하는 해당 에러 메시지입니다. POSIX 환경에서는 C 함수 perror`에 의해, Windows 환경에서는 :c:func:()!FormatMessage`에 의해 포맷됩니다.

filename¶
filename2¶

파일 시스템 경로를 포함하는 예외(예: open() 또는 os.unlink())의 경우, filename 은 함수에 전달된 파일 이름입니다. 두 개의 파일 시스템 경로를 포함하는 함수(예: os.rename())의 경우, filename2 는 함수에 전달된 두 번째 파일 이름에 해당합니다.

버전 3.3에서 변경: EnvironmentError, IOError, WindowsError, socket.error, select.error 및 mmap.error 가 OSError 로 통합되었으며, 생성자는 하위 클래스를 반환할 수 있습니다.

버전 3.4에서 변경: filename 어트리뷰트는 이제 파일 시스템 인코딩 및 에러 처리기 에서 인코딩되거나 디코딩된 이름이 아니라 함수에 전달된 원래 파일 이름입니다. 또한 filename2 생성자 인자 및 어트리뷰트가 추가되었습니다.

exception OverflowError¶

산술 연산 결과가 표현하기에 너무 클 때 발생합니다. 정수형의 경우 표현이 불가능할 경우 MemoryError 를 발생시키기 때문에 발생하지 않습니다. 그러나 역사적인 이유로 인해 필수 범위를 약간 벗어난 정수에 대해서도 때때로 OverflowError가 발생합니다. C에서 부동 소수점 예외 처리가 표준화되어 있지 않기 때문에 대부분의 부동 소수점 연산은 확인되지 않습니다.

exception PythonFinalizationError¶

이 예환은 RuntimeError 에서 파생되었습니다. Python 마무리 라고도 알려진 인터프리터 종료 중에 작업이 차단될 때 발생합니다.

Python 마무리 과정에서 PythonFinalizationError 와 함께 차단될 수 있는 작업의 예는 다음과 같습니다.

  • 새로운 Python 스레드 생성.

  • 실행 중인 데몬 스레드를 Join.

  • os.fork(),

  • 그렇지 않았으면 교착 상태(deadlock)에 빠졌을 것이라고 알려진 상황에서 threading.Lock 과 같은 록을 획득하는 경우.

sys.is_finalizing() 함수도 참조하십시오.

Added in version 3.13: 이전에는 일반적인 RuntimeError 가 발생했습니다.

버전 3.14에서 변경: threading.Thread.join() 이 이제 이 예외를 발생시킬 수 있습니다.

버전 3.15에서 변경: threading.Lock() 또는 threading.RLock() 을 획득할 때 이 예외가 발생할 수 있습니다.

exception RecursionError¶

이 예외는 RuntimeError 에서 파생되었습니다. 인터프리터가 최대 재귀 깊이(sys.getrecursionlimit() 참조)를 초과했음을 감지할 때 발생합니다.

Added in version 3.5: 이전에는 일반적인 RuntimeError 가 발생했습니다.

exception ReferenceError¶

weakref.proxy() 함수로 생성된 약한 참조 프록시가 가비지 컬렉션된 후 참조 대상의 어트리뷰트에 접근하려고 할 때 이 예외가 발생합니다. 약한 참조에 대한 자세한 내용은 weakref 모듈을 참조하십시오.

exception RuntimeError¶

다른 범주 중 어디에도 속하지 않는 오류가 감지될 때 발생합니다. 연관된 값은 정확히 무엇이 잘못되었는지를 나타내는 문자열입니다.

exception StopIteration¶

내장 함수 next() 와 이터레이터 의 __next__() 메서드에서 이터레이터가 생성하는 항목이 더 이상 없을 때 이를 알리기 위해 발생합니다.

value¶

예외 객체는 예외를 구성할 때 인자로 제공되며 기본값이 None`인 단일 어트리뷰트 :attr:!value`를 가집니다.

제너레이터 또는 코루틴 함수가 반환될 때, 새로운 StopIteration 인스턴스가 발생하며, 함수에서 반환된 값이 예외 생성자의 value 매개변수로 사용됩니다.

제너레이터 코드가 직접 또는 간접적으로 StopIteration 을 발생시키면, RuntimeError 로 변환됩니다(이때 StopIteration 은 새 예외의 원인으로 유지됩니다).

버전 3.3에서 변경: Added value attribute and the ability for generator functions to use it to return a value.

버전 3.5에서 변경: Introduced the RuntimeError transformation via from __future__ import generator_stop, see PEP 479.

버전 3.7에서 변경: Enable PEP 479 for all code by default: a StopIteration error raised in a generator is transformed into a RuntimeError.

exception StopAsyncIteration¶

Must be raised by __anext__() method of an asynchronous iterator object to stop the iteration.

Added in version 3.5.

exception SyntaxError(message, details)¶

Raised when the parser encounters a syntax error. This may occur in an import statement, in a call to the built-in functions compile(), exec(), or eval(), or when reading the initial script or standard input (also interactively).

The str() of the exception instance returns only the error message. Details is a tuple whose members are also available as separate attributes.

filename¶

The name of the file the syntax error occurred in.

lineno¶

Which line number in the file the error occurred in. This is 1-indexed: the first line in the file has a lineno of 1.

offset¶

The column in the line where the error occurred. This is 1-indexed: the first character in the line has an offset of 1.

text¶

The source code text involved in the error.

end_lineno¶

Which line number in the file the error occurred ends in. This is 1-indexed: the first line in the file has a lineno of 1.

end_offset¶

The column in the end line where the error occurred finishes. This is 1-indexed: the first character in the line has an offset of 1.

For errors in f-string fields, the message is prefixed by “f-string: ” and the offsets are offsets in a text constructed from the replacement expression. For example, compiling f’Bad {a b} field’ results in this args attribute: (‘f-string: …’, (‘’, 1, 2, ‘(a b)n’, 1, 5)).

버전 3.10에서 변경: Added the end_lineno and end_offset attributes.

exception IndentationError¶

Base class for syntax errors related to incorrect indentation. This is a subclass of SyntaxError.

exception TabError¶

Raised when indentation contains an inconsistent use of tabs and spaces. This is a subclass of IndentationError.

exception SystemError¶

Raised when the interpreter finds an internal error, but the situation does not look so serious to cause it to abandon all hope. The associated value is a string indicating what went wrong (in low-level terms). In CPython, this could be raised by incorrectly using Python’s C API, such as returning a NULL value without an exception set.

If you’re confident that this exception wasn’t your fault, or the fault of a package you’re using, you should report this to the author or maintainer of your Python interpreter. Be sure to report the version of the Python interpreter (sys.version; it is also printed at the start of an interactive Python session), the exact error message (the exception’s associated value) and if possible the source of the program that triggered the error.

exception SystemExit¶

This exception is raised by the sys.exit() function. It inherits from BaseException instead of Exception so that it is not accidentally caught by code that catches Exception. This allows the exception to properly propagate up and cause the interpreter to exit. When it is not handled, the Python interpreter exits; no stack traceback is printed. The constructor accepts the same optional argument passed to sys.exit(). If the value is an integer, it specifies the system exit status (passed to C’s exit() function); if it is None, the exit status is zero; if it has another type (such as a string), the object’s value is printed and the exit status is one.

A call to sys.exit() is translated into an exception so that clean-up handlers (finally clauses of try statements) can be executed, and so that a debugger can execute a script without running the risk of losing control. The os._exit() function can be used if it is absolutely positively necessary to exit immediately (for example, in the child process after a call to os.fork()).

code¶

The exit status or error message that is passed to the constructor. (Defaults to None.)

exception TypeError¶

Raised when an operation or function is applied to an object of inappropriate type. The associated value is a string giving details about the type mismatch.

This exception may be raised by user code to indicate that an attempted operation on an object is not supported, and is not meant to be. If an object is meant to support a given operation but has not yet provided an implementation, NotImplementedError is the proper exception to raise.

Passing arguments of the wrong type (e.g. passing a list when an int is expected) should result in a TypeError, but passing arguments with the wrong value (e.g. a number outside expected boundaries) should result in a ValueError.

exception UnboundLocalError¶

Raised when a reference is made to a local variable in a function or method, but no value has been bound to that variable. This is a subclass of NameError.

exception UnicodeError¶

Raised when a Unicode-related encoding or decoding error occurs. It is a subclass of ValueError.

UnicodeError has attributes that describe the encoding or decoding error. For example, err.object[err.start:err.end] gives the particular invalid input that the codec failed on.

encoding¶

The name of the encoding that raised the error.

reason¶

A string describing the specific codec error.

object¶

The object the codec was attempting to encode or decode.

start¶

The first index of invalid data in object.

This value should not be negative as it is interpreted as an absolute offset but this constraint is not enforced at runtime.

end¶

The index after the last invalid data in object.

This value should not be negative as it is interpreted as an absolute offset but this constraint is not enforced at runtime.

exception UnicodeEncodeError¶

Raised when a Unicode-related error occurs during encoding. It is a subclass of UnicodeError.

exception UnicodeDecodeError¶

Raised when a Unicode-related error occurs during decoding. It is a subclass of UnicodeError.

exception UnicodeTranslateError¶

Raised when a Unicode-related error occurs during translating. It is a subclass of UnicodeError.

exception ValueError¶

Raised when an operation or function receives an argument that has the right type but an inappropriate value, and the situation is not described by a more precise exception such as IndexError.

exception ZeroDivisionError¶

Raised when the second argument of a division or modulo operation is zero. The associated value is a string indicating the type of the operands and the operation.

OS exceptions¶

The following exceptions are subclasses of OSError, they get raised depending on the system error code.

exception BlockingIOError¶

Raised when an operation would block on an object (e.g. socket) set for non-blocking operation. Corresponds to errno EAGAIN, EALREADY, EWOULDBLOCK and EINPROGRESS.

In addition to those of OSError, BlockingIOError can have one more attribute:

characters_written¶

An integer containing the number of bytes written to the stream before it blocked. This attribute is available when using the buffered I/O classes from the io module.

exception ChildProcessError¶

Raised when an operation on a child process failed. Corresponds to errno ECHILD.

exception ConnectionError¶

A base class for connection-related issues.

Subclasses are BrokenPipeError, ConnectionAbortedError, ConnectionRefusedError and ConnectionResetError.

exception BrokenPipeError¶

A subclass of ConnectionError, raised when trying to write on a pipe while the other end has been closed, or trying to write on a socket which has been shutdown for writing. Corresponds to errno EPIPE and ESHUTDOWN.

exception ConnectionAbortedError¶

A subclass of ConnectionError, raised when a connection attempt is aborted by the peer. Corresponds to errno ECONNABORTED.

exception ConnectionRefusedError¶

A subclass of ConnectionError, raised when a connection attempt is refused by the peer. Corresponds to errno ECONNREFUSED.

exception ConnectionResetError¶

A subclass of ConnectionError, raised when a connection is reset by the peer. Corresponds to errno ECONNRESET.

exception FileExistsError¶

Raised when trying to create a file or directory which already exists. Corresponds to errno EEXIST.

exception FileNotFoundError¶

Raised when a file or directory is requested but doesn’t exist. Corresponds to errno ENOENT.

exception InterruptedError¶

Raised when a system call is interrupted by an incoming signal. Corresponds to errno EINTR.

버전 3.5에서 변경: Python now retries system calls when a syscall is interrupted by a signal, except if the signal handler raises an exception (see PEP 475 for the rationale), instead of raising InterruptedError.

exception IsADirectoryError¶

Raised when a file operation (such as os.remove()) is requested on a directory. Corresponds to errno EISDIR.

exception NotADirectoryError¶

Raised when a directory operation (such as os.listdir()) is requested on something which is not a directory. On most POSIX platforms, it may also be raised if an operation attempts to open or traverse a non-directory file as if it were a directory. Corresponds to errno ENOTDIR.

exception PermissionError¶

Raised when trying to run an operation without the adequate access rights - for example filesystem permissions. Corresponds to errno EACCES, EPERM, and ENOTCAPABLE.

버전 3.11.1에서 변경: WASI’s ENOTCAPABLE is now mapped to PermissionError.

exception ProcessLookupError¶

Raised when a given process doesn’t exist. Corresponds to errno ESRCH.

exception TimeoutError¶

Raised when a system function timed out at the system level. Corresponds to errno ETIMEDOUT.

Added in version 3.3: All the above OSError subclasses were added.

Exception groups¶

The following are used when it is necessary to raise multiple unrelated exceptions. They are part of the exception hierarchy so they can be handled with except like all other exceptions. In addition, they are recognised by except*, which matches their subgroups based on the types of the contained exceptions.

exception ExceptionGroup(msg, excs)¶
exception BaseExceptionGroup(msg, excs)¶

Both of these exception types wrap the exceptions in the sequence excs. The msg parameter must be a string. The difference between the two classes is that BaseExceptionGroup extends BaseException and it can wrap any exception, while ExceptionGroup extends Exception and it can only wrap subclasses of Exception. This design is so that except Exception catches an ExceptionGroup but not BaseExceptionGroup.

The BaseExceptionGroup constructor returns an ExceptionGroup rather than a BaseExceptionGroup if all contained exceptions are Exception instances, so it can be used to make the selection automatic. The ExceptionGroup constructor, on the other hand, raises a TypeError if any contained exception is not an Exception subclass.

Exception groups are generic over the type of their contained exceptions.

CPython 구현 상세: The excs parameter may be any sequence, but lists and tuples are specifically processed more efficiently here. For optimal performance, pass a tuple as excs.

message¶

The msg argument to the constructor. This is a read-only attribute.

exceptions¶

A tuple of the exceptions in the excs sequence given to the constructor. This is a read-only attribute.

subgroup(condition)¶

Returns an exception group that contains only the exceptions from the current group that match condition, or None if the result is empty.

The condition can be an exception type or tuple of exception types, in which case each exception is checked for a match using the same check that is used in an except clause. The condition can also be a callable (other than a type object) that accepts an exception as its single argument and returns true for the exceptions that should be in the subgroup.

The nesting structure of the current exception is preserved in the result, as are the values of its message, __traceback__, __cause__, __context__ and __notes__ fields. Empty nested groups are omitted from the result.

The condition is checked for all exceptions in the nested exception group, including the top-level and any nested exception groups. If the condition is true for such an exception group, it is included in the result in full.

Added in version 3.13: condition can be any callable which is not a type object.

split(condition)¶

Like subgroup(), but returns the pair (match, rest) where match is subgroup(condition) and rest is the remaining non-matching part.

derive(excs)¶

Returns an exception group with the same message, but which wraps the exceptions in excs.

This method is used by subgroup() and split(), which are used in various contexts to break up an exception group. A subclass needs to override it in order to make subgroup() and split() return instances of the subclass rather than ExceptionGroup.

subgroup() and split() copy the __traceback__, __cause__, __context__ and __notes__ fields from the original exception group to the one returned by derive(), so these fields do not need to be updated by derive().

>>> class MyGroup(ExceptionGroup):
...     def derive(self, excs):
...         return MyGroup(self.message, excs)
...
>>> e = MyGroup("eg", [ValueError(1), TypeError(2)])
>>> e.add_note("a note")
>>> e.__context__ = Exception("context")
>>> e.__cause__ = Exception("cause")
>>> try:
...    raise e
... except Exception as e:
...    exc = e
...
>>> match, rest = exc.split(ValueError)
>>> exc, exc.__context__, exc.__cause__, exc.__notes__
(MyGroup('eg', [ValueError(1), TypeError(2)]), Exception('context'), Exception('cause'), ['a note'])
>>> match, match.__context__, match.__cause__, match.__notes__
(MyGroup('eg', [ValueError(1)]), Exception('context'), Exception('cause'), ['a note'])
>>> rest, rest.__context__, rest.__cause__, rest.__notes__
(MyGroup('eg', [TypeError(2)]), Exception('context'), Exception('cause'), ['a note'])
>>> exc.__traceback__ is match.__traceback__ is rest.__traceback__
True

Note that BaseExceptionGroup defines __new__(), so subclasses that need a different constructor signature need to override that rather than __init__(). For example, the following defines an exception group subclass which accepts an exit_code and constructs the group’s message from it.

class Errors(ExceptionGroup):
   def __new__(cls, errors, exit_code):
      self = super().__new__(Errors, f"exit code: {exit_code}", errors)
      self.exit_code = exit_code
      return self

   def derive(self, excs):
      return Errors(excs, self.exit_code)

Like ExceptionGroup, any subclass of BaseExceptionGroup which is also a subclass of Exception can only wrap instances of Exception.

Added in version 3.11.
