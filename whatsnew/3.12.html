PEP 693 – Python 3.12 릴리스 일정

요약 – 릴리스 하이라이트¶

Python 3.12는 언어와 표준 라이브러리에 걸쳐 변경 사항이 있는 파이썬 프로그래밍 언어의 안정화된 릴리스입니다. 라이브러리 변경 사항은 사용 중단된 API, 사용성 및 정확성을 정리하는 데 초점을 맞추고 있습니다. 주목할 점은 distutils 패키지가 표준 라이브러리에서 제거되었다는 것입니다. :mod:`os`와 :mod:`pathlib`의 파일 시스템 지원이 여러 개선 사항을 보였으며, 여러 모듈의 성능이 더 좋아졌습니다.

언어의 초점이 사용성으로 전환되었습니다. f-문자열 및 type 문은 정적 타입 검사기와 함께 사용할 때 제네릭 타입 및 :term:`타입 별칭 <type alias>`의 편의성을 향상시킵니다.

이 문서는 모든 새로운 기능에 대한 완전한 명세를 제공하려는 것이 아니라, 편리한 개요를 제공합니다. 자세한 내용은 라이브러리 참조 및 :ref:`언어 참조 <reference-index>`와 같은 설명서를 참고하십시오. 변경 사항의 전체 구현과 설계 근거를 이해하려면 특정 새 기능에 대한 PEP를 참조하십시오. 단, PEP는 통상적으로 해당 기능이 완전히 구현된 후에는 최신 상태로 유지되지 않습니다.

  • gh-95299: venv 로 생성된 가상 환경에 setuptools 를 미리 설치하지 마십시오. 이는 이제 기본적으로 distutils, setuptools, pkg_resources 및 easy_install 을 사용할 수 없음을 의미하며, 이를 사용하려면 활성화된 가상 환경에서 pip install setuptools 를 실행하십시오.

  • asynchat, asyncore 및 imp 모듈이 여러 unittest.TestCase `메서드 별칭 <unittest-TestCase-removed-aliases>`_와 함께 제거되었습니다.

새로운 기능들¶

PEP 695: 타입 매개변수 구문¶

:pep:`484`에 따른 제네릭 클래스 및 함수는 타입 매개변수의 범위를 불분명하게 하고 변동성(variance)의 명시적 선언을 요구하는 장황한 구문을 사용하여 선언되었습니다.

PEP 695 는 제네릭 클래스 및 함수 를 생성하는 새롭고 더 간결하며 명시적인 방법을 도입합니다:

def max[T](args: Iterable[T]) -> T:
    ...

class list[T]:
    def __getitem__(self, index: int, /) -> T:
        ...

    def append(self, element: T) -> None:
        ...

또한, 이 PEP는 TypeAliasType`의 인스턴스를 생성하는 :keyword:`type 문을 사용하여 :ref:`타입 별칭 <type-aliases>`를 선언하는 새로운 방법을 도입합니다:

type Point = tuple[float, float]

타입 별칭 또한 :ref:`제네릭 <generic-type-aliases>`이 될 수 있습니다:

type Point[T] = tuple[T, T]

새 구문은 TypeVarTuple 및 ParamSpec 매개변수와 경계 또는 제약이 있는 TypeVar 매개변수를 선언할 수 있게 합니다:

type IntFunc[**P] = Callable[P, int]  # ParamSpec
type LabeledTuple[*Ts] = tuple[str, *Ts]  # TypeVarTuple
type HashableSequence[T: Hashable] = Sequence[T]  # 경계가 있는 TypeVar
type IntOrStrSequence[T: (int, str)] = Sequence[T]  # 제약이 있는 TypeVar

이 구문을 통해 생성된 타입 별칭의 값과 타입 변수의 경계 및 제약은 요청 시에만 평가됩니다(참고: 지연 평가). 이는 타입 별칭이 파일 내에서 나중에 정의된 다른 타입을 참조할 수 있음을 의미합니다.

타입 매개변수 목록을 통해 선언된 타입 매개변수는 선언의 범위 및 모든 중첩된 범위 내에서는 보이지만, 외부 범위에서는 보이지 않습니다. 예를 들어, 이들은 제네릭 클래스의 메서드에 대한 타입 주석이나 클래스 본문에서 사용될 수 있습니다. 그러나 클래스가 정의된 후 모듈 범위에서는 사용할 수 없습니다. 타입 매개변수의 런타임 의미에 대한 자세한 설명은 Type parameter lists 를 참조하십시오.

이러한 스코핑 시맨틱을 지원하기 위해 새로운 종류의 범위인 :ref:`어노테이션 범위 <annotation-scopes>`가 도입됩니다. 어노테이션 범위는 대부분 기능 범위(function scope)와 유사하게 동작하지만, 감싸는 클래스 범위(enclosing class scopes)와는 다르게 상호작용합니다. Python 3.13에서는 :term:`어노테이션 <annotation>`도 어노테이션 범위에서 평가됩니다.

자세한 내용은 :pep:`695`를 참조하십시오.

(Eric Traut가 작성한 PEP. Jelle Zijlstra, Eric Traut 및 기타 인원들이 gh-103764 를 통해 구현하였습니다.)

PEP 701: f-문자열의 구문 공식화¶

PEP 701 은 f-문자열 의 사용에 대한 일부 제한을 완화합니다. f-문자열 내의 표현 구성 요소는 이제 포함된 f-문자열과 동일한 따옴표를 재사용하는 문자열, 여러 줄의 표현식, 주석, 백슬래시 및 유니코드 이스케이프 시퀀스를 포함하여 모든 유효한 파이썬 표현식이 될 수 있습니다. 이를 자세히 살펴보겠습니다:

  • 따옴표 재사용: 파이썬 3.11에서 둘러싼 f-문자열과 동일한 따옴표를 재사용하면 SyntaxError 가 발생하며, 사용자는 다른 가능한 따옴표(f-문자열이 단일 따옴표를 사용하는 경우 이중 따옴표 또는 삼중 따옴표 사용)를 사용해야만 했습니다. 파이썬 3.12에서는 이제 다음과 같은 처리가 가능합니다:

    >>> songs = ['Take me back to Eden', 'Alkaline', 'Ascensionism']
>>> f"This is the playlist: {", ".join(songs)}"
'This is the playlist: Take me back to Eden, Alkaline, Ascensionism'

    이 변경 사항 이전에는 f-문자열이 중첩될 수 있는 방법에 대한 명시적인 제한은 없었으나, f-문자열의 표현 구성 요소 내에서 문자열 따옴표를 재사용할 수 없다는 사실 때문에 f-문자열을 임의로 중첩하는 것이 불가능했습니다. 실제로 이것이 작성 가능한 가장 많이 중첩된 f-문자열입니다:

    >>> f"""{f'''{f'{f"{1+1}"}'}'''}"""
'2'

    이제 f-문자열이 표현 구성 요소 내에 유효한 파이썬 표현식을 포함할 수 있으므로, f-문자령을 임의로 중첩하는 것이 가능해졌습니다:

    >>> f"{f"{f"{f"{f"{f"{1+1}"}"}"}"}"}"
'2'

  • 여러 줄의 표현식 및 주석: 파이썬 3.11에서 f-문자열 표현은 f-문자령 내의 표현식이 통상적으로 여러 줄에 걸쳐 나타날 수 있더라도(여러 줄에 걸쳐 정의되는 리터럴 목록과 같은 경우) 한 줄로 정의되어야 했으므로 읽기 어려웠습니다. 파이썬 3.12에서는 이제 여러 줄에 걸친 f-문자열을 정의하고 인라인 주석을 추가할 수 있습니다:

    >>> f"This is the playlist: {", ".join([
...     'Take me back to Eden',  # My, my, those eyes like fire
...     'Alkaline',              # Not acid nor alkaline
...     'Ascensionism'           # Take to the broken skies at last
... ])}"
'This is the playlist: Take me back to Eden, Alkaline, Ascensionism'

  • 백슬래시 및 유니코드 문자: 파이썬 3.12 이전에는 f-문자열 표현에 어떤 \ 캐릭터도 포함할 수 없었습니다. 이는 또한, 이전에 f-문자령의 표현 구성 요소의 일부가 될 수 없었던 \N 부분을 포함하는 유니코드 이스케이프 시퀀스 (예를 들어 \N{snowman}) 등에도 영향을 미쳤습니다. 이제와 같이 표현을 정의할 수 있습니다:

    >>> print(f"This is the playlist: {"\n".join(songs)}")
This is the playlist: Take me back to Eden
Alkaline
Ascensionism
>>> print(f"This is the playlist: {"\N{BLACK HEART SUIT}".join(songs)}")
This is the playlist: Take me back to Eden♥Alkaline♥Ascensionism

자세한 내용은 PEP 701 을(를) 참조하십시오.

이 기능이 구현된 방식( the PEG parser 를 사용하여 f-문자열을 파싱)의 긍정적인 부수 효과로, 이제 f-문자령에 대한 오류 메시지가 더 정확해졌으며 오류의 정확한 위치를 포함합니다. 예를 들어, 파이썬 3.11에서 다음 f-문자량은 SyntaxError 를 발생시킵니다:

>>> my_string = f"{x z y}" + f"{1 + 1}"
  File "<stdin>", line 1
    (x z y)
     ^^^
SyntaxError: f-string: invalid syntax. Perhaps you forgot a comma?

하지만 오류 메시지에 해당 줄 내의 정확한 오류 위치가 포함되지 않으며 표현식이 인위적으로 괄호로 둘러싸여 있었습니다. 파이썬 3.12에서는 f-문자령이 PEG 파서로 파싱되므로, 오류 메시지가 더 정밀해지고 전체 줄을 표시합니다:

>>> my_string = f"{x z y}" + f"{1 + 1}"
  File "<stdin>", line 1
    my_string = f"{x z y}" + f"{1 + 1}"
                   ^^^
SyntaxError: invalid syntax. Perhaps you forgot a comma?

PEP 684: 인터프리터당 하나(Per-Interpreter)의 GIL¶

:pep:`684`는 인터프리터마다 고유한 GIL을 갖는 하위 인터프리터를 생성할 수 있도록 하는 인터프리터당 하나(per-interpreter)의 :term:`GIL <global interpreter lock>`를 도입합니다. 이를 통해 파이썬 프로그램이 여러 CPU 코어를 최대한 활용할 수 있게 됩니다. 이는 현재 C-API를 통해서만 가능하지만, 파이썬 API는 :pep:`anticipated for 3.13 <554>`입니다.

고유한 GIL을 가진 인터프리터를 생성하려면 새로운 Py_NewInterpreterFromConfig() 함수를 사용하십시오:

PyInterpreterConfig config = {
    .check_multi_interp_extensions = 1,
    .gil = PyInterpreterConfig_OWN_GIL,
};
PyThreadState *tstate = NULL;
PyStatus status = Py_NewInterpreterFromConfig(&tstate, &config);
if (PyStatus_Exception(status)) {
    return -1;
}
/* 새 인터프리터가 이제 현재 스레드에서 활성화됩니다. */

sub-interpreter를 위한 C-API 사용법에 관한 추가 예제는 Modules/_xxsubinterpretersmodule.c 를 참조하십시오.

(Eric Snow가 gh-104210 등에서 기여하였습니다.)

PEP 709: 컴프리헨션 인라이닝¶

딕셔너리, 리스트 및 셋 컴프리헨션은 이제 매 실행마다 단발성 함수 객체를 생성하는 대신 인라이닝됩니다. 이를 통해 컴프리헨션의 실행 속도가 최대 두 배까지 향상됩니다. 자세한 내용은 PEP 709 를 참고하십시오.

컴프리헨션 반복 변수는 격리된 상태를 유지하며 외부 스코프의 동일한 이름의 변수를 덮어쓰지 않으며, 컴프리헨션이 끝난 후에도 노출되지 않습니다. 인라이닝으로 인해 몇 가지 눈에 띄는 동작 변화가 발생합니다:

  • 트레이스백에서 컴프리헨션(comprehension)을 위한 별도의 프레임이 더 이상 존재하지 않으며, 트레이싱/프로파일링에서도 컴프리헨션을 함수 호출로 표시하지 않습니다.

  • symtable 모듈은 더 이상 각 컴프리헨션에 대해 자식 심볼 테이블을 생성하지 않으며, 대신 컴프리헨션의 로컬 변수가 부모 함수의 심볼 테이블에 포함됩니다.

  • 컴프리헨션 내부에서 locals`를 호출하면 이제 컴프리헨션 외부의 변수가 포함되며, 더 이상 컴프리헨션 "인증"에 대한 합성 `().0`` 변수를 포함하지 않습니다.

  • locals()``를 직접 반복하는 컴프리헨션(예: ``[k for k in locals()])은 트레이싱(예: 코드 커버리지 측정) 하에서 실행될 때 “RuntimeError: dictionary changed size during iteration”을 발생시킬 수 있습니다. 이는 이미 for k in locals(): 등에서 확인된 것과 동일한 동작입니다. 이 오류를 방지하려면 먼저 반복할 키의 목록을 생성하십시오: keys = list(locals()); [k for k in keys].

(Carl Meyer와 Vladimir Matveev가 :pep:`709`에서 기여하였습니다.)

PEP 698: 정적 타이핑을 위한 오버라이드 데코레이터¶

typing 모듈에 새로운 데코레이터 :deco:`typing.override`가 추가되었습니다. 이는 타입 검사기에게 해당 메서드가 상위 클래스의 메서드를 오버라이드하려는 의도임을 나타냅니다. 이를 통해 타입 검사기는 베이스 클래스에서 무언가를 오버라이드하려고 시도하지만 실제로는 그렇지 않은 경우를 감지할 수 있습니다.

예제:

from typing import override

class Base:
  def get_color(self) -> str:
    return "blue"

class GoodChild(Base):
  @override  # 확인됨: Base.get_color를 오버라이드함
  def get_color(self) -> str:
    return "yellow"

class BadChild(Base):
  @override  # 타입 검사기 오류: Base.get_color를 오버라이드하지 않음
  def get_color(self) -> str:
    return "red"

자세한 내용은 PEP 698 를 참고하십시오.

(Steven Troxler가 :gh:`101561`를 통해 기능을 구현하였습니다.)

타이핑¶

  • isinstance() 검사가 runtime-checkable protocols 에서 수행될 때, 이제 속성이 존재하는지 확인하기 위해 hasattr() 대신 inspect.getattr_static() 를 사용합니다. 이는 디스크립터 및 __getattr__() 메서드가 런타임 체크 가능 프로토콜에 대한 isinstance() 검사 중에 예상치 못하게 평가되지 않음을 의미합니다. 그러나, 이는 이전에는 런타임 체크 가능 프로토콜의 인스턴스로 간주되었던 일부 객체들이 Python 3.12 이상에서 더 이상 해당 프로토콜의 인스턴스로 간주되지 않을 수도 있으며 그 반대의 경우도 있을 수 있음을 의미합니다. 대부분의 사용자는 이 변경 사항의 영향을 받지 않을 것입니다. (Alex Waygood이 gh-102433 를 통해 기여함.)

  • 런타임 체크 가능 프로토콜의 멤버는 이제 클래스가 생성되는 즉시 런타임에서 “frozen” 상태로 간주됩니다. 런타임 체크 가능 프로토콜에 속성을 몽키 패치(monkey-patch)하더라도 여전히 작동하지만, 객체를 해당 프로토콜과 비교하는 isinstance() 검사에는 영향을 미치지 않습니다. 예를 들어:

    >>> from typing import Protocol, runtime_checkable
>>> @runtime_checkable
... class HasX(Protocol):
...     x = 1
...
>>> class Foo: ...
...
>>> f = Foo()
>>> isinstance(f, HasX)
False
>>> f.x = 1
>>> isinstance(f, HasX)
True
>>> HasX.y = 2
>>> isinstance(f, HasX)  # unchanged, even though HasX now also has a "y" attribute
True

    이 변경 사항은 런타임 체크 가능 프로토콜에 대한 isinstance() 검사 속도를 높이기 위해 수행되었습니다.

  • isinstance() 검사가 runtime-checkable protocols 에서 작동할 때의 성능 프로필이 상당히 변화했습니다. 멤버가 몇 개 없는 프로토콜에 대한 대부분의 isinstance() 검사는 3.11보다 최소 2배 더 빠르고, 일부는 20배 이상 빨라질 수 있습니다. 그러나 멤버가 많은 프로토콜에 대한 isinstance() 검사는 Python 3.11에서보다 느려질 수 있습니다. (Alex Waygood이 gh-74690 및 gh-103193 를 통해 기여함.)

  • 모든 typing.TypedDict 및 typing.NamedTuple 클래스가 이제 __orig_bases__ 속성을 가집니다. (Adrian Garcia Badaracco가 gh-103699 를 통해 기여함.)

  • platform:

  • types:

    • types.CodeType: codeobject.co_lnotab 에 대한 접근은 PEP 626 을 통해 3.10부터 사용 지원 중단(deprecated)되었으며 3.12에서 제거될 예정이었으나, 3.12에서 적절한 DeprecationWarning 만 추가되었습니다. 3.15에서 제거될 수 있습니다. (Nikita Sobolev가 gh-101866 를 통해 기여함.)

파이썬 3.17에서 제거 예정임¶

  • datetime:

    • 연도 정보가 없는 ``%e``(월의 일)를 포함하는 형식 문자열을 사용하는 strptime() 호출은 파이썬 3.15부터 사용 지원 중단되었습니다. (Stan Ulbrych가 gh-70647 를 통해 기능을 구현하였습니다.)

  • collections.abc:

    • :class:`collections.abc.ByteString`은 파이썬 3.17에서 제거될 예정입니다.

      실행 시점에 obj 가 buffer protocol 를 구현하는지 확인하려면 isinstance(obj, collections.abc.Buffer)``를 사용하십시오. 타입 어노테이션에서 사용하는 경우, :class:`~collections.abc.Buffer` 또는 코드가 지원하는 유형을 명시적으로 지정하는 유니언(예: ``bytes | bytearray | memoryview)을 사용하십시오.

      ByteString`은 원래 :class:`bytes`와 :class:`bytearray 모두의 상위 타입 역할을 하는 추상 클래스로 의도되었습니다. 그러나 이 ABC는 어떠한 메서드도 포함하지 않았기 때문에, 객체가 ByteString 인스턴스라는 사실을 알게 되어도 해당 객체에 대해 유용한 정보를 제공하지 못했습니다. 또한 memoryview`와 같은 다른 일반적인 버퍼 타입들도 (실행 시점이나 정적 타입 검사기에서) :class:!ByteString`의 하위 타입으로 인식되지 않았습니다.

      더 자세한 내용은 PEP 688 를 참고하십시오. (Shantanu Jain이 :gh:`91896`를 통해 기여했습니다.)

  • encodings:

    • encodings.normalize_encoding`에 비ASCII *encoding* 이름을 전달하는 것은 사용 지원 중단되었으며 파이썬 3.17에서 제거될 예정입니다. (Stan Ulbrych가 :gh:`136702() 를 통해 기능을 구현하였습니다.)

  • webbrowser:

    • webbrowser.MacOSXOSAScript`는 :class:!webbrowser.MacOS`를 대신하여 사용 지원 중단되었습니다. (gh-137586)

  • typing:

    • 파이썬 3.14 이전에는 구형 스타일의 유니언(union)을 비공개 클래스 ``typing._UnionGenericAlias``를 사용하여 구현했습니다. 이 클래스는 더 이상 구현에 필요하지 않지만, 하위 호환성을 위해 유지되어 왔으며 파이썬 3.17에서 제거될 예정입니다. 사용자는 비공개 구현 세부 사항에 의존하는 대신 typing.get_origin() 및 :func:`typing.get_args`와 같은 문서화된 인트로스펙션 도우미를 사용해야 합니다.

    • :class:`typing.ByteString`은 파이썬 3.9부터 사용 지원 중단되었으며 파이썬 3.17에서 제거될 예정입니다.

      실행 시점에 obj 가 buffer protocol 를 구현하는지 확인하려면 isinstance(obj, collections.abc.Buffer)``를 사용하십시오. 타입 어노테이션에서 사용하는 경우, :class:`~collections.abc.Buffer` 또는 코드가 지원하는 유형을 명시적으로 지정하는 유니언(예: ``bytes | bytearray | memoryview)을 사용하십시오.

      ByteString`은 원래 :class:`bytes`와 :class:`bytearray 모두의 상위 타입 역할을 하는 추상 클래스로 의도되었습니다. 그러나 이 ABC는 어떠한 메서드도 포함하지 않았기 때문에, 객체가 ByteString 인스턴스라는 사실을 알게 되어도 해당 객체에 대해 유용한 정보를 제공하지 못했습니다. 또한 memoryview`와 같은 다른 일반적인 버퍼 타입들도 (실행 시점이나 정적 타입 검사기에서) :class:!ByteString`의 하위 타입으로 인식되지 않았습니다.

      더 자세한 내용은 PEP 688 를 참고하십시오. (Shantanu Jain이 :gh:`91896`를 통해 기여했습니다.)

파이썬 3.12로 이식¶

이 섹션에서는 이전에 설명된 변경 사항과 코드를 수정해야 할 수 있는 다른 버그 수정 사항을 나열합니다.

파이썬 API의 변경 사항¶

  • 정규 표현식의 숫자 그룹 참조 및 그룹 이름에 대한 더 엄격한 규칙이 적용됩니다. 이제 수치 참조로는 ASCII 숫자의 시퀀스만 허용됩니다. 바이트 패턴과 치환 문자열 내의 그룹 이름에는 ASCII 영문자, 숫자, 밑줄(_)만 포함될 수 있습니다. (Serhiy Storchaka가 :gh:`91760`에 기여하였습니다.)

  • Python 3.10부터 폐지된 randrange() 기능이 제거되었습니다. 이전에는 randrange(10.0) 가 randrange(10) 로 손실 없이 변환되었으나 이제는 TypeError 를 발생시킵니다. 또한, randrange(10.5) 또는 randrange('10') 와 같은 정수가 아닌 값에 대해 발생하는 예외가 ValueError 에서 TypeError 로 변경되었습니다. 이는 randrange(1e25) 가 randrange(10**25) 보다 더 큰 범위에서 조용히 선택되는 버그를 방지합니다. (원래 Serhiy Storchaka gh-86388 에 의해 제안되었습니다.)

  • argparse.ArgumentParser`가 파일(예: ``fromfile_prefix_chars` 옵션)에서 인자를 읽을 때 사용하는 인코딩 및 에러 처리기가 기본 텍스트 인코딩(예: locale.getpreferredencoding(False))에서 :term:`파일 시스템 인코딩 및 에러 처리기 <filesystem encoding and error handler>`로 변경되었습니다. Windows에서는 ANSI Codepage 대신 UTF-8로 인코딩된 인자 파일이 사용되어야 합니다.

  • Python 3.4.7 및 3.5.4에서 폐지된 asyncore 기반의 smtpd 모듈을 제거했습니다. 권장되는 대체재는 asyncio 기반의 aiosmtpd PyPI 모듈입니다.

  • shlex.split(): s 인자에 None 을 전달하면 이제 sys.stdin 을 읽는 대신 예외를 발생시킵니다. 이 기능은 Python 3.9에서 폐지되었습니다. (Victor Stinner가 gh-94352 에서 기여했습니다.)

  • os 모듈은 더 이상 bytearray 및 memoryview`와 같은 바이트 유사(bytes-like) 경로를 수용하지 않습니다. 바이트 문자열의 경우 정확한 :class:`bytes 타입만 허용됩니다. (Victor Stinner가 :gh:`98393`에서 기여했습니다.)

  • syslog.openlog() 및 :func:`syslog.closelog`는 이제 서브 인터프리터에서 사용될 경우 실패합니다. :func:`syslog.syslog`는 서브 인터프리터에서도 여전히 사용할 수 있지만, 이제 메인 인터프리터에서 :func:`syslog.openlog`가 이미 호출된 경우에만 가능합니다. 이러한 새로운 제한 사항은 메인 인터프리터에는 적용되지 않으므로 매우 적은 수의 사용자에게만 영향을 미칠 것입니다. 이 변경 사항은 인터프리터 격리에 도움이 됩니다. 또한, :mod:`syslog`는 프로세스 전역 리소스를 래핑하며, 이는 메인 인터프리터에서 관리하는 것이 가장 좋습니다. (Donghee Na가 :gh:`99127`에서 기여했습니다.)

  • 문서화되지 않은 :deco:`~functools.cached_property`의 잠금 동작이 제거되었습니다. 이 기능은 클래스의 모든 인스턴스에 대해 잠금을 걸어 높은 잠금 경합(lock contention)을 유발했기 때문입니다. 이는 두 스레드가 경쟁하는 경우, 단일 인스턴스에 대해 캐시된 속성 getter 함수가 두 번 이상 실행될 수 있음을 의미합니다. 대부분의 간단한 캐시된 속성(예: 멱등성을 가지며 인스턴스의 다른 속성에 기반하여 단순히 값을 계산하는 것)의 경우 이 문제는 괜찮을 것입니다. 동기화가 필요한 경우에는 캐시된 속성 getter 함수 내부 또는 멀티 스레드 접근 지점 주변에 잠금을 구현하십시오.

  • sys._current_exceptions`는 이제 ``(typ, exc, tb)`() 튜플 대신 스레드 ID에서 예시 인스턴스로의 매핑을 반환합니다. (Irit Katriel이 :gh:`103176`을 통해 기여함.)

  • tarfile 또는 :func:`shutil.unpack_archive`를 사용하여 tar 파일을 추출할 때, 놀랍거나 위험할 수 있는 기능을 제한하려면 filter 인자를 전달하십시오. 자세한 내용은 :ref:`tarfile-extraction-filter`를 참고하십시오.

  • tokenize.tokenize() 및 tokenize.generate_tokens() 함수의 출력이 PEP 701 에서 도입된 변경 사항으로 인해 이제 변경되었습니다. 이는 f-문자열에 대해 STRING 토큰이 더 이상 방출되지 않고 대신 PEP 701 에서 설명하는 토큰들이 생성됨을 의미합니다: 즉, 표현식 구성 요소의 토큰화에 적절한 토큰 외에도 f-문자열 “문자열” 부분에 대하여 FSTRING_START, FSTRING_MIDDLE 및 FSTRING_END 가 이제 방출됩니다. 예를 들어, f-문자열 f"start {1+1} end" 의 경우 이전 버전의 토큰화기는 다음을 출력했습니다:

    1,0-1,18:           STRING         'f"start {1+1} end"'

    반면 새 버전은 다음을 출력합니다:

    1,0-1,2:            FSTRING_START  'f"'
1,2-1,8:            FSTRING_MIDDLE 'start '
1,8-1,9:            OP             '{'
1,9-1,10:           NUMBER         '1'
1,10-1,11:          OP             '+'
1,11-1,12:          NUMBER         '1'
1,12-1,13:          OP             '}'
1,13-1,17:          FSTRING_MIDDLE ' end'
1,17-1,18:          FSTRING_END    '"'

    추가로, PEP 701 지원에 필요한 변경 사항으로 인해 몇 가지 사소한 동작 변화가 있을 수 있습니다. 이러한 변경 사항 중 일부는 다음을 포함합니다:

    • ! 와 같은 몇 가지 잘못된 파이썬 문자를 토큰화할 때 방출되는 토큰의 type 속성이 ERRORTOKEN 에서 OP 로 변경되었습니다.

    • 불완전한 한 줄 문자열도 이제 불완전한 여러 줄 문자열과 마찬가지로 :exc:`tokenize.TokenError`를 발생시킵니다.

    • 일부 불완전하거나 유효하지 않은 파이썬 코드를 토큰화할 때 임의의 ERRORTOKEN 토큰을 반환하는 대신 :exc:`tokenize.TokenError`를 발생시킵니다.

    • 동일한 파일 내에서 탭과 스페이스를 혼합하여 들여쓰기를 사용하는 것은 더 이상 지원되지 않으며 :exc:`TabError`를 발생시킵니다.

파이썬 3.12로 이식¶

  • Legacy Unicode APIs based on Py_UNICODE* representation has been removed. Please migrate to APIs based on UTF-8 or wchar_t*.

  • Argument parsing functions like PyArg_ParseTuple() doesn’t support Py_UNICODE* based format (e.g. u, Z) anymore. Please migrate to other formats for Unicode like s, z, es, and U.

  • tp_weaklist for all static builtin types is always NULL. This is an internal-only field on PyTypeObject but we’re pointing out the change in case someone happens to be accessing the field directly anyway. To avoid breakage, consider using the existing public C-API instead, or, if necessary, the (internal-only) _PyObject_GET_WEAKREFS_LISTPTR() macro.

  • This internal-only PyTypeObject.tp_subclasses may now not be a valid object pointer. Its type was changed to void* to reflect this. We mention this in case someone happens to be accessing the internal-only field directly.

    To get a list of subclasses, call the Python method __subclasses__() (using PyObject_CallMethod(), for example).

  • Add support of more formatting options (left aligning, octals, uppercase hexadecimals, intmax_t, ptrdiff_t, wchar_t C strings, variable width and precision) in PyUnicode_FromFormat() and PyUnicode_FromFormatV(). (Contributed by Serhiy Storchaka in gh-98836.)

  • An unrecognized format character in PyUnicode_FromFormat() and PyUnicode_FromFormatV() now sets a SystemError. In previous versions it caused all the rest of the format string to be copied as-is to the result string, and any extra arguments discarded. (Contributed by Serhiy Storchaka in gh-95781.)

  • Fix wrong sign placement in PyUnicode_FromFormat() and PyUnicode_FromFormatV(). (Contributed by Philip Georgi in gh-95504.)

  • Extension classes wanting to add a __dict__ or weak reference slot should use Py_TPFLAGS_MANAGED_DICT and Py_TPFLAGS_MANAGED_WEAKREF instead of tp_dictoffset and tp_weaklistoffset, respectively. The use of tp_dictoffset and tp_weaklistoffset is still supported, but does not fully support multiple inheritance (gh-95589), and performance may be worse. Classes declaring Py_TPFLAGS_MANAGED_DICT must call _PyObject_VisitManagedDict() and _PyObject_ClearManagedDict() to traverse and clear their instance’s dictionaries. To clear weakrefs, call PyObject_ClearWeakRefs(), as before.

  • The PyUnicode_FSDecoder() function no longer accepts bytes-like paths, like bytearray and memoryview types: only the exact bytes type is accepted for bytes strings. (Contributed by Victor Stinner in gh-98393.)

  • The Py_CLEAR, Py_SETREF and Py_XSETREF macros now only evaluate their arguments once. If an argument has side effects, these side effects are no longer duplicated. (Contributed by Victor Stinner in gh-98724.)

  • The interpreter’s error indicator is now always normalized. This means that PyErr_SetObject(), PyErr_SetString() and the other functions that set the error indicator now normalize the exception before storing it. (Contributed by Mark Shannon in gh-101578.)

  • _Py_RefTotal is no longer authoritative and only kept around for ABI compatibility. Note that it is an internal global and only available on debug builds. If you happen to be using it then you’ll need to start using _Py_GetGlobalRefTotal().

  • The following functions now select an appropriate metaclass for the newly created type:

    • PyType_FromSpec()

    • PyType_FromSpecWithBases()

    • PyType_FromModuleAndSpec()

    Creating classes whose metaclass overrides tp_new is deprecated, and in Python 3.14+ it will be disallowed. Note that these functions ignore tp_new of the metaclass, possibly allowing incomplete initialization.

    Note that PyType_FromMetaclass() (added in Python 3.12) already disallows creating classes whose metaclass overrides tp_new (__new__() in Python).

    Since tp_new overrides almost everything PyType_From* functions do, the two are incompatible with each other. The existing behavior – ignoring the metaclass for several steps of type creation – is unsafe in general, since (meta)classes assume that tp_new was called. There is no simple general workaround. One of the following may work for you:

    • If you control the metaclass, avoid using tp_new in it:

      • If initialization can be skipped, it can be done in tp_init instead.

      • If the metaclass doesn’t need to be instantiated from Python, set its tp_new to NULL using the Py_TPFLAGS_DISALLOW_INSTANTIATION flag. This makes it acceptable for PyType_From* functions.

    • Avoid PyType_From* functions: if you don’t need C-specific features (slots or setting the instance size), create types by calling the metaclass.

    • If you know the tp_new can be skipped safely, filter the deprecation warning out using warnings.catch_warnings() from Python.

  • PyOS_InputHook and PyOS_ReadlineFunctionPointer are no longer called in subinterpreters. This is because clients generally rely on process-wide global state (since these callbacks have no way of recovering extension module state).

    This also avoids situations where extensions may find themselves running in a subinterpreter that they don’t support (or haven’t yet been loaded in). See gh-104668 for more info.

  • PyLongObject has had its internals changed for better performance. Although the internals of PyLongObject are private, they are used by some extension modules. The internal fields should no longer be accessed directly, instead the API functions beginning PyLong_... should be used instead. Two new unstable API functions are provided for efficient access to the value of PyLongObjects which fit into a single machine word:

    • PyUnstable_Long_IsCompact()

    • PyUnstable_Long_CompactValue()

  • Custom allocators, set via PyMem_SetAllocator(), are now required to be thread-safe, regardless of memory domain. Allocators that don’t have their own state, including “hooks”, are not affected. If your custom allocator is not already thread-safe and you need guidance then please create a new GitHub issue and CC @ericsnowcurrently.

    • Type macros like Py_T_INT, Py_T_DOUBLE, etc. (previously T_INT, T_DOUBLE, etc.)

    • Py_GetPath(): Use PyConfig_Get("module_search_paths") (sys.path) instead.

    • Py_GetPrefix(): Use PyConfig_Get("base_prefix") (sys.base_prefix) instead. Use PyConfig_Get("prefix") (sys.prefix) if virtual environments need to be handled.

    • Py_GetExecPrefix(): Use PyConfig_Get("base_exec_prefix") (sys.base_exec_prefix) instead. Use PyConfig_Get("exec_prefix") (sys.exec_prefix) if virtual environments need to be handled.

    • Py_GetProgramFullPath(): Use PyConfig_Get("executable") (sys.executable) instead.

    • Py_GetProgramName(): Use PyConfig_Get("executable") (sys.executable) instead.

    • Py_GetPythonHome(): Use PyConfig_Get("home") or the PYTHONHOME environment variable instead.

    The pythoncapi-compat project can be used to get PyConfig_Get() on Python 3.13 and older.

향후 버전에서 제거 예정인 항목들¶

The following APIs are deprecated and will be removed, although there is currently no date scheduled for their removal.

  • Py_TPFLAGS_HAVE_FINALIZE: Unneeded since Python 3.8.

  • PyErr_Fetch(): Use PyErr_GetRaisedException() instead.

  • PyErr_NormalizeException(): Use PyErr_GetRaisedException() instead.

  • PyErr_Restore(): Use PyErr_SetRaisedException() instead.

  • PyModule_GetFilename(): Use PyModule_GetFilenameObject() instead.

  • PyOS_AfterFork(): Use PyOS_AfterFork_Child() instead.

  • PySlice_GetIndicesEx(): Use PySlice_Unpack() and PySlice_AdjustIndices() instead.

  • PyUnicode_READY(): Unneeded since Python 3.12

  • PyErr_Display(): Use PyErr_DisplayException() instead.

  • _PyErr_ChainExceptions(): Use _PyErr_ChainExceptions1() instead.

  • PyBytesObject.ob_shash member: call PyObject_Hash() instead.

  • Thread Local Storage (TLS) API:

    • PyThread_create_key(): Use PyThread_tss_alloc() instead.

    • PyThread_delete_key(): Use PyThread_tss_free() instead.

    • PyThread_set_key_value(): Use PyThread_tss_set() instead.

    • PyThread_get_key_value(): Use PyThread_tss_get() instead.

    • PyThread_delete_key_value(): Use PyThread_tss_delete() instead.

    • PyThread_ReInitTLS(): Unneeded since Python 3.7.

  • Remove the token.h header file. There was never any public tokenizer C API. The token.h header file was only designed to be used by Python internals. (Contributed by Victor Stinner in gh-92651.)

  • Legacy Unicode APIs have been removed. See PEP 623 for detail.

    • PyUnicode_WCHAR_KIND

    • PyUnicode_AS_UNICODE()

    • PyUnicode_AsUnicode()

    • PyUnicode_AsUnicodeAndSize()

    • PyUnicode_AS_DATA()

    • PyUnicode_FromUnicode()

    • PyUnicode_GET_SIZE()

    • PyUnicode_GetSize()

    • PyUnicode_GET_DATA_SIZE()

  • Remove the PyUnicode_InternImmortal() function macro. (Contributed by Victor Stinner in gh-85858.)
