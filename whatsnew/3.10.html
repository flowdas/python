파이썬 3.10의 새로운 기능¶

편집자:

파블로 갈린도 살가도

이 기사에서는 3.9와 비교한 파이썬 3.10의 새로운 기능에 대해 설명합니다. 파이썬 3.10은 2021년 10월 4일에 출시되었습니다. 자세한 내용은 변경 내역\을 참조하십시오.

새로운 문법 기능:

  • PEP 634, Structural Pattern Matching: 사양

  • PEP 635, 구조적 패턴 매칭: 동기 및 근거

새로운 기능들¶

괄호로 묶인 컨텍스트 관리자¶

컨텍스트 매니저에서 여러 줄에 걸친 계속을 위해 감싸는 괄호를 사용하는 것이 이제 지원됩니다. 이를 통해 컨텍스트 관리자의 긴 컬렉션을 이전에는 임포트 문으로 가능했던 방식으로 여러 줄 형식화할 수 있습니다. 예를 들어, 이 모든 예제가 이제 유효합니다:

with (CtxManager() as example):
    ...

with (
    CtxManager1(),
    CtxManager2()
):
    ...

with (CtxManager1() as example,
      CtxManager2()):
    ...

with (CtxManager1(),
      CtxManager2() as example):
    ...

with (
    CtxManager1() as example1,
    CtxManager2() as example2
):
    ...

감싸는 그룹의 끝에 쉼표를 사용하는 것도 가능합니다:

with (
    CtxManager1() as example1,
    CtxManager2() as example2,
    CtxManager3() as example3,
):
    ...

이 새로운 구문은 새 파서의 non LL(1) 기능을 사용합니다. 자세한 내용은 :pep:`617`을 확인하십시오.

(Guido van Rossum, Pablo Galindo 및 Lysandros Nikolaou가 bpo-12782 및 :issue:`40334`에서 기여함.)

개선된 오류 메시지¶

SyntaxErrors (구문 에러)¶

괄호나 대괄호가 닫히지 않은 코드를 구문 분석할 때, 인터프리터는 SyntaxError: unexpected EOF while parsing 을 표시하거나 잘못된 위치를 가리키는 대신, 열린 괄호의 위치를 포함합니다. 예를 들어, 다음 코드를 고려해 보세요 (닫히지 않은 ‘{’: 주의).

expected = {9: 1, 18: 2, 19: 2, 27: 3, 28: 3, 29: 3, 36: 4, 37: 4,
            38: 4, 39: 4, 45: 5, 46: 5, 47: 5, 48: 5, 49: 5, 54: 6,
some_other_code = foo()

이전 버전의 인터프리터는 구문 오류의 위치를 혼란스러운 장소로 보고했습니다:

File "example.py", line 3
    some_other_code = foo()
                    ^
SyntaxError: invalid syntax

하지만 Python 3.10에서는 더 상세한 오류가 발생합니다:

File "example.py", line 1
    expected = {9: 1, 18: 2, 19: 2, 27: 3, 28: 3, 29: 3, 36: 4, 37: 4,
               ^
SyntaxError: '{' was never closed

닫히지 않은 문자열 리터럴(단일 및 삼중 인용)과 관련된 오류는 이제 EOF/EOL을 보고하는 대신 문자열 시작 지점을 가리킵니다.

이러한 개선 사항은 이전 PyPy 인터프리터의 작업에서 영감을 받았습니다.

(Pablo Galindo가 :issue:`42864`에, Batuhan Taskaya가 :issue:`40176`에 기여했습니다.)

인터프리터에 의해 발생한 SyntaxError 예외는 이제 오류가 발견된 위치뿐만 아니라 구문 오류 자체를 구성하는 전체 오류 범위도 강조합니다. 이런 방식으로, (Python 3.10 이전의 표시 방식과 달리):

>>> foo(x, z for z in range(10), t, w)
  File "<stdin>", line 1
    foo(x, z for z in range(10), t, w)
           ^
SyntaxError: Generator expression must be parenthesized

이제 Python 3.10에서는 다음과 같이 예외가 표시됩니다:

>>> foo(x, z for z in range(10), t, w)
  File "<stdin>", line 1
    foo(x, z for z in range(10), t, w)
           ^^^^^^^^^^^^^^^^^^^^
SyntaxError: Generator expression must be parenthesized

이 개선 사항은 Pablo Galindo님이 :issue:`43914`에서 기여하셨습니다.

SyntaxError 예외에 대한 상당량의 새로운 전문화된 메시지가 통합되었습니다. 가장 눈에 띄는 몇 가지는 다음과 같습니다:

  • 블록 앞에 누락된 ::

    >>> if rocket.position > event_horizon
  File "<stdin>", line 1
    if rocket.position > event_horizon
                                      ^
SyntaxError: expected ':'

    (Pablo Galindo가 기여했습니다; bpo-42997.)

  • 컴프리헨션에서 괄호가 없는 튜플 대상:

    >>> {x,y for x,y in zip('abcd', '1234')}
  File "<stdin>", line 1
    {x,y for x,y in zip('abcd', '1234')}
     ^
SyntaxError: did you forget parentheses around the comprehension target?

    (Pablo Galindo가 기여했습니다; bpo-43017.)

  • 컬렉션 리터럴과 표현식 사이의 누락된 쉼표:

    >>> items = {
... x: 1,
... y: 2
... z: 3,
  File "<stdin>", line 3
    y: 2
       ^
SyntaxError: invalid syntax. Perhaps you forgot a comma?

    (Pablo Galindo가 :issue:`43822`에서 기여함.)

  • 괄호 없는 여러 예외 유형:

    >>> try:
...     build_dyson_sphere()
... except NotEnoughScienceError, NotEnoughResourcesError:
  File "<stdin>", line 3
    except NotEnoughScienceError, NotEnoughResourcesError:
           ^
SyntaxError: multiple exception types must be parenthesized

    (Pablo Galindo가 :issue:`43149`에서 기여함.)

  • 딕셔너리 리터럴에 : 와 값이 누락된 경우:

    >>> values = {
... x: 1,
... y: 2,
... z:
... }
  File "<stdin>", line 4
    z:
     ^
SyntaxError: expression expected after dictionary key and ':'

>>> values = {x:1, y:2, z w:3}
  File "<stdin>", line 1
    values = {x:1, y:2, z w:3}
                        ^
SyntaxError: ':' expected after dictionary key

    (Pablo Galindo가 :issue:`43823`에서 기여함.)

  • except``나 ``finally 블록 없이 try 블록만 있는 경우:

    >>> try:
...     x = 2
... something = 3
  File "<stdin>", line 3
    something  = 3
    ^^^^^^^^^
SyntaxError: expected 'except' or 'finally' block

    (Pablo Galindo가 :issue:`44305`에서 기여함.)

  • 비교 시 == 대신 = 을 사용한 점:

    >>> if rocket.position = event_horizon:
  File "<stdin>", line 1
    if rocket.position = event_horizon:
                       ^
SyntaxError: cannot assign to attribute here. Maybe you meant '==' instead of '='?

    (Pablo Galindo가 :issue:`43797`에서 기여했습니다.)

  • f-문장에서 * 의 사용법:

    >>> f"Black holes {*all_black_holes} and revelations"
  File "<stdin>", line 1
    (*all_black_holes)
     ^
SyntaxError: f-string: cannot use starred expression here

    (Pablo Galindo 기여자; bpo-41064.)

들여쓰기 오류¶

많은 IndentationError 예외는 어떤 종류의 블록이 들여쓰기를 기대했는지, 그리고 해당 구문의 위치를 포함하여 더 많은 맥락을 가지게 되었습니다:

>>> def foo():
...    if lel:
...    x = 2
  File "<stdin>", line 3
    x = 2
    ^
IndentationError: expected an indented block after 'if' statement in line 2

AttributeErrors¶

AttributeError`를 인쇄할 때, :c:func:!PyErr_Display`는 예외가 발생한 객체에서 유사한 속성 이름을 제안합니다:

>>> collections.namedtoplo
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
AttributeError: module 'collections' has no attribute 'namedtoplo'. Did you mean: namedtuple?

(Pablo Galindo 기재; bpo-38530.)

경고

만약 다른 사용자 지정 오류 표시 함수가 사용된 경우에 발생할 수 있는 문제라, :c:func:`!PyErr_Display`를 호출하여 오류를 표시하지 않으면 작동하지 않는 점에 유의하십시오. 이는 IPython과 같은 일부 REPL에서 흔한 시나리오입니다.

NameErrors¶

인터프리터가 발생시킨 NameError`를 출력할 때, :c:func:!PyErr_Display`는 예외가 발생한 함수에서 유사한 변수 이름을 제안하여 보여줍니다:

>>> schwarzschild_black_hole = None
>>> schwarschild_black_hole
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
NameError: name 'schwarschild_black_hole' is not defined. Did you mean: schwarzschild_black_hole?

(Pablo Galindo 기재; bpo-38530.)

경고

만약 다른 사용자 지정 오류 표시 함수가 사용된 경우에 발생할 수 있는 문제라, :c:func:`!PyErr_Display`를 호출하여 오류를 표시하지 않으면 작동하지 않는 점에 유의하십시오. 이는 IPython과 같은 일부 REPL에서 흔한 시나리오입니다.

PEP 626: 디버깅 및 기타 도구를 위한 정밀한 행 번호¶

PEP 626은 디버깅, 프로파일링 및 커버리지 도구에 더 정확하고 안정적인 행 번호를 가져옵니다. 올바른 행 번호를 가진 이벤트 추적은 실행되는 모든 코드 라인과 실제로 실행되는 코드 라인에 대해서만 생성됩니다.

프레임 객체의 f_lineno 속성은 항상 예상된 행 번호를 포함합니다.

code objects <code-objects>`의 :attr:!codeobject.co_lnotab` 속성은 더 이상 사용되지 않으며 3.12 버전에서 제거될 예정입니다. 오프셋을 행 번호로 변환해야 하는 코드는 대신 새로운 co_lines() 메서드를 사용하십시오.

PEP 634: 구조적 패턴 매칭¶

구조적 패턴 매칭은 match 문 과 연결된 액션을 가진 케이스 문 의 형태로 추가되었습니다. 패턴은 시퀀스, 맵핑, 원시 데이터 유형뿐만 아니라 클래스 인스턴스로 구성됩니다. 패턴 매칭은 프로그램이 복잡한 데이터에서 정보를 추출하고, 데이터 구조에 따라 분기하며, 서로 다른 데이터 형태를 기반으로 특정 액션을 적용할 수 있게 합니다.

구문 및 연산¶

패턴 매칭의 일반적인 구문은 다음과 같습니다:

match subject:
    case <pattern_1>:
        <action_1>
    case <pattern_2>:
        <action_2>
    case <pattern_3>:
        <action_3>
    case _:
        <action_wildcard>

match 문은 표현식을 받아 그 값을 하나 이상의 케이스 블록으로 주어진 연속된 패턴과 비교합니다. 구체적으로, 패턴 매칭은 다음을 통해 작동합니다:

  1. 타입과 모양(subject)을 가진 데이터 사용

  2. match 문에서 subject 평가

  3. 대상(subject)과 각 패턴을 위에서 아래로 비교하여 일치하는지 확인합니다.

  4. 확인된 일치에 연결된 액션 실행

  5. 정확히 일치하는 것이 확인되지 않으면, 마지막 케이스(와일드카드 _)가 제공된 경우 일치 케이스로 사용됩니다. 정확히 일치하는 것이 확인되지 않았고 와일드카드 케이스가 존재하지 않으면, 전체 match 블록은 아무 작업도 하지 않습니다 (no-op).

선언적 접근 방식¶

독자들은 C, Java 또는 JavaScript(및 다른 많은 언어)의 switch 문에서 주체(data object)를 리터럴(pattern)과 매칭하는 간단한 예제를 통해 패턴 매칭을 알고 있을 수 있습니다. 종종 switch 문은 객체/표현식을 리터럴을 포함하는 케이스문과 비교하는 데 사용됩니다.

Scala나 Elixir와 같은 언어에서는 더 강력한 패턴 매칭 예시를 찾을 수 있습니다. 구조적 패턴 매칭을 사용하면 접근 방식이 “선언적”이며 데이터가 일치하는 조건(패턴)을 명시적으로 밝히게 됩니다.

중첩된 “if” 문을 사용하는 “명령형” 명령어들로 구조적 패턴 매칭과 유사한 것을 수행할 수는 있지만, 선언적인 접근 방식보다 명확하지 않습니다. 대신 “선언적” 접근 방식은 일치에 필요한 조건을 명시하고 그 명시적인 패턴을 통해 가독성이 높습니다. 구조적 패턴 매칭은 변수를 case 문 리터럴과 비교하는 가장 간단한 형태로 사용될 수 있지만, Python의 진정한 값은 대상의 타입 및 형태를 다루는 데 있습니다.

단순 패턴: 리터럴에 매치하기¶

가장 단순한 형태의 패턴 매칭 예시를 살펴보겠습니다. 값(subject)이 여러 리터럴(patterns)과 일치하는 경우를 매칭합니다. 아래 예제에서 `status`는 match 문의 subject입니다. 패턴은 각각 case 문이며, 리터럴은 요청 상태 코드를 나타냅니다. 해당 case와 연결된 액션은 매치가 발생한 후에 실행됩니다:

def http_error(status):
    match status:
        case 400:
            return "Bad request"
        case 404:
            return "Not found"
        case 418:
            return "I'm a teapot"
        case _:
            return "Something's wrong with the internet"

위 함수에 status 가 418인 경우, “I’m a teapot”이 반환됩니다. 위 함수에 status 가 500인 경우, case 문 _ 를 와일드카드처럼 매치하고 “Something’s wrong with the internet”이 반환됩니다. 마지막 블록에 주목해주세요: 변수 이름인 _ 는 와일드카드 역할을 하여 subject가 항상 매치되도록 보장합니다. _ 의 사용은 선택적입니다.

파이프 기호(|)를 사용하여 단일 패턴 내에 여러 리터럴을 결합할 수 있습니다:

case 401 | 403 | 404:
    return "Not allowed"
와일드카드가 없는 동작 방식¶

위 예제에서 마지막 case 블록을 제거하여 수정하면 다음과 같습니다:

def http_error(status):
    match status:
        case 400:
            return "Bad request"
        case 404:
            return "Not found"
        case 418:
            return "I'm a teapot"

case 문에 _ 를 사용하지 않으면, 매치는 존재하지 않을 수 있습니다. 매치가 존재하지 않으면 no-op(아무 작업도 수행하지 않음) 동작이 발생합니다. 예를 들어, status 가 500인 경우 no-op 동작이 발생합니다.

리터럴과 변수를 포함하는 패턴¶

패턴은 언패킹 할당문처럼 보일 수 있으며, 패턴을 사용하여 변수를 바인딩할 수 있습니다. 이 예제에서는 데이터 포인트를 x 좌표와 y 좌표로 언패킹할 수 있습니다:

# point는 (x, y) 튜플입니다
match point:
    case (0, 0):
        print("Origin")
    case (0, y):
        print(f"Y={y}")
    case (x, 0):
        print(f"X={x}")
    case (x, y):
        print(f"X={x}, Y={y}")
    case _:
        raise ValueError("Not a point")

첫 번째 패턴은 두 개의 리터럴인 (0, 0) 을 가지고 있으며, 위의 리터럴 패턴의 확장으로 생각할 수 있습니다. 다음 두 패턴은 리터럴과 변수를 결합하며, 변수는 subject (point)에서 값을 바인딩 합니다. 네 번째 패턴은 두 개의 값을 포착하여 개념적으로 언패킹 할당문 (x, y) = point 와 유사하게 만듭니다.

패턴과 클래스¶

데이터를 구조화하기 위해 클래스를 사용하는 경우, 생성자와 유사한 인자 목록에 이어서 클래스 이름을 패턴으로 사용할 수 있습니다. 이 패턴은 인스턴스 어트리뷰트를 변수로 캡처하는 기능을 가지고 있습니다:

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

def location(point):
    match point:
        case Point(x=0, y=0):
            print("Origin is the point's location.")
        case Point(x=0, y=y):
            print(f"Y={y} and the point is on the y-axis.")
        case Point(x=x, y=0):
            print(f"X={x} and the point is on the x-axis.")
        case Point():
            print("The point is located somewhere else on the plane.")
        case _:
            print("Not a point")
위치 기반 매개변수를 포함하는 패턴¶

어트리뷰트에 순서를 제공하는 일부 내장 클래스(예: dataclasses)에서는 위치 기반 매개변수를 사용할 수 있습니다. 또한, 클래스의 __match_args__ 특별 어트리뷰트를 설정하여 패턴에서 어트리뷰트의 특정 위치를 정의할 수도 있습니다. 이 값이 (“x”, “y”)로 설정되어 있으면, 다음 모든 패턴은 동일하며 (모두 y 어트리뷰트를 var 변수에 바인딩합니다):

Point(1, var)
Point(1, y=var)
Point(x=1, y=var)
Point(y=var, x=1)

중첩된 패턴¶

패턴은 임의로 중첩될 수 있습니다. 예를 들어, 데이터가 포인트에 대한 짧은 리스트인 경우 다음과 같이 매치될 수 있습니다:

match points:
    case []:
        print("No points in the list.")
    case [Point(0, 0)]:
        print("The origin is the only point in the list.")
    case [Point(x, y)]:
        print(f"A single point {x}, {y} is in the list.")
    case [Point(0, y1), Point(0, y2)]:
        print(f"Two points on the Y axis at {y1}, {y2} are in the list.")
    case _:
        print("Something else is found in the list.")

복합 패턴과 와일드카드¶

이전 예시들에서는 마지막 case statement에서 _ 만을 사용했습니다. 와일드카드(wildcard)는 ('error', code, _) 와 같이 더 복잡한 패턴에서도 사용할 수 있습니다. 예를 들면:

match test_variable:
    case ('warning', code, 40):
        print("A warning has been received.")
    case ('error', code, _):
        print(f"An error {code} occurred.")

위의 경우, test_variable 은 (‘error’, code, 100)과 (‘error’, code, 800)에 대해 모두 일치합니다.

보호 구문 (Guard)¶

패턴에 “가드(guard)”라고 알려진 if 절을 추가할 수 있습니다. 가드가 거짓이면, match 는 다음 case 블록으로 진행됩니다. 참고로 값 포획은 가드가 평가되기 전에 발생합니다:

match point:
    case Point(x, y) if x == y:
        print(f"The point is located on the diagonal Y=X at {x}.")
    case Point(x, y):
        print(f"Point is not on the diagonal.")

그 외 주요 기능들¶

몇 가지 다른 주요 기능들:

  • 언패킹 할당과 같이, 튜플 및 리스트 패턴은 완전히 동일한 의미를 가지고 임의의 시퀀스에 일치합니다. 기술적으로 주어는 시퀀스를 나타내야 합니다. 따라서 중요한 예외 사항은 패턴이 이터레이터를 매칭하지 않는다는 점입니다. 또한 일반적인 실수 방지를 위해, 시퀀스 패턴은 문자열과도 매칭되지 않습니다.

  • 시퀀스 패턴은 와일드카드를 지원합니다: [x, y, *rest] 와 (x, y, *rest) 는 언패킹 할당에서 와일드카드와 유사하게 작동합니다. * 뒤의 이름은 _ 일 수도 있으므로, (x, y, *_ ) 는 나머지 항목을 바인딩하지 않고 최소한 두 개의 항목으로 구성된 시퀀스와 일치합니다.

  • 매핑 패턴: {"bandwidth": b, "latency": l} 은 딕셔너리에서 "bandwidth" 와 "latency" 값을 포획합니다. 시퀀스 패턴과 달리, 추가 키는 무시됩니다. 와일드카드 **rest 도 지원됩니다. (하지만 **_ 는 중복적이라서 허용하지 않습니다.)

  • 하위 패턴은 as 키워드를 사용하여 포획할 수 있습니다:

    case (Point(x1, y1), Point(x2, y2) as p2): ...

    이는 as 절 없이 예상하는 대로 x1, y1, x2, y2를 바인딩하며, p2는 주어의 두 번째 항목 전체에 바인딩됩니다.

  • 대부분의 리터럴은 동등성으로 비교됩니다. 그러나 싱글톤 값인 True, False 및 None 은 아이덴티티로 비교됩니다.

  • 패턴에서는 이름이 지정된 상수를 사용할 수 있습니다. 이러한 이름이 지정된 상수들은 상수가 포획 변수로 해석되는 것을 방지하기 위해 점 표기법(dotted names)이어야 합니다:

    from enum import Enum
class Color(Enum):
    RED = 0
    GREEN = 1
    BLUE = 2

color = Color.GREEN
match color:
    case Color.RED:
        print("I see red!")
    case Color.GREEN:
        print("Grass is green")
    case Color.BLUE:
        print("I'm feeling the blues :(")

전체 사양은 :pep:`634`를 참조하십시오. 동기 및 근거는 :pep:`635`에 있고, 더 긴 튜토리얼은 :pep:`636`에 있습니다.

선택적 EncodingWarning 및 encoding="locale" 옵션¶

대부분의 Unix 플랫폼에서는 UTF-8이 사용되므로, UTF-8 파일(예: JSON, YAML, TOML, Markdown)을 열 때 ``encoding` 옵션을 생략하는 것은 매우 흔한 버그입니다. 예를 들면:

# 버그: "rb" 모드 또는 encoding="utf-8"를 사용해야 합니다.
with open("data.json") as f:
    data = json.load(f)

이러한 유형의 버그를 찾기 위해, 선택적 EncodingWarning 이 추가되었습니다. 이는 sys.flags.warn_default_encoding 가 참이고 로케일별 기본 인코딩을 사용할 때 방출됩니다.

경고를 활성화하려면 -X warn_default_encoding 옵션과 :envvar:`PYTHONWARNDEFAULTENCODING`이 추가되었습니다.

더 자세한 정보는 :ref:`io-text-encoding`을 참조하십시오.

타입 힌트와 관련된 새로운 기능¶

본 섹션에서는 PEP 484 타입 힌트와 typing 모듈에 영향을 미치는 주요 변경 사항을 다룹니다.

PEP 604: 새로운 타입 유니온 연산자¶

새로운 타입 유니온 연산자가 도입되어 X | Y 문법을 사용할 수 있게 되었습니다. 이는 특히 타입 힌트에서 :class:`typing.Union`을 사용하는 대신 ‘X 타입 또는 Y 타입’을 표현하는 더 깔끔한 방법을 제공합니다.

이전 버전의 Python에서는, 여러 타입을 인수로 받는 함수에 대한 타입 힌트를 적용하기 위해 :class:`typing.Union`이 사용되었습니다:

def square(number: Union[int, float]) -> Union[int, float]:
    return number ** 2

이제 타입 힌트는 더 간결한 방식으로 작성할 수 있습니다:

def square(number: int | float) -> int | float:
    return number ** 2

이 새로운 구문은 또한 :func:`isinstance`와 :func:`issubclass`의 두 번째 인수로도 허용됩니다:

>>> isinstance(1, int | str)
True

더 자세한 내용은 :ref:`types-union`과 :pep:`604`를 참조하십시오.

(Maggie Moss와 Philippe Prados가 bpo-41428, 그리고 Yurii Karabas와 Serhiy Storchaka가 :issue:`44490`에서 추가하였습니다.)

PEP 612: 매개변수 지정 변수들¶

PEP 484 의 Callable 에 대한 정적 타입 검사기에게 제공되는 정보를 개선하기 위해 두 가지 새로운 선택 사항이 typing 모듈에 추가되었습니다.

첫 번째는 매개 변수 사양 변수입니다. 이는 하나의 호출 가능한 개체의 매개 변수 유형을 다른 호출 가능한 개체에 전달하는 데 사용되는 패턴으로, 주로 고차 함수와 데코레이터에서 발견됩니다. 사용 예시는 :class:`typing.ParamSpec`에서 찾을 수 있습니다. 이전에는 이처럼 정확한 방식으로 매개 변수 유형의 종속성을 타입 주석 처리할 쉬운 방법이 없었습니다.

두 번째 옵션은 새로운 Concatenate 연산자입니다. 이것은 매개 변수 사양 변수와 함께 사용되어 다른 호출 가능한 개체의 매개 변수를 추가하거나 제거하는 고차 호출 가능 개체를 타입 주석 처리하는 데 사용됩니다. 사용 예시는 :class:`typing.Concatenate`에서 찾을 수 있습니다.

자세한 내용은 typing.Callable, typing.ParamSpec, typing.Concatenate, typing.ParamSpecArgs, typing.ParamSpecKwargs 및 :pep:`612`를 참조하십시오.

(Ken Jin이 :issue:`41559`에서 기여하고, Jelle Zijlstra가 :issue:`43783`에서 사소하게 향상시켰습니다. PEP는 Mark Mendoza가 작성했습니다.)

PEP 613: 타입 별칭(TypeAlias)¶

:pep:`484`는 타입 별칭의 개념을 도입했으며, 최상위 레벨의 주석 없는 할당만 요구했습니다. 이러한 단순성은 특히 포워드 참조나 유효하지 않은 유형이 포함된 경우, 타입 검사기가 타입 별칭과 일반적인 할당을 구별하기 어렵게 만들 때가 있었습니다. 비교 예시입니다:

StrCache = 'Cache[str]'  # 타입 별칭
LOG_PREFIX = 'LOG[DEBUG]'  # 모듈 상수

이제 typing 모듈에는 더 명시적으로 타입 별칭을 선언할 수 있게 해주는 특별한 값인 :data:`~typing.TypeAlias`가 있습니다:

StrCache: TypeAlias = 'Cache[str]'  # 타입 별칭
LOG_PREFIX = 'LOG[DEBUG]'  # 모듈 상수

더 자세한 내용은 :pep:`613`을 참조하십시오.

(Mikhail Golubev가 :issue:`41923`에서 기여했습니다.)

PEP 647: 사용자 정의 타입 가드 (User-Defined Type Guards)¶

TypeGuard`가 :mod:`typing 모듈에 추가되어 타입 가드 함수를 주석 처리하고, 유형 축소 중 정적 타입 검사기에 제공되는 정보를 개선합니다. 더 자세한 정보는 :data:`~typing.TypeGuard`의 문서를 참조하시고, :pep:`647`을 참고하십시오.

(Ken Jin과 Guido van Rossum이 :issue:`43766`에서 기여하고, PEP는 Eric Traut이 작성했습니다.)

이외의 언어 변경 사항¶

  • int 타입에 새 메서드 :meth:`int.bit_count`가 추가되어, 주어진 정수의 이진수 전개에 있는 1의 개수를 반환합니다. 이는 인구 수(population count)라고도 알려져 있습니다. (Niklas Fiekas가 :issue:`29882`에서 기여했습니다.)

  • dict.keys(), dict.values() 및 dict.items`가 반환하는 뷰는 이제 모두 원본 딕셔너리를 감싸는 :class:`types.MappingProxyType() 개체를 제공하는 mapping 속성을 갖게 되었습니다. (Dennis Sweeney가 :issue:`40890`에서 기여했습니다.)

  • PEP 618: zip() 함수에 이제 선택적 strict 플래그가 추가되어, 모든 이터러블이 동일한 길이를 가지도록 요구하는 데 사용됩니다.

  • 정수 인자를 받는 내장 및 확장 함수는 더 이상 Decimal들, Fraction들과 정수로 변환될 때 손실을 수반하는 다른 객체들(예: __int__() 메서드는 있지만, __index__() 메서드는 없는 것들)를 허용하지 않습니다. (Serhiy Storchaka가 :issue:`37999`에서 기여했습니다.)

  • 만약 :func:`object.__ipow__`가 :data:`NotImplemented`를 반환하면, 연산자는 예상대로 :func:`object.__pow__`와 :func:`object.__rpow__`로 올바르게 폴백됩니다. (Alex Shkop이 :issue:`38302`에서 기여했습니다.)

  • 할당 표현식을 이제 세트 리터럴 및 세트 컴프리헨션 내에서는 물론 시퀀스 인덱스(슬라이스는 제외) 내에서도 괄호 없이 사용할 수 있습니다.

Keyword-only fields¶

dataclasses는 이제 생성된 __init__ 메서드에서 키워드 전용 필드를 지원합니다. 키워드 전용 필드를 지정하는 여러 방법이 있습니다.

모든 필드가 키워드 전용이라고 할 수 있습니다:

from dataclasses import dataclass

@dataclass(kw_only=True)
class Birthday:
    name: str
    birthday: datetime.date

name``과 ``birthday 모두 생성된 __init__ 메서드의 키워드 전용 매개변수입니다.

필드별로 키워드 전용을 지정할 수 있습니다:

from dataclasses import dataclass, field

@dataclass
class Birthday:
    name: str
    birthday: datetime.date = field(kw_only=True)

여기서는 birthday 만 키워드 전용입니다. 개별 필드에 kw_only 를 설정할 때는, 키워드 전용 필드가 비키워드 전용 필드 뒤에 위치해야 하므로 필드 재정렬에 관한 규칙이 있다는 점에 유의하십시오. 자세한 내용은 전체 dataclasses 문서를 참조하십시오.

또한 KW_ONLY 마커 다음에 오는 모든 필드가 키워드 전용임을 지정할 수도 있습니다. 이것이 아마도 가장 일반적인 사용법일 것입니다:

from dataclasses import dataclass, KW_ONLY

@dataclass
class Point:
    x: float
    y: float
    _: KW_ONLY
    z: float = 0.0
    t: float = 0.0

여기서 z 와 t 는 키워드 전용 매개변수이고, x 와 y 는 그렇지 않습니다. (Eric V. Smith가 bpo-43532 에서 기여함.)

    • A call to PyParser_SimpleParseStringFlags followed by PyNode_Compile can be replaced by calling Py_CompileString().

    • There is no direct replacement for PyParser_SimpleParseFileFlags. To compile code from a FILE * argument, you will need to read the file in C and pass the resulting buffer to Py_CompileString().

source_bytes_object = PyObject_CallMethod(fileobject, "read", "");
result = PyObject_CallMethod(fileobject, "close", "");

code = Py_CompileString(source_buf, filename, Py_file_input);

Notable security feature in 3.10.7¶

Converting between int and str in bases other than 2 (binary), 4, 8 (octal), 16 (hexadecimal), or 32 such as base 10 (decimal) now raises a ValueError if the number of digits in string form is above a limit to avoid potential denial of service attacks due to the algorithmic complexity. This is a mitigation for CVE 2020-10735. This limit can be configured or disabled by environment variable, command line flag, or sys APIs. See the integer string conversion length limitation documentation. The default limit is 4300 digits in string form.

Notable security feature in 3.10.8¶

The deprecated mailcap module now refuses to inject unsafe text (filenames, MIME types, parameters) into shell commands. Instead of using such text, it will warn and act as if a match was not found (or for test commands, as if the test failed). (Contributed by Petr Viktorin in gh-98966.)

See 추출 필터입니다. for details. In Python 3.12, use without the filter argument will show a DeprecationWarning. In Python 3.14, the default will switch to 'data'. (Contributed by Petr Viktorin in PEP 706.)
